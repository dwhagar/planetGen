## 3. What the code does today

Checked against the checkout on 2026-10-09 (revisions 0061 to 0065 exist):

- `planetgen/db/alembic_runner.py`: a revision's id is its schema version as four digits (`0062`), baseline `0061`. `upgrade()` stamps `alembic_version` to the stored version, then per pending revision runs `command.upgrade`, `connection.commit()`, then `record(version)` into `schema_migrations`. `env.py` runs online only, on the runner's connection, with `target_metadata=None`: revisions are hand-written, not autogenerated.
- `store.migrate_database` holds a MySQL named lock (`_schema_lock`, `SCHEMA_LOCK_WAIT_S = 600`) for the whole migration and first runs all of `schema.sql` (`CREATE TABLE IF NOT EXISTS`), so a new table exists before its revision runs; a new column or index on an old table is the revision's job. `update.sh` runs `planetgen.cli.migrate --status`, then `planetgen.cli.migrate`, on the console without capturing output and without stopping services.
- `planetgen/cli/migrate.py` draws one rich `Progress` over steps with `TimeRemainingColumn`; steps differ hugely in cost, so the estimate is poor, and nothing shows progress inside a step. It does not use `StageProgress` (`cli/reset.py` and `cli/orbits.py` do).
- Interrupt window: between `connection.commit()` and `record(target)` the database has `alembic_version = N+1` while `schema_migrations` says N. The next run restamps to N and re-runs N+1, so every revision must be idempotent. Revision 0063 checks `information_schema` first, but copies `generation_runs.arguments` with one INSERT per argument in a Python loop and builds five indexes with plain `CREATE INDEX`: fine on a small table, the wrong pattern for a large one.
- MySQL DDL is not transactional (`MySQLImpl.transactional_ddl = False` [S: Alembic source]); a revision that stops half way stays half applied. The DB.8 schema check treats that as a normal failure mode.
- `db/models.py` is generated from `schema.sql` (`scripts/generate_db_models.py`) for `compare_metadata`; `tests/test_db_models.py` keeps it honest. Migration fixtures are `src/tests/fixtures/old_schemas/schema_v61` to `v64`.
- `schema.sql` has 71 foreign keys, enforced; only `cli/reset.py` (line 173) sets `foreign_key_checks=0`, so orphans appear only after such loads. The control database has its own version (`CONTROL_SCHEMA_VERSION = 10`), not Alembic.
- Absent: a `check-db` or `repair-db` command, a checksum column, a parity file, and any database dump step (`cli/render_parity.py` mentions `mysqldump` only in a docstring).

## 4. How MariaDB behaves when a page is damaged

Measured on MariaDB 10.11.14 by flipping 8 bytes in one page of a 400,000-row table [C]; MySQL 8.4's read path returns an error and flags the index rather than crashing while `innodb_force_recovery` is below `SRV_FORCE_IGNORE_CORRUPT` [S: `buf0buf.cc`].

| Damaged page | `CHECK TABLE` | Later queries | `CHECKSUM TABLE` | Repair |
|---|---|---|---|---|
| Secondary index | "The B-tree of index parent_id is corrupted"; "Index contains 158560 entries, should be 400000" | `SELECT COUNT(*)` fails with error 1712 on every connection until the index is dropped and re-added | still works, same value as before (reads the clustered index) | Rebuild the index; no parity needed |
| Clustered index (PRIMARY) | PRIMARY B-tree corrupt | `COUNT(*)` fails (error 1030, engine error 1877). After a restart, a range that avoids the bad page still reads; a range crossing it fails with error 1034 | NULL | Rebuild the table (below) |

- `innochecksum` (shipped with both servers) found the bad page offline ("Fail: page::1184 invalid") [C]; it needs the server stopped or a file copy.
- InnoDB verifies a page's checksum when it is read from disk into the buffer pool, not while it sits in memory, so a cached page hides on-disk damage until it is evicted or the server restarts [S source]. MySQL 8.4 `innodb_checksum_algorithm` values are `crc32` (default), `strict_crc32`, `innodb`, `strict_innodb`, `none`, `strict_none`; MariaDB 11.4's are `crc32`, `strict_crc32`, `full_crc32` (default), `strict_full_crc32`. The doublewrite buffer covers torn page writes, not bit rot. The checker reports `@@innodb_checksum_algorithm`, `@@innodb_doublewrite` and `@@innodb_page_size` as advisories.
- **Repair of a bad clustered page** is a bigger job than "rebuild each damaged sector". SQL can neither read nor delete the rows on that page. Repair has to: stop writers; make the server skip the bad page (`innodb_force_recovery=1`, which needs a restart [R for the documented behaviour; the check is in `buf0buf.cc` [S]]); dump the surviving rows of each affected table; drop and recreate the table; reload with `foreign_key_checks=0`; delete any partial sector left over; insert the parity-rebuilt exports with their original ids (other tables reference them). A bad page belongs to one table, so the work is grouped per table.
- The DB.9 test should flip bytes in an `.ibd` page of a copy while the server is stopped, not `UPDATE` rows, or it will not exercise the real failure.

## 5. Parity repair (DB.9, DB.10)

### 5.1 Checksums detect, parity corrects

A checksum says "these bytes are not the bytes we hashed" but not where, and cannot fix anything. Reed-Solomon parity over k data blocks with m parity blocks rebuilds any m blocks it is told are missing (erasures); finding m wrong blocks unaided would take 2m parity blocks. Here every sector has a stored checksum, so a failing checksum names the erased member, and the rebuilt bytes are checked against the stored checksum before being written (a stale parity record would otherwise miscorrect silently). XOR parity (RAID 5) is the case m = 1: the codec's first parity row is all ones.

### 5.2 The export must leave out what the orbit update rewrites

`store.advance_orbital_phases`, `advance_galactic_positions` and `advance_comet_orbits` (run by `planetgen.cli.orbits`, planned daily by OPS.16) rewrite these columns of essentially every body. Verified in `store.py`:

| Table | Rewritten columns |
|---|---|
| `planets`, `moons` | `orbital_phase_deg`, `position_x/y/z_km`, `velocity_x/y/z_kms` |
| `stars` | `galactic_orbital_phase_deg`, `reflex_offset_x/y/z_km` |
| `planets` | `reflex_offset_x/y/z_km` (from their moons) |
| `star_systems` | `binary_mutual_orbital_phase_deg`, `binary_mutual_position_*`, `binary_primary_position_*`, `binary_secondary_position_*`, `binary_planetary_wobble_*`, `binary_galactic_orbital_phase_deg`; from the galactic move also `position_x/y/z_mpc`, `quadrant`, `velocity_*` and `sector_id` |
| `black_holes`, `neutron_stars`, `nebulae`, `supernova_remnants`, `rogue_planets`, `interstellar_comets`, `asteroid_fields` | `galactic_orbital_phase_deg`; from the galactic move also `center_*_pc`, `galactic_radius_pc` and `sector_id` |
| `facilities` (stand-alone) | `center_x/y/z_pc`, `sector_id`, `orbit_phase_deg` |
| `comets` | `mean_anomaly_deg`, `parabolic_mean_anomaly`, `distance_km`, `position_*`, `orbital_speed_kms`, `velocity_*` |

The orbit update also refiles an object that drifts into another generated sector (its `sector_id`, sector-relative position and octant change), so which sector a system belongs to changes over time. The existing code already treats an orbit tick as "not a change" (`modified_at = modified_at`).

Recommended: the parity export covers what generation and admin edits wrote and omits every column above, `sector_id` of a placed system included, keying each system by its uid under the sector it was generated in. DB.8 checks the omitted columns by range (phase in [0, 360), finite, position consistent with distance, inclination and phase). Positions, velocities and reflex offsets are pure functions of the phases, so the state that cannot be recomputed is the phases themselves (and each comet's anomaly), because the guarded updates (`min_update_interval_years`) make them depend on the path.

This leaves a gap that is open for Boss: after a repair the rebuilt rows carry their as-generated phases and sectors. Options are (a) accept it and let the next orbit update carry on from there, (b) replay the orbit update from the stored epoch, or (c) keep a small volatile snapshot (id, phases, sector) rewritten by the daily run next to the parity file. Option (a) is simplest and is the default; (c) is the exact one and costs a few tens of bytes per body per day.

### 5.3 A separate storage checksum, not GEN.58's fingerprint

The TODO text for DB.9 says "the canonical hash of GEN.58's fingerprint", and [generation-determinism.md](generation-determinism.md) section 4.3 says the leaf digest "is DB.9's content checksum". For damage detection that is wrong in three ways:

1. The fingerprint rounds floats to 9 significant digits. A flipped low mantissa bit of a DOUBLE changes nothing after rounding, yet is real corruption.
2. It skips ids and foreign keys, so damage to them is invisible.
3. It describes the as-generated sector. A sector with an admin edit no longer matches its as-generated hash.

The storage checksum is SHA-256 over a lossless dump of the stored rows (ids and uids included, the columns of section 5.2 excluded), computed from the rows as read back after the write. Reading back also catches values the column silently altered (VARCHAR truncation, DOUBLE round trip) at the first save, not at the first check. It costs one extra read of the sector per save. Keep both hashes: GEN.58 for reproducibility, this one for integrity. The export format must be re-importable, so repair can insert a rebuilt sector's rows with their original ids.

|---|---|---|---|---|---|
| 8 | 50 KB | 0.44 / 0.47 | 1.2 | 1.0 | 0.28 |
| 16 | 50 KB | 0.81 / 0.83 | 3.5 | 1.0 | 0.25 |
| 16 | 200 KB | 5.4 / 4.2 | 16.8 | 9.5 | 0.96 |
| 32 | 200 KB | 14.7 / 14.1 | 50.5 | 20.7 | 1.0 |

Everything is under 60 ms per group. A sector save already costs generation (about 1.3 s per 40-system sector) plus several database round trips, so encode cost is irrelevant. The scaling cost is IO: a rebuild reads G-1 other sectors.

Overhead with variable-length members (160,000 sectors, lognormal sizes with median 30 KB clipped to 2 to 200 KB, mean 43 KB; one parity block padded to the longest member) [C]:

| G | Ideal m/G | Grouped by address | Grouped by size class | m=2 by address |
|---|---|---|---|---|
| 8 | 12.5% | 33.0% | 13.5% | 66.0% |
| 16 | 6.25% | 20.6% | 6.84% | 41.2% |
| 32 | 3.12% | 12.1% | 3.44% | 24.3% |

### 5.6 Layout: groups, records, updates, stale detection

**Group.** G members plus m parity blocks, formed at save time from sectors of the same size class: class = ceil(log(size / 2000) / log 1.25), about 20 classes for 2 to 200 KB. A new sector joins an open group of its class that has no member within W = 256 sector ids, because a damaged extent of a table file hits neighbouring rows, which are neighbouring sectors. Simulated at N = 10^6 this costs nothing (6.84 percent, same as W = 1); at N = 20,000 it leaves 11.6 percent of sectors in unfilled groups, so W should shrink for small galaxies (about N / 100) [C]. An unfilled group is still protected (a one-member group is a mirror). W = 256 is a guess at corruption extent, not a measurement [R].

**Variable lengths.** Every member is virtually zero-padded to the group's longest; the parity length P is that maximum, and each record stores every member's true length so a rebuilt block is cut back.

**Record.** One per group, self-describing: magic, format version, group id, `seq` (incremented on every update), k, m, member count, per member (sector address or uid, length, 16-byte SHA-256 checksum), P, the m x P parity bytes, and a CRC32C of the record (it only has to detect torn writes).

**File.** An append-only log of records, an in-memory index of group id to (offset, seq) rebuilt by a header scan (optional checkpoint file), last valid record per group wins. A torn tail fails its CRC and the previous record is intact. Compaction (rewrite live records, rename) runs in the daily maintenance run. A SQLite file was rejected (one damaged b-tree page can hide many groups); fixed slots waste space for small groups. The path is in `config.json`, as the TODO says.

**Update on every save, without rewriting the file.** For a changed member i, read its old export (the before-image, from the database inside the saving transaction, verified against its old checksum first), then for each parity row j: `P_j' = P_j XOR c_ji x (old_i XOR new_i)`, zero-padding as needed and extending P if the new member is longer. A new member in an open group has old = zeros, so no other member is read. Cost: 0.01 to 1.8 ms plus appending one record of m x P bytes (about 50 to 200 KB). If the before-image fails its checksum, do not delta-update (that would bake the damage into parity); mark the group for a full recompute after repair.

**Stale parity after a partial write.** A save writes the rows and the new checksum and commits, then updates the parity record. A crash between the two leaves the record behind the database. Each record stores the checksum each member had when it was built, and the database stores the sector's current checksum, so the decision needs no extra state:

| Database rows vs DB checksum | Record's member checksum vs DB checksum | Meaning | Action |
|---|---|---|---|
| all match | all match | healthy | nothing |
| all match | member i differs | record is stale, not damage | recompute the record from the database |
| member i fails | record equals DB checksum | real damage, parity current | rebuild i from parity |
| member i fails | record differs from DB checksum | damage and a stale record at once | parity cannot be trusted for i; use seed regeneration (DB.9's fallback) or a backup |
| record CRC fails | n/a | parity damaged | recompute from the database if every member verifies |

A `dirty` flag on the sector row, set in the same transaction by every writer of exported columns and cleared after the parity update, makes row 2 explicit and lets DB.8 report "N sectors unprotected" instead of calling them damaged. It also covers writers that bypass the save path (`store.py` has direct UPDATEs for names, positions and velocity; `api/edits.py`, `db/edits.py`): each must set the flag or the checker reports false damage. Listing every writer of exported columns is a DB.9 task not yet done.

### 5.7 Recommended numbers

- Codec: GF(256), Cauchy generator scaled so row 0 is all ones; k + m <= 256.
- Default G = 32, m = 2: 6.9 percent overhead, two bad sectors per group tolerated. With independent per-sector damage chance p, a group fails with about C(32,3) p^3 = 4,960 p^3, against C(16,2) p^2 = 120 p^2 for G = 16, m = 1 (at p = 10^-4: 5 x 10^-9 against 1.2 x 10^-6) [C arithmetic; the spacing rule handles clustering]. A rebuild reads 31 other sectors instead of 15. G = 16, m = 1 (6.85 percent) is the simple alternative. k and m are settings in `config.json`.
- The parity file is about 7 percent of export bytes: about 3 GB at 10^6 sectors of 43 KB mean.

### 5.9 The codec

The codec below was tested again while this note was written: for (k, m) = (16,1), (16,2), (32,2), (8,3), random erasure patterns of m blocks decode exactly, and `update` gives the same parity as a fresh `encode` [C]. It is CC0 with the project and is meant to go in as `planetgen/util/rscodec.py` with its own tests.

```python
EXP = [0] * 512; LOG = [0] * 256
x = 1
for i in range(255):
    EXP[i] = x; LOG[x] = i
    x <<= 1
    if x & 0x100: x ^= 0x11D                     # GF(256), x^8+x^4+x^3+x^2+1
for i in range(255, 512): EXP[i] = EXP[i - 255]
def gmul(a, b): return 0 if a == 0 or b == 0 else EXP[LOG[a] + LOG[b]]
def ginv(a): return EXP[255 - LOG[a]]
_T = {}
def table(c):
    if c not in _T: _T[c] = bytes(gmul(c, v) for v in range(256))
    return _T[c]
def cauchy(m, k):                                 # m x k, row 0 scaled to all ones (= XOR parity)
    C = [[ginv((k + j) ^ i) for i in range(k)] for j in range(m)]
    for i in range(k):
        s = ginv(C[0][i])
        for j in range(m): C[j][i] = gmul(C[j][i], s)
    return C
def matinv(M):                                    # Gauss-Jordan over GF(256)
    n = len(M); A = [r[:] + [int(i == j) for j in range(n)] for i, r in enumerate(M)]
    for c in range(n):
        p = next(r for r in range(c, n) if A[r][c]); A[c], A[p] = A[p], A[c]
        iv = ginv(A[c][c]); A[c] = [gmul(iv, v) for v in A[c]]
        for r in range(n):
            if r != c and A[r][c]:
                f = A[r][c]; A[r] = [A[r][i] ^ gmul(f, A[c][i]) for i in range(2 * n)]
    return [r[n:] for r in A]
def _combine(coefs, blocks, L):                   # sum of coef * block, whole blocks at a time
    acc = 0
    for c, b in zip(coefs, blocks):
        if c: acc ^= int.from_bytes(b if c == 1 else b.translate(table(c)), 'little')
    return acc.to_bytes(L, 'little')
class RS:
    def __init__(self, k, m): self.k, self.m, self.C = k, m, cauchy(m, k)
    def encode(self, blocks):                     # k equal-length blocks -> m parity blocks
        return [_combine(self.C[j], blocks, len(blocks[0])) for j in range(self.m)]
    def row(self, i): return [int(c == i) for c in range(self.k)] if i < self.k else self.C[i - self.k]
    def decode(self, have):                       # {index: bytes} with >= k entries -> k data blocks
        idx = sorted(have)[:self.k]; inv = matinv([self.row(i) for i in idx]); L = len(have[idx[0]])
        return [_combine(inv[r], [have[i] for i in idx], L) for r in range(self.k)]
    def update(self, parity, i, old, new):        # member i changed old -> new (equal length): new parity
        L = len(old); d = (int.from_bytes(old, 'little') ^ int.from_bytes(new, 'little')).to_bytes(L, 'little')
        return [(int.from_bytes(parity[j], 'little') ^
                 int.from_bytes(d if self.C[j][i] == 1 else d.translate(table(self.C[j][i])), 'little')
                 ).to_bytes(L, 'little') for j in range(self.m)]
```

The codec needs equal-length blocks; callers zero-pad to P first. Parity row j of a group maps to index k + j in `decode`.

## 6. The check (DB.8)

`planetgen check-db` and the Admin dashboard button (run as a job) report one pass or fail line per check and exit non-zero on damage. The exit code should tell "damaged" from "could not check". `--sector` and `--region` limit the scope; a quick and a `--deep` mode exist because full-table work is slow.

### 6.1 Checks and queries

1. **Revision** (read-only, tested inside `START TRANSACTION READ ONLY` [C]). `MigrationContext.configure(conn).get_current_heads()` against `ScriptDirectory.from_config(cfg).get_heads()`. Then three-way agreement of `alembic_version`, `max(schema_migrations.version)` and `store.SCHEMA_VERSION` (equal to `alembic_runner.head_version()`). A mismatch means an interrupted migration (section 3); `detect_schema_version` (DB.4's shape markers, `_VERSION_MARKERS`) says which version the tables show. Add `compare_metadata(mc, models.metadata)` with `compare_type=True`: it reflects through `information_schema` and reported missing columns, missing indexes, extra tables and a type difference in a test, in 0.04 s for a three-table schema [C]. The repo's `models.py` uses `mysql.DOUBLE`, which avoids the `Float(53)` against `DOUBLE` false positive seen with generic types.
2. **Table health.** `CHECK TABLE t QUICK` per table (or `FOR UPGRADE` after a server upgrade). Report the message rows and warn that a failing run flags indexes corrupt.
3. **Foreign-key orphans.** Generated from `information_schema.KEY_COLUMN_USAGE` where `REFERENCED_TABLE_NAME IS NOT NULL`, one `SELECT COUNT(*) FROM child c LEFT JOIN parent p ON c.fk = p.pk WHERE c.fk IS NOT NULL AND p.pk IS NULL` per constraint (composite keys join on every column). Tested on a child table with one orphan inserted under `foreign_key_checks=0`: returned 1 [C]. Each is an index-only anti-join. Then hand-written checks for what foreign keys do not cover: `nearest_systems`, `sector_paths` (polymorphic `object_table`/`object_id`), `first_object_table`/`first_object_id` on the phenomenon holders, and `sector_stats` rows against `sectors`.
4. **Ids against `id_blocks`.** `SELECT MAX(id)` per table (an index dive) against `id_blocks.next_id`; blocks must not overlap.
5. **Names.** Dropped by GEN.71 per the TODO plan.
6. **Values.** DOUBLE columns cannot hold NaN or infinity through SQL (inserts of `'nan'`, `'inf'` and `1e999` fail [C]), so "no value is NaN or infinite" can only be a Python-side check before save. The stored-value check is a plausibility range per column (`WHERE radius_km <= 0 OR radius_km > bound`), plus `validation.check_star_system` per sector when scoped, and the range checks on orbit-updated columns of section 5.2.
7. **Counts.** `sector_stats.actual_systems` against `COUNT(*) FROM star_systems GROUP BY sector_id` for the scope.
8. **Per-sector checksum** (once DB.9 exists). Recompute the export and compare, skipping `dirty` sectors.

### 6.2 Cost and what `CHECK TABLE` does

Measured on MariaDB 10.11, a 5.0 million row copy of `phenomenon_scatter` (487 MB data, 172 MB index), 1 GB buffer pool so everything was cached [C]:

| Statement | Time |
|---|---|
| `COUNT(*)` | 2.6 s |
| `CHECK TABLE` default, QUICK, MEDIUM | 6 to 7 s each (no difference on InnoDB here) |
| `CHECK TABLE EXTENDED` | 29 s |
| `CHECKSUM TABLE` | 9.2 s (QUICK: 0.1 s but NULL; EXTENDED: 12 s) |
| `BIT_XOR(CRC32(CONCAT_WS(...)))` over 9 columns | 16 s |

Scaled linearly to the 1.17 x 10^9 rows (about 161 GB) GEN.100 would write before the mass cut of DB.19 (the earlier 1.6 x 10^8 was an unverified estimate; after the cut at 20 solar masses the table is about 2.7 x 10^5 rows, so these times apply to the bright-star scatter, not to it) these become roughly 83 s, 3.2 min, 16 min, 4.9 min and 8.5 min in memory, and many times longer on a cold cache [R]. Hence the quick and deep modes, scoping and a progress bar.

- `CHECK TABLE` [S: MySQL 8.4 `sql_admin.cc`, `ha_innobase::check`] takes `MDL_SHARED_READ` (it does not block DML but blocks DDL), scans each index with non-locking reads in REPEATABLE READ, validates each B-tree unless QUICK, compares each secondary index's entry count with the clustered index, and calls `dict_set_corrupted` on a failing index. It is therefore not strictly read-only on an already damaged table: later queries on the flagged index fail until it is rebuilt. MySQL 8.4 needs only `SELECT_ACL` [S]; on MariaDB 10.11 a SELECT-only account ran `CHECK TABLE` and `CHECKSUM TABLE`, also under `SET SESSION TRANSACTION READ ONLY` [C] (MariaDB's documented privilege may be SELECT plus INSERT [R]).
- `CHECKSUM TABLE` depends on column types and row format, is not comparable across servers or after an ALTER, is NULL for QUICK on InnoDB and for a corrupted table, does not see secondary-index damage, and is not a snapshot under concurrent writes [R]. Use per-sector application checksums and keep it for `--deep`.
- `mysqlcheck`/`mariadb-check` just send `CHECK TABLE` per table [R] and cannot do the application checks; the Python checker sends the SQL itself to control scope, progress and the account.

### 6.3 Avoiding long locks; read-only guarantees

- `CHECK TABLE` holds `MDL_SHARED_READ` for its whole run, so a DDL queued behind it waits, and everything queued behind that DDL waits too. Run the checker with a short `lock_wait_timeout` and never over a migration.
- Bound the work per statement: scope by sector range (the indexed `ring_index, layer_index, ring_slot_index` on `sectors`) and chunk anti-joins by id range, so each statement takes seconds, not minutes.
- A passive run uses a dedicated account with SELECT only, `SET SESSION TRANSACTION READ ONLY`, and the default snapshot for the SELECTs. The one remaining side effect is `CHECK TABLE` flagging an index that was already bad; `--no-check-table` skips it.

### 6.4 Built (DB.8)

`planetgen check-db` (`planetgen/db/check.py`) and the Generate page's "Check the database" section, which runs it as a job. It writes nothing, ends with one pass, FAIL or warn line per check, and exits 0 (clean, warnings allowed), 1 (damage) or 2 (a check could not run and none found damage). As built:

- `--ring` and `--sector` scope only the value, count and version-key checks; revision, table health, orphans and ids always look at the whole database.
- An empty `alembic_version` is not damage: a database built whole from `schema.sql` is never stamped, only an upgrade stamps it. A different or doubled revision is.
- The value rules (`VALUE_RULES`) are deliberately loose, only numbers no generator can write; a generated 8-sector galaxy passes with none flagged.
- `validation.check_star_system` is not run: it takes a loaded `StarSystem`, and loading every system is far costlier than the SQL rules. It joined as `--deep` (DB.21): a `systems` check loads every star system in scope and runs it, with one failure line per bad system. `--deep` first prints a time estimate (the speed recorded under stats kind `db-check`, else a stated rough guess of 0.04 s a system), asks for a yes on a terminal and needs `--yes` off one; `--estimate-only` prints just the estimate. The Generate page's Check the database section has a Deep check box that shows the same estimate and asks to confirm.
- A stale `sector_stats.actual_systems` is a warning, as an orbit refile moves a system without updating the stats.

## 7. Long migrations and progress (DB.15, DB.7, NAV.10)

### 7.1 Helpers for revisions

Revision 0063 hand-rolls its `_exists` checks and per-row loop. A small module, `planetgen/db/migrations/helpers.py`, should carry the pattern: `add_index_online(table, name, columns)`, `add_column_instant(...)`, `batched_update(sql, table, key, batch, label)` with the progress callback, `exists_*` checks, and a `lock_wait_timeout` context. Alembic's `op.add_column` and `op.create_index` cannot pass an `ALGORITHM`, so the helpers use `op.execute("ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE")`. This is the Alembic part of DB.7 (four columns on `sectors`, a small table: `ADD COLUMN ... ALGORITHM=INSTANT`) and of NAV.10 (position indexes on `star_systems` and others: `INPLACE, LOCK=NONE`). Every revision stays idempotent (section 3).

Batched backfill, tested with Alembic 1.16.5, SQLAlchemy 2.0.54 and PyMySQL on MariaDB 10.11 [C]: keyset paging on the primary key, `WHERE ... IS NULL` so a re-run resumes, a commit per batch (no giant undo log or purge lag), and a progress callback read from `context.config.attributes`.

```python
from alembic import op, context
import sqlalchemy as sa
BATCH = 20000
def upgrade():
    conn = op.get_bind()
    progress = context.config.attributes.get("on_progress")   # (label, done, total)
    total = conn.execute(sa.text("SELECT COUNT(*) FROM big WHERE b IS NULL")).scalar()
    done = last = 0
    while True:
        ids = conn.execute(sa.text("SELECT id FROM big WHERE id > :l AND b IS NULL ORDER BY id LIMIT :n"),
                           {"l": last, "n": BATCH}).scalars().all()
        if not ids: break
        conn.execute(sa.text("UPDATE big SET b = a * 2 WHERE id BETWEEN :lo AND :hi AND b IS NULL"),
                     {"lo": ids[0], "hi": ids[-1]})
        conn.commit()
        last = ids[-1]; done += len(ids)
        if progress: progress("big.b", done, total)
```

It ran 200,000 rows in 10 batches with ten progress calls and no NULLs left. Wiring: `alembic_runner._config()` gets `cfg.attributes["on_progress"] = on_progress`, and `upgrade()` and `migrate_database` take the callback. `StageProgress.detail(label, done, total)` already has the signature; `cli/migrate.py` must move from its own `Progress` to `StageProgress` for the callback to draw a bar, which also gives it the progress file and `_DecayingRemainingColumn`. A real batch trace (one new column over 5.0 million rows, 50,000-row batches, primary-key ranges): 105 batches, 156.7 s (about 32,000 rows/s), mean 1.49 s per batch, no trend [C]; scaled to 1.6 x 10^8 rows that is about 83 minutes if cached.

### 7.2 Progress reporting

- **Two bars.** Bar 1 is the revision count (as now), bar 2 the rows of the current step. Single statements (index builds) have no row progress: MariaDB 10.11 shows `PROGRESS 0.000 / STAGE 0/0` in `information_schema.PROCESSLIST` for an inplace index build [C]; MySQL 8.4 reports per-stage work through Performance Schema stage events [S: `ut0stage.h`], but only with those instruments enabled and only on MySQL [R]. The portable choice is a spinner with elapsed time and an "about N min" estimate from the row count and a rate measured on an earlier build or recorded under PERF.32, labelled as an estimate.
- **Non-terminal output is silent today.** `run_common._generation_progress`'s docstring says rich falls back to periodic line-by-line output when stdout is not a terminal. Rich 13.9.4 and 15.0.0 print exactly one final line [C], so a migration run by the maintenance timer, `update.sh | tee log` or ssh without `-t` shows nothing until it ends. DB.15 needs a plain reporter for `not console.is_terminal`: at most one line every 30 s and at each 10 percent, for example `migrate 0066 big.b 1,200,000/5,000,000 24% elapsed 0:08:10 left about 0:26:00`, with the same numbers to `PLANETGEN_PROGRESS_FILE` when set (which also gives the web UI a bar if a migration ever runs as a job). The docstring needs correcting.
- **ETA smoothing.** Keep the existing `DecayingRate` (time constant 60 s, PERF.7). Six traces (five synthetic, the real one above) were scored by the median and worst error of "time left" at 10 to 90 percent progress for the overall average, EWMAs of 0.1 and 0.3, the last 10 batches and time-EWMAs of 60 s and 300 s [C]. On steady work every estimator is within a few points. When the speed changes phase all are wrong alike (53 to 60 percent off on a "4x slower after 60 percent" trace), and 300 s is the worst choice (median 20.4 percent against 2.9 for 60 s when the cache warms). The 60 s estimator is within a few points of the best on every trace, so no second estimator is built. On the real trace the worst case (about 50 percent) is at 10 percent progress, where the first ten batches ran slower (2 s against 1.4 s); from 25 percent on the error was 1 to 21 percent.
- **Presentation rules.** No estimate before 3 batches or 10 s; round to the minute above 2 minutes; never show a time that jumps up by more than the interval since the last update. PERF.32's "recorded rate averaged with the live rate" fits as the prior for the first minutes of an index build.
- **What the update script shows.** `run_cli migrate` runs on the console without capture, so rich draws live bars in any real terminal. `migrate --status` could also print a row estimate for the tables each pending revision touches, so the "delete data instead?" prompt in `migrate_or_reset_db` can say "this update will run about 40 minutes".

### 7.3 Slow DDL

Measured on MariaDB 10.11.14, 5.0 million rows, 1 GB buffer pool (everything cached), with a concurrent writer doing single-row updates every 5 ms [C]:

| Statement | Time | Writer during it |
|---|---|---|
| `ADD COLUMN a INT NULL` (default algorithm) | 0.41 s | no errors |
| `ADD COLUMN ... INT NOT NULL DEFAULT 0, ALGORITHM=INSTANT` | 0.13 s | no errors |
| `ADD COLUMN ... AFTER kind, ALGORITHM=INSTANT` | 0.08 s | no errors |
| `DROP COLUMN ..., ALGORITHM=INSTANT` | 0.09 s | no errors |
| `MODIFY kind VARCHAR(24)` to `VARCHAR(40), ALGORITHM=INSTANT` | 0.07 s | no errors |
| `MODIFY ring_index INT` to `BIGINT, ALGORITHM=INPLACE, LOCK=NONE` | refused at once: "Cannot change column type" | n/a |
| `ADD INDEX (kind, ring_index), ALGORITHM=INPLACE, LOCK=NONE` | 59.2 s | 3,662 ops, p50 9.4 ms, max 136 ms, no errors |
| `ADD INDEX (seed)` (random BIGINT), default | 43.3 s | 2,832 ops, p50 8.3 ms, max 604 ms |
| two indexes as two statements / in one `ALTER` | 20.0 + 28.0 s / 46.5 s | no saving from combining |
| `ADD INDEX (built_at), ALGORITHM=COPY` | 177.9 s | blocked: 6 ops in 178 s |
| `ADD CONSTRAINT CHECK (ring_index >= 0)` | 141.8 s | blocked: 11 ops in 142 s |

Scaled by 32 to 1.6 x 10^8 rows (cached; much worse when the table does not fit in memory), an index build is 11 to 31 minutes and a COPY-style alter 1.5 hours or more with writes blocked.

- Adding a column with a default, dropping a column and widening a VARCHAR within its length byte are instant. Adding an index is online but long. Changing a column type, adding a CHECK constraint and `ALGORITHM=COPY` block writes for the whole run. Always write `ALGORITHM=...` (and `LOCK=NONE`) explicitly so the server refuses instead of silently copying.
- The repo's own history agrees: the old v26-to-v27 step used `ALGORITHM=INSTANT` and online indexes, while v45-to-v46 used `LOCK=SHARED` and blocked writes for minutes ([database-schema.md](../database-schema.md)).
- MySQL 8.4 [R]: `ADD COLUMN` is `INSTANT` by default (any position since 8.0.29; at most 64 row versions, then a rebuild: `MAX_ROW_VERSION = 64` [S, `dict0mem.h`]); `DROP COLUMN` instant; `ADD INDEX` in place with concurrent DML; changing a column type, adding a CHECK or a foreign key (unless `foreign_key_checks=0`) or changing the primary key rebuilds or copies. `innodb_ddl_threads` (8.0.27+) parallelises index builds.
- MariaDB 11.4 [S source / R]: `innodb_instant_alter_column_allowed` is `never`, `add_last` or `add_drop_reorder`, default `add_drop_reorder` (`ha_innodb.cc`), so add, drop and reorder columns are instant by default, matching the 10.11 run. No progress reporting for InnoDB ALTER in 10.11 [C].
- On the 10^8-row tables (`star_systems`, `stars`, `planets`, `moons`, `phenomenon_scatter`, `nearest_systems`): `op.create_index` is online but long with no progress; `op.alter_column` emits `MODIFY` and often copies; `op.create_check_constraint` and `op.create_foreign_key` copy or rebuild; `op.batch_alter_table` is a table copy built for SQLite (never use it here); `op.add_column` with a literal `server_default` and `op.drop_column` are instant.
- **Metadata-lock pile-up** [C]. With one open transaction that had read the table, `ALTER TABLE ... ADD INDEX` with `lock_wait_timeout=4` failed after 4.0 s with error 1205, and a plain `SELECT` issued 1 s later was blocked behind the waiting ALTER for 3.1 s. The online ALTER takes an exclusive MDL briefly at start and end, so any long transaction stalls the whole table. Migrations should `SET SESSION lock_wait_timeout = 30` (or so), retry the statement a few times, and refuse to start while `information_schema.INNODB_TRX` shows transactions older than a minute on that table [R for the query].
- **A risk in the update flow.** `SCHEMA_LOCK_WAIT_S` is 600 s, and every new connection that ensures the schema waits on the migration's named lock for that long. An index build on `phenomenon_scatter` (about 161 GB at 1.17 x 10^9 rows before DB.19's mass cut, 138 bytes a row; the earlier 21 GB at 1.6 x 10^8 rows was an unverified estimate, and after the cut the table is about 37 MB) will exceed it, so web and worker processes that start during the update get lock timeouts. Either raise the wait, or stop services for update runs that have a heavy revision.
- **gh-ost and pt-online-schema-change are not needed.** gh-ost needs row-based binary logs and does not support foreign keys or triggers (this schema has 71 foreign keys; MariaDB is not mentioned in its requirements) [S]. pt-osc can handle foreign keys with caveats [S: its `--alter-foreign-keys-method` text] but copies the whole table and doubles disk use for a table of that size. Native `INPLACE`/`INSTANT` covers every planned change.
- NAV.10 caution: three single-column indexes on x, y and z let the optimizer use one of them (or an index merge), not a 3-D box. A box query wants a cell key (a Morton or sector-cell column) or the existing `(ring_index, layer_index, ring_slot_index)` address. Decide that before paying for 10^8-row index builds.

## 8. Backup tooling facts

- The repo has no database dump step, and OPS.18 rotates the JSON settings file, not dumps. Parity and seed regeneration are the only repair paths for sector data; nothing covers the non-sector tables (control database, admin logins, population tables).
- `mysqldump` (MySQL 8.4) has `--source-data` (and `--master-data` as a deprecated alias); `mariadb-dump` (MariaDB 11.4) has `--master-data`, `--gtid`, `--as-of` and `--system` but no `--source-data` [S: `client/mysqldump.cc`]. One script cannot pass the same replication options to both: use `--single-transaction` and leave them out. MySQL's `mysqldump` against MariaDB needs `--column-statistics=0` [R].
- Point in time needs the binary log (on by default in MySQL 8.4, off in MariaDB 11.4 [R]); parity and seed regeneration do not.
