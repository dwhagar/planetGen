# Cache warm-up and invalidation (PERF.104)

Informs: PERF.104, PERF.2 (the page cache), PERF.64 (stored counts), MAP.134 (the Galaxy Map warm-up), PERF.86 (Redis rules), OPS.51 (maintenance)
Status: built (Core 2, 2026-10-16). Nothing here changes a table; no migration.

## The problem

After `update.sh` the first visit to a page builds it from the database, and today the warm-up covers one thing, the Galaxy Map's opening tiles. The page cache (`web/lib/pagecache.py`) is a dict inside each WSGI process, so no outside script can fill it, and it drops a database's whole cache whenever the galaxy's content stamp moves. A warm-up therefore needs a store every process shares, and "changing one sector rebuilds only the caches that read it" needs the cache to know what each answer read.

## Design

**One shared store, Redis (PERF.86 rules).** The page cache keeps its in-process copy for speed and adds Redis behind it. Redis is the only place a warm-up can write for every worker to read. It runs with AOF `everysec` and `noeviction`, so every key carries a TTL and every value is capped (one body at most a quarter of `page_cache.max_mb`). A cold Redis is an empty cache, never wrong: a read that cannot reach Redis is a miss and the answer is not stored.

**Every entry names what it read (tags), and every change bumps tags.** Redis holds one hash per database, `planetgen:ver:<db>`, of tag name to counter, and a field `_id` (an incarnation token made when the hash is first written, so a flushed Redis cannot revive an old in-process copy). An entry stores the counters of its tags at the time it was fetched; it is served only when every counter still matches. A stale copy is therefore never served as current, in this process or another.

| Tag | Bumped when |
|---|---|
| `epoch` | the plan, the galaxy shape, the naming key, a release, a bulk delete, or a write the table below cannot place. Every entry carries it. |
| `sector:<id>` | that sector is edited, regenerated, has systems added or removed, or a system in it is edited (ids as printed, API.23) |
| `system:<id>` | that system is edited or deleted |
| `phenomenon:<type>:<id>` | that phenomenon is edited or deleted |
| `sector-set`, `system-set`, `phenomena-set` | an object of that kind is added or deleted (who is next to whom, counts) |
| `sector-data`, `system-data`, `phenomena-data` | any object of that kind is added, deleted or edited (what a list shows) |
| `system-any` | a star, planet, moon or facility is edited and the route does not name its system |
| `population` | the population pass ran, or a species, polity or territory was edited |
| `positions` | the orbital update moved objects |

Every bump also adds one to `_n`, which `begin`/`put` compare so an answer fetched while data changed is not stored.

**What an answer reads** (`web/lib/pagetags.py`, the one place that says; the ids come from the answer's body):

| Answer | Tags |
|---|---|
| Sector page | `epoch`, `sector:<its id>`, `sector:<each neighbour's id>`, `sector-set`, `phenomena-data`, `population`, `positions` |
| System page, text, sections, scene | `epoch`, `system:<id>`, `sector:<its sector>`, `system-any`, `phenomena-data`, `population`, `positions` (the two set tags when the body names no sector) |
| Phenomenon page | `epoch`, `phenomenon:<type>:<id>`, `sector-data`, `phenomena-set` |
| Sector list | `epoch`, `sector-data`, `system-set`, `phenomena-set`, `population`, `positions` |
| System lists | `epoch`, `sector-data`, `system-data`, `system-any`, `population`, `positions` |
| Phenomena list | `epoch`, `sector-data`, `phenomena-data` |
| Polities, species | `epoch`, `population`, `system-data` |
| Anything not listed (search, near, nav, galaxy) | `epoch` plus every tag above except the per-object ones |

So renaming one sector bumps `sector:<id>` and `sector-data`: its page, its neighbours' pages and its systems' pages are rebuilt, and the lists; no other sector's page and no other system's. Renaming one system bumps `system:<id>`, `system-data` and `sector:<its sector>`: its page, its sector's page and its siblings' pages are rebuilt, no other sector.

**Who bumps.** (1) A write through the API (`web/__init__.py`) maps the route to a change kind (`pagetags.change_for_write`) and bumps its tags before the response goes out; for a system the sector is looked up before the write runs; a route it cannot place bumps `epoch`. (2) The command line records its change when it finishes (`cli/generate.py`: `plan` is `everything`, `population` is `population`, every other writing command `generated`; `cli/orbits.py`: `orbits`). (3) The backstop for everything else, as before: the content stamp (`GET /api/galaxy/changes`, checked every `page_cache.stamp_seconds`). The first process to see a new state claims it in Redis (`dataversion.claim_state`) and bumps `sector:<id>` for each sector named (`galaxy_changes` now lists them, placed or not) and `sector-data`, plus every set and data tag when something was added; a change it cannot place (`full`) bumps `epoch`. The state the last claim recorded is what the next check asks about, so a change made while no web process ran is found by the first check after. While a fill makes the galaxy `busy` (PERF.38) nothing is bumped from the second busy check on and entries age out, the one documented case where an answer can be up to `max_age_seconds` old. The age limit stays the last backstop.

**Counts.** `db/countcache.py` already keys its answers by the stamp and refreshes them in the background; the warm-up asks for each table page's counts once, which stores them.

## The warm-up

Superseded in part (Boss, 2026-10-18, 5:43 PM EDT, PERF.139): the flat family order below is to be replaced by budgeted warm-up phases in place of the level cap.

`planetgen warm` (PERF.127; it was `python -m planetgen.cli.warm_map`), run after `update.sh` as the web server's user. It covers these families, each its own command on the work queue (`warm-cluster-field`, `warm-object-index`, `warm-galaxy-map`, `warm-galaxy-nodes`, `warm-galaxy-deep-nodes`, `warm-lists`, `warm-sectors`, `warm-systems`, `warm-phenomena`, `warm-search`; `queue/commands.py`) that warms that family and nothing else and can run alone (`planetgen command-run`). `planetgen warm` builds the list of them and the wrapper runs them in order as a maintenance run (`runrecord.MAINTENANCE`: its own place in Redis, so it does not block a generation run and the visitors' banner never shows it):

| Family | What it warms |
|---|---|
| `cluster-field` | the galaxy's cluster field (PERF.225): the globular clusters, satellites and young open clusters as one field the density model reads. Building it takes 20 to 60 s on a galaxy of tens of thousands of open clusters, nearly all of it the mean system mass of each distinct age, so it is a stage of small units (`galaxy/field_job.py`): one unit per `PART_AGES` (1000) ages writes its part as a file in `<state folder>/galaxy-field/<signature>.parts/`; when the last is in, the stage's conclusion makes the field from the rows and the parts and writes `<signature>.field` by a rename, then removes the parts and all but the newest two fields. A run that stopped is carried on from the parts that are there. The signature names the rows (`store.component_field_key`) and a hash of the source that decides the numbers, so a changed row or formula is a new file; the file is read through an unpickler that allows only the field's own classes. The web daemon only reads the file (`store._component_field`); a visitor's request that finds no file for a galaxy of more than `INLINE_COMPONENTS` (1500) components is refused at once with the 503 of the cache guard (`admin/cachebuild.py`, cause `missing`), and a worker, the command line or the warm-up builds it in their own process; the `opening` phase |
| `object-index` | the object index (PERF.140): one `object_index` row per object of every kind the site lists, written only when the object changed since the kind's last run |
| `galaxy-map` | the opening nodes and stage (existing `warm_opening_view`), the galaxy shape, sector list, phenomena, superbubbles, shell specs, bright-star status |
| `galaxy-deep-nodes` | the zoom run (MAP.261): the nodes the map fetches on a zoom from the opening view in to the galaxy's centre, down to blocks of `tile_cache.warm_zoom_floor` shells (default 9), at most `MAX_WARM_NODES` (100,000), coarsest first, in chunks of `NODE_CHUNK` through `tilecache.fetch_nodes`; the `deep-nodes` phase |
| `galaxy-nodes` | the Galaxy Map's sector-block nodes (MAP.260): every block of level `warmup.NODE_WARM_FLOOR` (243) and above that holds a generated sector or pre-placed objects (`nodes.populated_node_keys`), biggest blocks first, in chunks of `NODE_CHUNK` (64) through `tilecache.fetch_nodes`; the `built-levels` phase, which stops at the cache budget |
| `lists` | the first page of the sector, system, uncharted-system, phenomena, polity and species lists, the lists page and the first page of each kind's list (UX.141), and each list's counts |
| `sectors` | every sector page (the sector detail), nearest the galaxy centre first, up to `page_cache.warm_max_objects` |
| `systems` | every system page, same order and cap |
| `phenomena` | every phenomenon page, same cap |
| `search` | the search page's empty and default answers and its index counts |

**Nodes (PERF.130, MAP.260, MAP.261).** The families cut into many units. Before MAP.262 the map was cut into cube tiles and `galaxy-tiles` built the octree's first levels and a zoom run of them (7,112 tiles in 12 minutes 17 seconds in one process on the scaled probe galaxy, 40 MB on disk, a second run 1.0 second and none built); the cube tiles are gone and the same two ideas run on the sector-block nodes. `galaxy-nodes` lists the populated blocks of `NODE_WARM_FLOOR` and above from the stored block rows and cuts them into chunks of `NODE_CHUNK`; a unit builds one chunk through `tilecache.fetch_nodes`, the call the map's own request makes, so what is stored is what a visitor is served and a node that is stored and current is not built again (a second run builds nothing). `galaxy-deep-nodes` is the zoom run: the union of `nodecut.node_cut` for the camera on the opening camera's line through the origin (the page's starting angles round the central black hole), from the opening distance in, one `ZOOM_STEP` (1.3) closer at a time, keeping nodes finer than `NODE_WARM_FLOOR` down to `warm_zoom_floor` shells; a floor that would build more than `MAX_WARM_NODES` is refused with its count. Nodes deeper than the run are built on first request, and the ones around a visit are built ahead (below).

*Settled-view time* (the server's time to hand a fresh visitor every node of one view, asked in request-sized chunks one after the other, for the camera on the zoom run's line at each distance, on that galaxy): without warming 5.1 / 9.0 / 18.6 / 53.5 / 12.5 / 8.4 / 3.0 / 1.2 s at 100,000 / 30,000 / 10,000 / 3,000 / 1,000 / 300 / 100 / 30 pc, 111 s over the eight views; after the warm-up 0.0 / 0.0 / 1.7 / 1.2 / 0.1 / 0.1 / 0.0 / 0.1 s, 3.2 s over the eight. What remains is nodes the run's one-step grid does not hold; PERF.132 builds those around a visit. (These figures are of the cube tiles, kept as the record of what warming buys.) The node cache is keyed by the tile stamp (PERF.133, below), which leaves the release number out, so a release that changes neither the format nor the generator epoch keeps every stored node and the `planetgen warm` that `update.sh` starts finds them stored ("0 built").

**Building around a visit (PERF.132, MAP.260).** `web/lib/tileprefetch.py`. When a `/galaxy/nodes` response has gone, the route hands the request's node keys to `tileprefetch.schedule`, which queues what the visitor is likely to ask for next and does not have: for each requested node (the request lists them nearest first) its children and then its parent and the parent's other children, for a visitor who zooms in, out or pans. The page's own idle prefetch (zoom 3, after 1.5 s of a still camera, at most 12 nodes, marked `X-Map-Prefetch`) fills the browser's cache and does not queue anything on the server. The jobs go to the bulk queue (never the interactive one, so an admin's work is not behind them) as chunks of 16 nodes that a worker builds into the same disk cache through `tilecache.fetch_nodes`; one worker is started if none serves the queue. Rules, each a `tile_cache` setting or a fixed constant: at most `prefetch_per_visit` (128) nodes per request, `prefetch_per_minute` (600) in all, nothing while `prefetch_max_queued` (8) jobs wait, nothing for ten minutes after `prune` deleted files (the cache is full), nothing during an update, nothing for a node stored or already claimed (a Redis key per node and generation, 15 minutes), so a visit to a built area queues nothing and a second visitor to the same area causes no build. It fails open: no Redis or no cache directory means no background build. It does not queue stages or windows: the map asks for them one block at a time.

**The phases (PERF.141, Boss 2026-10-18 5:43 PM EDT).** `warmup.PHASES` names five phases and the families in each, in the order they run: (1) `opening`: `cluster-field`, `object-index`, `galaxy-map` and `lists`, the cluster field, the object index, the opening views and the first page of each list; (2) `built-levels`: `galaxy-nodes`, the populated blocks of `NODE_WARM_FLOOR` and above; (3) `deep-nodes`: `galaxy-deep-nodes`, the zoom run in to the centre down to `warm_zoom_floor`; (4) `objects`: `sectors`, `systems`, `phenomena`; (5) `search`. Each family is still a command of its own; a phase is what the run reports (`warmup.PhaseTally`: built, already stored, left out by the budget or a cap, or `unchanged, nothing built`) and what `planetgen warm PHASE` runs. The node phases stop at `cache.max_mb` (below); the page phases write to Redis. **The automatic start (PERF.141 slice 2).** `queue/warmstart.py`. `dataversion.bump`, the one place every change that moves a data version tag passes through (a generation run, `planetgen orbits`, an edit through the API, a change the page cache found in the galaxy's content state), ends with `warmstart.request(database, tag)`. It adds the change to the Redis hash `planetgen:warm:wanted:<database>` and, unless the lock `planetgen:warm:auto:<database>` is held by a live process, takes it and starts `planetgen warm --on-change <database>` apart from the caller (as the owner of the tile cache directory when the caller is root, so Apache can read what it writes). A request made while a warm-up waits or runs only adds to the hash. The started process waits `cache.warm_settle_seconds` (default 60) so a burst of edits is one warm-up, takes the hash, runs the whole warm-up once (which rebuilds only what the changes touched, so a small change costs seconds), lets go of the lock and looks again: a change that arrived meanwhile starts another round, at most five in one start (`MAX_ROUNDS`; one more change after that starts a new one). Nothing starts while an update runs (`update.sh` starts its own warm-up at its end), with `cache.warm_on_change` off (`PLANETGEN_WARM_ON_CHANGE=0`; the test suite sets it so) or without Redis; a start that fails warns on stderr and never fails the change. A change on a database other than the one the site shows warms nothing. A failed run is in the activity log and ends the process; the next change starts it again. **The admin page's phase state (PERF.141 slice 3).** `queue/warmphases.py`. Every `planetgen warm` run writes the Redis hash `planetgen:warm:phases:<database>`: a field per phase and `_run` for the run. A phase is `waiting`, `running`, then `built`, `unchanged` (nothing built), `stopped` (the budget or a cap left something out), `nothing` (no family of it had anything to warm) or `failed`, with its report line, counts and times (`PhaseTally.result`). A phase the run did not ask for keeps what an earlier run wrote, so `planetgen warm lists` leaves the rest as they were; a failed run marks the running phase `failed` and puts the phases it never reached back to not run; a run whose process died reads as `interrupted`. `GET /api/admin/work/warm?database=NAME` (admin) returns it, with what the automatic start waits for, and the admin queue page (`/admin/queue`) shows it as the "Cache warm-up" panel: the last run (state, start, end, what asked for it), whether a start after a change waits or runs, and one row per phase. The object index is built (PERF.140) and the lists page and each kind's list are warmed in phase 1. Deeper list pages are not warmed: a page of the object lists starts after the last object of the one before (UX.141), so page 500 reads as little as page 1 and warming it buys nothing.

**The object index (PERF.140).** `db/objectindex.py` fills `object_index` (DB.79) from the live tables with one `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE` for each kind of object (`SOURCES`: the columns the lists sort and search by, taken from the object's table and its system). A row's `indexed_at` moves only when a column it holds changed. `build` writes every object of a kind and removes the rows of objects that are gone. `refresh` writes only the objects whose `modified_at` (a child's edit reaches its row through its system) is later than the kind's last run, which Redis keeps (`planetgen:objindex:<database>`, the time taken from the database's own clock); a kind with no record is built, and a kind whose rows are fewer or more than its objects is swept, then written whole if it still differs. The automatic start (`warmstart`) asks for a `build` after a `positions` or `epoch` change, since an orbital update leaves `modified_at` alone and moves which sector holds an object, and a refresh otherwise. The index is kept first in the budget: `tilecache.max_cache_bytes` is `cache.max_mb` less the size the index took when its last run ended (`objectindex.reserved_bytes`, never less than one byte, so a budget the index fills leaves the tile cache full, not off). `planetgen check-db object-index` compares the index with the tables, naming how many rows are missing, extra or different (a warning when nothing has built it yet), and the admin queue page shows each kind's rows, last run and the index size.

**A tile is built again only when what it holds changed (PERF.133, Boss 2026-10-18 6:05 PM EDT).** The stored tiles are keyed by `query.galaxy_tile_stamp`, a hash of the galaxy shape, the bright-star seed, the naming key, `query.TILE_FORMAT`, the generator epoch and the change counters; the release number is not in it (it stays in `galaxy_content_stamp`, which the pages and counts follow). So (1) nothing changed: a second warm-up, or the `planetgen warm` after a release, builds no tile and says `N built, M already stored`; (2) a sector edited, added or given a system: `GET /api/galaxy/changes` names its tile at every level, only those files are deleted, and the ones that were stored are queued at once for a rebuild on the bulk queue (`tilecache.take_rebuilds`, `tileprefetch.rebuild`, coarsest first, at most 2,048 a change, off with the prefetch, during an update and while the cache is full), so the next visit finds them built; (3) a deleted sector, a new shape, tile format or epoch, more than 1,000 changed sectors, or a backfill: a new generation, rebuilt by the next warm-up. A change to what a tile holds or how it is packed must raise `query.TILE_FORMAT`; `tests/test_tile_format.py` pins the bytes of one fixed tile and fails until the number and its digest are updated. The stored tiles are never dropped for age.

**The budget (PERF.139, PERF.133 part 2; Boss, 2026-10-18, 5:43 to 5:57 PM EDT).** One setting, `cache.max_mb` (default 1024, `0` turns the disk caches off, `PLANETGEN_CACHE_MAX_MB`), replaces `tile_cache.max_mb` with no shim; the tile cache is the first thing under it, and the object index (PERF.140) shares it and is kept before tiles, as the stored lists (PERF.141) will be. A tile built ahead (the warm-up, the background build, a rebuild after a change) is written with `AHEAD_MODE` (group-read bit); a tile a visit asked for is written 0600, and every visit to a stored file sets its modification time. `tilecache.prune` runs when a write may have taken the cache over the budget and, over it, deletes only the files a visit asked for, least recently visited first, down to 80% of the budget; the tiles built ahead are never deleted for size, so a cache of nothing else stays over the budget. Warming then stops: each unit of `planetgen warm`'s `galaxy-tiles` checks `tilecache.cache_is_full` first, builds nothing and reports the tiles it left out (`N tiles left out, the tile cache is full`), and the background build waits while `prune` has just deleted files (`.full`).

Each family ends with one line, `<family>: <n> warmed (<m> already cached, <k> left out by the cap) in <s> s`, printed by the command, written to the activity log (the admin's log) and returned as the unit's result. `planetgen warm` exits non-zero if any command fails, and says which (the run stops at the failing one, as every wrapper list does); it has no silent fallback (a Redis that does not answer, another warm-up running, or an update running are errors, printed). A cap that leaves objects out says so; those fill on first visit. `planetgen warm lists search` runs just those; there is no `--no-rq` and no `--only`, since the order and the choice live in the wrapper's list and Redis is required. A family warms by visiting the pages through the site's own Flask app (`warmup.build_app`: open during the sector-switch maintenance, not rate limited), so what it caches is exactly what the page asks for; a page that does not answer 200 fails the family. The activity log has `GEN warm.family` or `GEN warm.failed`. `planetgen warm` waits for a running update to finish before it queues (the queue takes no job during one, OPS.53), `update.sh` runs it in two stages in the foreground, each with a progress bar (`--progress`): stage 1, `planetgen warm opening`, just before the Apache reload (what the reload and the health check need, so the reload cannot interrupt it); then it reloads, waits 10 s (`HEALTH_SETTLE_SECONDS`) and checks `/api/health` at `api_base_url` only; then it releases the update guard (the site opens) and stage 2, the full warm-up, runs while update.sh stays up showing its bar until it ends.

It runs inside the maintenance flag the update set (OPS.51). A list of every family ends with the command `end-map-rebuild-maintenance`, which ends the sector-switch maintenance after every family has succeeded: it is the list, not a family, that knows the maps are then rebuilt. It registers with the update guard (OPS.53) so a later update lists and cancels it.

## Done when

After `update.sh`, the first visit to the Galaxy Map, a sector, a system, a phenomena or system list and a search answers from the cache. Changing one sector rebuilds only the caches that read it. A test per kind of change proves a stale copy is never served as current.

## Not in this slice

Warming past the cap (a galaxy of millions of sectors warms its nearest `warm_max_objects`, the rest fill on first visit); resolving a star, planet or moon edit to its system (those routes bump every system page, `system-any`, instead); a per-page progress bar on the runs page (the node shows its state and the one result line).

## Without Redis

The shared tier needs Redis (PERF.86 makes it required for generation anyway). With none, the page cache stores nothing (a copy it could not validate is never served), `planetgen warm` refuses with a printed error (Redis is required for every run, PERF.127 removed the inline `--no-rq` mode).
