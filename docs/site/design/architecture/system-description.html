How planetGen turns a star system, a planet, a moon, a belt or a comet into the text and tables people read, so that the web page, the API, the command line and the Markdown export all say the same thing from one place.

Status: design, 2026-10-15; wikitext and the wiki upload were removed on 2026-10-24 (OPS.69, Boss: "strip out all of the wiki functionality"), Markdown and text stay. Decisions marked "Boss" are his; everything else is a recommendation. Written by the Foundations Wording lane. Informs: UX.103 (this note), UX.104 (the model), UX.105 (the web page; absorbs UX.30), API.25, UX.106, GEN.218 to GEN.221, UX.107, TEST.155, DB.31, DOC.45.

Boss (2026-10-15 04:21Z): "sweep all planet and system text output ... Make sure wording matches the habitability index and vice versa ... we're stripping out the markdown from the web site display in favor of more advanced tables like we're using, and generating markdown on the fly as needed; we can output markdown / wikitext for the user on request but it is no longer the default." Earlier (UX.30, 2026-10-01): "Rework planet information displays to pull away from the markdown render and instead fits with the modern web UI." The system overview stays prose (Boss, 2026-10-10 19:12Z).

1. What is wrong today

  • Every model class writes its own prose and tables: Star, BinaryStarProxy, WideBinary, Planet (planets and moons), AsteroidBelt, Comet, StarSystem.summary_paragraph, and six phenomenon classes, each in to_paragraph_list(). The output format is a mutable flag on the shared config (SystemConfig.MARKDOWN), flipped around each render by db/render.py, and saved in the run-config row (markdown column).
  • The web's expanded body rows were that Markdown, split per body by /api/systems/<id>/sections, then converted to HTML by web/lib/mdrender.py (the Python markdown package cut down to headers, pipe tables and <sup>). Since UX.120 the system page reads /description and splits the Document per body (describe.model.split_by_body); /sections is gone.
  • Units, header levels, template names and sentences live in the model classes. Quantities in sentences are formatted by four different helpers and bypass the unit ladders (util/ladders.py).
  • Life timelines (*_evolutionary_paragraphs), flavor_text and hab_note are stored as finished prose, and the code reads the stage back out of the text.

The audit file lists every surface and every finding with file:line.

2. The shape

model object graph / stored rows
        |  describe()          (pure, no format, no HTML, no Markdown)
        v
   Document  (typed, JSON-serialisable)
        |
        +--> HTML renderer      (web: tables, chips, .qty spans)
        +--> Markdown renderer  (on request)
        +--> text renderer      (command line)
        +--> JSON               (API, `GET /api/systems/<id>/description`)

describe() lives in a new package planetgen/describe/ (generation side: it may import the model and physics). It is a pure function of the system. The web app does not import it (the web app never imports numba, and the generation package pulls it in); the web gets the Document as JSON from the API and renders HTML from that, the way it already gets rows. The one-off system page, which today runs the CLI in a subprocess, asks the CLI for the JSON form and renders it the same way. The Markdown and text renderers are plain Python in planetgen/describe/ because the API (/text) and the CLI both run on the generation side.

The old per-class to_paragraph_list(), __str__ renderers, properties_to_string, to_scientific_notation's format switch, db/render.py and SystemConfig.MARKDOWN are deleted when the new path lands (no shims; Boss, 2026-10-07).

3. The Document

A Document is a tree of sections. Every node is a plain dict or list, the same in Python and in JSON; describe/model.py holds the constructors (qty, facts, prose, ratings, section, ...) and check(), which a test runs on every Document.

Document   {"kind": "system", "ref": "system:12", "title": "40 Eridani", "sections": [Section, ...]}
Section    {"kind": "system|star|pair|planet|moon|belt|comet",
            "ref": "planet:31",            # the object reference the site already uses (anchors, links)
            "title": "40 Eridani II",
            "blocks": [Block, ...],
            "children": [Section, ...]}    # a planet's moons; a wide pair's stars hold their own bodies
Block      one of
  Facts     {"type": "facts", "caption": "Orbit", "rows": [{"key": "distance", "label": "Distance", "value": Inline}]}
  Ratings   {"type": "ratings", "overall": {...}, "rows": [{"domain": "pressure", "tier": "Red", "score": 0.0,
                                                            "text": [Inline, ...]}], "gear": [Inline, ...]}
  Composition {"type": "composition", "label": "Atmosphere", "parts": [{"name": "nitrogen", "share": 0.78}, ...]}
  Prose     {"type": "prose", "role": "overview|summary|life|timeline|flavour", "text": [Inline, ...]}
Inline     a string, or one of
  {"qty": {"kind": "pressure", "value": 0.0, "unit": "Pa"}}   a quantity: kind (the ladder family), the value in the unit it was stored in
  {"ref": "planet:31", "name": "40 Eridani II"}     a link to another object
  {"strong": "Pressure: Red"}                       emphasis, rendered per format
  {"swatch": {"hex": "#99bfff", "word": "pale blue"}}   a colour (GEN.420): the word, with a chip where the format has one

The Atmosphere Colour row (GEN.420, key atmosphere_colour) of a planet or moon is a facts row whose value is one swatch: the colour of the body's air worked out by physics/atmosphere_colour.py from its stored mixture, ozone column and star (how it is worked out). Text and Markdown write the word (with the hex colour); the web page writes a swatch span that static/units.js paints from data-colour, because the site policy forbids style attributes. The row is absent for an airless body and for a giant.

Rules:

  1. No format in the model. No #, **, <sup>, templates or ''', and no Unicode superscripts. Emphasis and links are Inline nodes the renderers turn into whatever the format has.
  2. Quantities are values, never strings. A quantity names its family (distance, speed, period, mass, temperature, pressure, gravity, dose, luminosity, density...), its value and the registry unit the value is held in (model.qty checks the unit against unit_registry; model.measured keeps a Quantity's own unit). Each renderer calls the one ladder for that family (util/ladders.py for the text forms; unitladder.js for the browser, which is how the unit preference UX.78 can later re-render every .qty span from data-si). Nothing in describe/ formats a number itself, and a test fails on a raw :.2f or f"{x} km" in that package.
  3. A fact row has a stable key. The key is the old template parameter name where there was one (type, radius, mass, temp, lum, hab, orbit, loc, wobble, class, distance, period, speed, gravity, moon_wobble, separation, mutual_orbit, eccentricity, primary_limit, secondary_limit). The label is the display name (the Markdown key map, Property | Value).
  4. Text is short and complete. A Prose or Ratings sentence is a finished sentence in the site's voice (section 6). Wording is chosen in describe/, not in the model classes and not in the renderers.
  5. Everything is derivable. A Document is a function of the stored rows (or a fresh system). Nothing is cached in the database, so rewording changes every page with no regeneration.

3.1 What goes in each section

Section Facts Other blocks
system the overview prose only (stays prose: counts, habitable worlds, heliosphere, edge of the system; the cloud sentence) Prose(role=overview), Prose(role=flavour) when present
star type, radius, mass, temperature, luminosity, habitable zone, galactic orbit, planetary wobble, location Prose(role=summary): age, lifespan, the one sentence about what that means for life
pair (close binary) type, mass, luminosity, habitable zone, separation, mutual orbit, barycenter offset, galactic orbit, location Prose: the pair's age
pair (wide binary) separation, eccentricity, mutual orbit, barycenter offset, each star's planetary limit none
planet, moon class, distance, period, speed, radius, gravity, moon wobble; surface temperature, pressure (so the 0 kPa of an airless world is a fact, not a gap) Composition (atmosphere, surface), Ratings (rocky bodies), Prose(life), Prose(timeline), Prose(flavour)
gas giant the same facts; internal pressure and temperature Composition, Prose for the depth sentences
belt inner and outer edge, density Composition
comet type, perihelion, eccentricity, period, current distance and speed, nucleus size, activity Composition

One set of facts for the life text (GEN.666). The life paragraph and the timeline paragraph of a body are written from one describe.life_facts.LifeFacts (chemistry, pace, spectra, and the timeline's system age, milestone and milestone age), resolved once from the stored columns by life_facts.resolve. A sentence reads its fact from there and never from the body, and the pace is stated once, in the life paragraph (the timeline paragraph says "at that pace"). The generator draws the pace once (evolution.draw_scale) and the stored column is the only copy. The milestone name and text follow the chemistry's metabolism (tuning.LIFE_METABOLISMS), so a world whose life does not split water is never told it releases oxygen. tests/test_life_text_consistency.py fails if two sentences of a generated page name a different pace, chemistry, milestone or age. A new life fact (the four life scores of GEN.649) goes into LifeFacts and the checker in that test, not into a sentence on its own.

The table rows and prose are the ones the old text carried; UX.104 adds a coverage test that every old fact key and every old sentence topic has a home, so nothing is lost silently. Phenomena (nebula, quasar, rogue planet, asteroid field, compact remnant, supernova remnant) are described by the same model from GEN.221; the web's phenomenon page already shows their facts as tables (FIELD_SPECS) and only the CLI shows their prose.

3.2 The rating table

The six PHI-6 domains are a table, not a paragraph:

Domain Rating Why
Pressure Red (0.00) The air pressure is 0 kPa, so a pressure suit is needed.
Temperature Red (0.00) The air temperature is -227 C, so an environment suit is needed.
Air Red (0.0) There is no atmosphere (0.0 kPa).
Water Red (0.00) There is no liquid water to support life.
Radiation Yellow (0.45) The radiation dose is a mean of 742 mSv a year, inside the Yellow band (up to 1 Sv a year).
Suitability Red (0.20) There is no atmosphere (0.0 kPa), no food or water. Shelter is potentially available.

with the overall line above it ("PHI-6 habitability is 0.00, and a visitor needs an environment suit.") and the equipment label. These rows are Boss's text (GEN.216, 2026-10-15 03:46Z). The colour is a chip, using the symbols of UX.101; the colour is never the only signal (the word is in the cell). Markdown renders the same rows as lines of bold text, as GEN.216's examples do, because a table is not needed there. One module builds the rows from physics/habitability and physics/protection_limits (the single limits table), so the colour, the score, the band the sentence names and the gear come from one calculation. Until GEN.215 and GEN.216 merge, UX.104 calls the existing functions and the rows carry the current wording; GEN.218 replaces the wording.

4. Renderers

Renderer Where Output
HTML describe/html.py (UX.119; the page passes it the links of its own routes) A body's detail is: a facts table (<table> in the site's table-scroll wrapper), the ratings table with chips and symbols, the composition bars, prose paragraphs, then its moons. Quantities are <span class="qty" data-q="..." data-si="..."> (data-si is the value converted to the kind's SI unit, DISPLAY_UNITS). Same tables, chips and both themes as the rest of the site; no header levels or Markdown, so no mdrender.
Markdown describe/markdown.py Today's layout: # system, ## planet, ### moon, `Property
text describe/text.py Plain tables and sentences for the terminal (Unicode superscripts, no markup). The command line default.
JSON the API The Document as above.

The web page keeps its row list (name, chips, a <details> per body); only what is inside a row changes, from converted Markdown to the Document's HTML. The page-level Markdown button keeps working: it asks /text?format= and shows the result in the code box. It is on request only.

5. Inputs

describe(system) takes a StarSystem object graph. That is what db/store.load_star_system already returns for a stored system and what generation builds for a new one, so the stored page, a fresh planetgen system --output - and the one-off page all go through the same code with no second row shape. Each body keeps its db_id (set by the loader) so a Section's ref matches the row the page links to. The habitability rows read the same column-named values the stored scores come from (habitability_world.values_from_body).

Cost: the page already loaded the graph for /sections; the Document replaced that call, so there is no extra load. The Document is not cached in the database; the page cache (web/lib/pagecache.py) already covers repeat views.

6. Wording rules (the style the sentences are written to)

  • Short, plain, in-universe: the voice of a chart or a survey, not of the generator. Public pages use the UX.42 words (chart, charted, uncharted); admin pages keep plain wording. Boss's lines are the model: "The air pressure is 0 kPa, so a pressure suit is needed."
  • One fact per sentence; a sentence names its value (as a quantity) and, where it helps, the band it falls in.
  • No filler joins ("of a mix of", "which is expected to", "approximately" before a computed value). Lists use "A, B and C".
  • Ages and durations use the ladder (Gyr, Myr after UX.81); "Billion Years" goes.
  • Moons and planets share templates with a noun parameter; no regex rewriting of planet wording into moon wording.
  • "Habitable" in a sentence means the PHI-6 rating: overall Green or Blue (Boss, 2026-10-23; habitability.is_habitable is the one definition the API, lists, search, map and counts use). The class flag is called "habitable class". The zone keeps its name ("habitable zone").
  • The index is PHI-6 everywhere a person reads it. Stored column names (phi4, phi4_<domain>) are internal and stay (default; renaming is an optional migration).

GEN.221 rewrites the fixed text (class descriptions, star notes, flavour) to these rules; this note does not.

8. API and command line

  • GET /api/systems/<id>/description returns the Document (JSON). GET /api/systems/<id>/text?format=markdown|text renders it. GET /api/systems/<id>/sections and render_system_sections are removed (UX.120); mdrender.py and the markdown dependency of the web app go with UX.109. docs/reference/api.md documents both.
  • CLI: --markdown on system, sector, galaxy and the phenomenon commands becomes --format text|markdown (default text; Decided default). --output FILE writes whichever format was asked. - is stdout.

9. Tests

  • Coverage: every fact key and sentence topic of the old render has a home in the Document (a fixture over the example systems in examples/systems/).
  • Renderer parity: Markdown and text for the same Document carry the same facts and the same sentences; quantities agree with the ladder text (util/ladders.py) and the browser's unitladder.js (existing Python/JS parity test).
  • No-format rule: nothing in describe/model or the builders contains Markdown or HTML (a scan test), and no raw numeric formatting (:.Nf, toFixed) in describe/.
  • Web: the system page contains no output of markdown and no <sup>; every quantity is a .qty span with data-si.
  • Index and wording agree (TEST.155): colour, score, band named, gear and equipment label from the same world, for random worlds and the example systems; an airless body is never better than Red in Air; text that claims life agrees with the life guard.
  • The Markdown tests (test_mdrender.py, test_fuzz_text_rendering.py, test_system_render.py, test_bughunt_render_edges.py) are rewritten against the Document and the renderers, not patched.

10. Order of work

  1. This note (UX.103).
  2. describe/ builds the Document for every section kind from a StarSystem, with the coverage test; the old renderers still exist (UX.104). Quantities not yet on a ladder (mass, temperature, pressure: UX.22 and UX.23, Foundations UX) are carried as a plain number with a unit symbol until their ladders land, then switched by changing one table.
  3. The three consumers move over and the old code is deleted in the same PR as each move: the web page and one-off page (UX.105, which is UX.30), the API and exporters with the removal of SystemConfig.MARKDOWN (API.25), the CLI (UX.106).
  4. Wording (GEN.218, GEN.220, GEN.221) and units at the remaining call sites (UX.107), after GEN.215 and GEN.216 for the habitability text.
  5. The stored-prose migration (DB.31), when Foundations Database has room.
