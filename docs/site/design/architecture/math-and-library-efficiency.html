A survey of the generator's numerical code against the libraries it could use: which hot spots are still plain Python, which already run on NumPy or SciPy, what each candidate fix measured, and what each new library would cost to install and keep. Measured on a real two-sector fill and a real plan, with the fixes prototyped outside the repository and run end to end. No code in the repository was changed.

Informs: GEN.105, GEN.106, GEN.115, PERF.31, PERF.46, PERF.72, GEN.198, GEN.199, OPS.20

Status: decided; the study itself changed no generator code. Built: Python 3.12 and numba required (OPS.42, #1291) and astropy dropped (GEN.211, #1310). Built: the numba sector-path integrator, now the shared field kernel physics/field_kernel.py (PERF.88, 21 times faster per path; timings in generation-benchmark-report.md). Any other "recommend" is a proposal for Boss.

Evidence tags: [C] measured in this research (scripts under /mnt/project-files/research/scripts/mathperf/); [S] read in the repository or on a package page; [R] recalled and unconfirmed.

Method and limits

  • One 4-core Linux container (Ubuntu 24.04, the VPS's size and OS), MariaDB 10.11 and Redis on the same box, Python 3.13.16, NumPy 2.5.4, SciPy 1.18.1, astropy 8.0.1, numba 0.68.0 [C]. The project's minimum was Python 3.9 and is now 3.12 (see Decisions). apt's NumPy on 24.04 is 1.26 [S][C]; speeds on the VPS's Python 3.12 will differ a little.
  • The workload is the PERF.31 benchmark's: seed ...BEEF, plan to ring 12 (2,041 layers), then galaxy --ring 12 --limit 2 --yes with one worker (1,916 systems, 17,284 bodies that get a sector path) [C]. Profiles were taken on 8.0.9xx (2c135ba); the end-to-end comparisons on 8.0.986 (PERF.73 merged).
  • Stage seconds come from the run's own stage records, not from cProfile, which inflates code made of many small calls about 2.5 times; profile seconds are used for shares only. Timings are one run each and vary by about 10% between identical runs (the baseline "Generate the sectors" stage took 46.3, 48.1 and 52.5 s on three runs), so only differences well above that are claimed.
  • The prototypes live in /mnt/project-files/research/scripts/mathperf/ and are run with patched_run.py, which patches them into a normal planetgen run. Nothing here was run on the VPS, at the default galaxy's scale, on MySQL 8.4, or with more than one worker.

The answer in short

  1. The numeric core is already on NumPy and SciPy where it was looked at. The phenomenon scatter is vectorised (PERF.63), routing uses cKDTree (NAV.52) and A* on a k-nearest graph, Kepler's equation has a vectorised Halley solver, nebula meshes use scikit-image's marching cubes. No library the project lacks would speed those up.
  2. Three places are still plain Python and cost real time, and one of them needs a new library.
    • The sector-path integrator (physics/sector_path.integrate_path) is 1.0 ms a path; 17,284 paths are the "Save the sector paths" stage, 34 s of a 92 s fill, and the orbital update (the 8.0 headline) runs it again for every body that moves. A numba port runs it in 34 to 46 us (22 to 31 times); with it the stage fell from 34.2 s to 13.4 s, the rest being database writes. A NumPy batch version managed only 1.8 times.
    • SpaceSector.nearest_neighbors sorts every other system for each system. scipy.spatial.cKDTree, already required, answers it 190 to 590 times faster with identical neighbours; the generate stage lost about 10%.
    • The bright and massive star scatters evaluate the galaxy density one point at a time (556,000 calls, 7.9 us each); the NumPy form the phenomenon scatter already uses is 47 times faster per point.
  3. numba is the one library worth adding, and only for the integrator and later kernels like it. It costs 196 MB installed, Python 3.12 or later (Boss's decision, 2026-10-14), and a compile cache. Everything else recommended below needs no new dependency.
  4. Two libraries looked at are not worth adding: orjson (JSON encoding is 1 to 4% of a tile request) and mysqlclient (no faster on inserts, GPL).
  5. One library could come out: astropy is imported for about twenty constants; reading them from a table saves 280 ms and 29 MB per process start and 53 MB of install.

Findings

1. Sector paths: 1.0 ms a path, 22 to 31 times faster in numba

integrate_path is a leapfrog integrator written with tuples: per step it loops over up to 32 point masses twice (step size, acceleration), tests the cell with sector_address_at, and a bisection of 40 more tests finds the exit. Every one of the 17,284 paths came out as two knots (a straight line within the 0.2% tolerance), at about 90 steps each [C]. Where the 1.0 ms goes: in a profile of 300 paths _step_size and _acceleration (31 masses by 90 steps) took 57%, and relevant_masses measured alone is 180 us (18%); the cell test and bisection are the rest [C].

Variant (8,678 paths of one sector) ms/path Against shipped
V0 shipped 1.02 to 1.08 1
V1 memoise ring_sector_count and friends (functools.lru_cache) 0.92 to 1.00 1.1
V3 NumPy batch: all bodies advance together, 192 lock-step iterations 0.53 1.8 to 2.8
V2 numba integration, NumPy mass selection 0.21 5
V2b numba mass selection, integration and spline check in one call 0.034 to 0.046 22 to 31
  • The NumPy batch is the best that needs no new library and it is not worth its complexity: the bodies need different step counts, so the batch is mostly masked work.
  • A pure-Python shortcut exists: 69% of bodies have a summed deflection bound under the tolerance, so a straight line would do for them [C]. That caps the saving at about 3 times and changes how the exit knot is found; numba keeps the algorithm as it is.
  • End to end (patched_run.py --kdtree --numba): "Save the sector paths" 34.2 s to 13.4 s. What is left is the database: for each path the delete-by-key, the insert and the knot insert are separate statements [S].
  • Agreement. Without fastmath, numba uses the same arithmetic in the same order. 34,566 of the 34,568 saved knots are bit-identical to the shipped run; the other two differ by at most 7e-15 pc in position and 4e-16 in relative time. An exit time agreed to 0.0 in the micro-benchmark. The prototype falls back to the shipped code for any path needing more than two knots (none did here). Tests that compare saved paths should use a tolerance, not equality.
  • Scale. One million bodies is about 1,000 s of single-core integration in Python and about 40 s in numba. The orbital update recomputes the paths of every sector holding a body that moved (cli/orbits.py, db/sector_paths.compute_sector_paths) [S], so this is the cost that grows with the 8.0 headline, not a one-time fill cost.

2. Neighbours: sort-everything against a k-d tree

SpaceSector.nearest_neighbors(entry, count) sorts all other entries by entry.distance_to for every entry saved: N^2 log N, each distance_to going through two position properties (SpatialPosition3D.get_coordinates, 0.43 us). In the fill profile that chain was 8.3 million get_coordinates calls, 11% of profiled time [C].

Systems in the sector Shipped cKDTree Speed-up
300 0.22 s 3.2 ms 68
1,000 2.28 s 3.9 ms 587
1,900 9.22 s 47.9 ms 192

The benchmark sectors hold about 960 systems; denser inner rings hold more, and the shipped cost is quadratic. End to end the "Generate the sectors" stage went from 46 to 52 s (three baseline runs) to 42.7 s with the tree, about 10%. The neighbour lists written to the database were identical in all 51,861 rows. The placement loop (sector.py _massive_neighbors, 919,000 distance_between calls) has the same shape and can use the same tree.

3. Galaxy density, one point at a time

bright_stars._ring_bins and layer_expected_stars call density.population_densities per angle bin: 556,000 calls in the plan, 7.9 us each (4.4 s) [C]. density.total_density_array, built for the phenomenon scatter, gives the same sum at 0.17 us a point (47 times) [C]. A per-population array version is a copy of that function returning the four terms. Share of the plan: about 4 s of the 15 to 20 s the massive and bright star stages take; the rest of those stages is waiting on the database (20.7 s of the 82 s profile sat in socket reads) [C].

4. Random draws can be bulk with no change to any galaxy

draw.Stream builds everything on random.Random.random(), so every galaxy depends on that exact sequence. CPython's random and NumPy's MT19937 are the same generator with the same 624-word state and the same 53-bit float, so the state can be handed to NumPy, a batch drawn in C, and the state handed back. The floats are identical, and so is the generator's state afterwards; getrandbits(63) (two draws, shifted) also matches [C].

Draws in a batch Python loop Bulk Speed-up
6 1.7 us 102 us 0.02 (slower)
600 99 us 113 us 0.9
6,000 581 us 141 us 4
60,000 5.7 ms 0.46 ms 12.5

The 102 us is the fixed cost of moving the state. It pays off above about 1,000 draws a call, which only the scatter layers reach (_uniforms: 6 per object; rng.getrandbits(63) per object). At the benchmark's scale the draws are 0.3 s of 16 s, so this is a default-scale concern (hundreds of millions of rows), not a today concern. No reseed is needed, unlike the move to a different generator.

Built (PERF.91): draw.Stream.random_array and draw.Stream.randbits_list (bulk from draw.BULK_MIN = 1,000 draws), used by the phenomenon scatter, the far-reach scatter and the component pass; tests/test_draw_bulk.py proves the same floats, bits and final state.

5. The orbital update's per-row Python

advance_galactic_positions moves each due system with a chain of small functions per row (turn, rotate, local_to_galaxy_pc, sector_address_at, galaxy_to_local_pc, classify_octant). The chain costs 25.7 us a row; the same maths on NumPy arrays 3.8 us a row (7 times), and the refiled sector address agreed on all 100,000 rows [C]. The SQL side (UPDATE ... executemany) costs about as much per row again, so the whole update gains about 3 to 4 times, not 7. Planet and moon motion is already a set-based SQL UPDATE [S].

7. Libraries looked at and not recommended

  • orjson. Encoding a Galaxy Map tile of 120 to 700 kB takes 0.2 to 2.8 ms against 1.7 to 13 ms for json (4 to 10 times faster), but the tile query itself is 37 to 660 ms [C]; encoding is 1 to 4% of the request.
  • mysqlclient (the C driver). executemany of 200,000 13-column rows took 5.0 s against 4.4 s for pymysql (the server, not the driver, is the limit), fetchall 1.6 s against 3.0 s [C]. It is GPL-2.0-or-later, which the CC0 project has not accepted (orbital-solvers-and-integrators.md section 4.3), and it needs a compiler and libmariadb-dev to build [C]. LOAD DATA LOCAL INFILE was 2.7 times faster on inserts but needs local_infile on both ends, which PERF.73 already declined.
  • Cython or Pythran for the integrator. Likely as fast as numba [R], but needs a compiler and Python headers on the VPS and a build in update.sh. Not measured.
  • A NumPy batch integrator. 1.8 times; see finding 1.

The scatter workers now pre-import before they fork, so this matters for each command line start, each mod_wsgi process and each worker restart, not for each job. astropy on disk is 41 MB, with pyerfa 3 MB and the IERS data 8.6 MB; physics/constants.py is the only user [S]. The constants are fixed numbers (CODATA and IAU), so a table in the repository (generated once from astropy, checked against it by the existing test_astropy_constants.py with astropy kept in the test extra) removes the dependency and the import. nltk is only used for the words corpus; reading the same file directly would drop 1.1 s and 97 MB, but that is a names question, not a math one, and is listed only so it is not lost.

Boss's rule of no compatibility shims argues against a pure-Python fallback beside the numba kernel: make numba a hard requirement and raise the minimum Python to 3.12 (the VPS runs 3.12). Memory is the VPS's tighter limit with MySQL on the same box: importing numba adds 75 MB to each process that does, so only the processes that integrate paths (the settle step, the orbit update, workers) should import it, not the web app.

Decisions (Boss, 2026-10-14)

  1. numba is a hard requirement and the minimum Python is 3.12. The Python 3.9 CI leg, the lock-file branches for 3.9 to 3.11 and the python_requires floor go with it. Because this changes what the project installs on, the CHANGELOG and the README must say so when it lands.
  2. The numba cache stays in numba's default place, not /var/cache/planetgen/numba. See the next section for the one thing this has to be checked against.
  3. astropy is dropped for a constants table, with astropy kept in the test extra. Double-check, run on 2026-10-14: physics/constants.py run under astropy 6.0.1, 6.1.7 and 8.0.1 gives the same value for 89 of 90 numbers; only HYDROGEN_ATOM_MASS_KG differs, by 1.35e-9 relative. astropy is imported for nothing else, so it gives the project no behaviour beyond the numbers and makes them depend on the installed version (the problem GEN.156 was filed to patch). Table plus the existing test is strictly better.

The default cache and the web user

Measured 2026-10-14 with a one-function @njit(cache=True) module run as an unprivileged user [C]:

Tree owner Process user's home Result
user does not own the tree not writable import fails: RuntimeError: cannot cache function: no locator available, even when root already warmed the tree's __pycache__
user does not own the tree writable works; numba builds its own cache under that home (~/.cache/numba), so a warm-up by another user does not help
user owns the tree any works; cache in the tree's __pycache__

So numba's default location works for every process that can write either the checkout's __pycache__ or its own home. Processes that may not (the web user under Apache, with /var/www normally root-owned) fail at the import of any module holding a cached kernel, and an update.sh warm-up run by the tree's owner or root does not reach them. Two ways to keep the default location: (a) the kernels live in a module only the settle step, the orbit update and the workers import (the web app imports it lazily, or not at all), which also keeps numba's 75 MB out of the web processes; (b) update.sh makes those __pycache__ directories writable for the web group. Whichever is built must be tested by importing the integrator as the web user.

What this does not predict

  • Default scale. All timings are from a ring-12 galaxy of 1,916 systems. The quadratic term in finding 2 and the draw volume in finding 4 grow with scale; the numba gain is per body and should hold.
  • The database. After the fixes in findings 1 and 2 the sector-path stage is 13.4 s of which nearly all is writes; the next gain there is batching the statements, not faster maths.
  • Workers. Everything ran with one worker. With two workers the fill speeds up and the settle step does not (it is one process) [S]; numba matters more as the fill scales out.
  • mod_wsgi. Importing numba inside Apache processes was not tried.
  • Python 3.12 against 3.13. Timings are from 3.13; speeds will differ a little, the ratios between variants should not.
