This document is the map of the program. It says which file holds what, and it traces the main flows (generating a galaxy, storing it, serving it, running admin jobs, shipping a release) through those files. Use it to find where something lives before you open the code.

It does not repeat the reference docs. For details, follow the links: api.md (the JSON API), database-schema.md (tables and columns), html-interface.md (the web pages), config.md (config.json), testing.md (the test suite) and deployment/ (servers). The other files in this folder are topic designs; they explain why a part works the way it does.

Keeping it current. A PR that adds, moves, renames or removes a module, script, workflow or top-level folder updates this file in the same PR. If a flow below changes shape (a new step, a new cache, a new process), update its diagram too. Each module's own docstring stays the detailed source of truth; this file only needs one line per module.

The big picture

planetGen has three layers that share one Python package:

  1. Generation. planetgen and the generation/, physics/, galaxy/, population/, names/ and describe/ packages under src/planetgen/ build stars, planets, sectors and whole galaxies from physics models and random draws.
  2. Storage. src/planetgen/db/store.py writes those objects into a MySQL database (schema.sql), reads them back, and migrates old databases forward. A second, separate schema (control_schema.sql) holds admin logins.
  3. Serving. One Flask app (planetgen/web/app.py, started by src/html/wsgi.py) serves both the JSON API (/api/...) and the HTML pages. The pages never query the database themselves; they call the API in-process through planetgen/web/lib/apiclient.py, and the API reads through planetgen.db.query and store.py. Redis sits beside MySQL: the work queue (RQ), the rate limits, the login throttle and a running job's progress live there (see redis-and-the-work-queue.md).

Around those sit the installers (install.sh and update.sh), maintenance tools (planetgen.cli.orbits, planetgen.cli.migrate, ...), the tests, and the release workflows.

Flow 1: generating a galaxy

A galaxy is built in two passes. planetgen plan stores the galaxy's shape and outline and scatters its bright stars and phenomena. Then sectors are filled, either in bulk (planetgen galaxy, with a mode for a random start, one sector, a shell, a span of addresses, a course or a neighborhood) or on demand when an admin asks for a neighborhood. Every sector is addressed by (shell, band, wedge) in the spherical grid (galaxy-coordinate-system.md).

flowchart TD

Plan. run_plan in planetgen/generation/run_plan.py builds a GalaxyShape (galaxy/density.py) and finds each shell's reach with skeleton.build_shell_extents: the highest band the shell has to cover before the density drops under one star per sector. It stores the shape (galaxy_shape) and the outline (galaxy_shell, one row per shell) and then scatters the phenomena and bright stars. Sector positions are never stored up front; they are pure functions of the (shell, band, wedge) address (galaxy/spherical.py). The run's stages (generation/stages.py) are numbered and announced as it goes.

Scatter. scatter_phenomena (phenomenon_scatter.py) places the galaxy's black holes, neutron stars, planetary nebulae and supernova remnants, plus the special objects, one task per run of shells, with the object-first rule (object_first.py): decide how many objects a shell holds, then where. scatter_bright_stars then draws the stars in two passes (GEN.185): the mass pass places every star born at or above the stellar mass limit, and the luminosity pass places every lighter star at least as bright as the luminosity floor, skipping sectors a pass-one star already marks (bright_stars.scatter_shell, canonical_bands). Both write bright_stars in batches, leave out sectors that are already filled, and can be redone alone (--redo-scatters).

Sector fill. Every galaxy mode ends in generate_and_save_sector_at (run_galaxy.py). It loads the sector's FillContext (population mix, its unfilled bright stars, its unbuilt scattered phenomena), then calls generate_directed_sector and generate_sector in run_sector.py, inside the sector's own seed (galaxy/seed.py) so the run's order and worker count do not matter. That builds a full StarSystem around each pre-placed bright star from its stored seed, draws the remaining systems from dim stars only (the expected count shrinks by the bright share), places each one with Hill-sphere spacing (SpaceSector.add_system), and adds phenomena. The center sector may also get a quasar (add_galactic_nucleus).

System. StarSystem (generation/system.py) builds its star or binary (star.py, binary.py, wide_binary.py, phenomena/compact_remnant.py), then planets and moons (planet.py over physics/planets.py), belts and comets, then applies life data (life.py). Names come from names/gated_phoneme_codec.py and names/bodies.py. object_timing.py records how long each kind of object took.

Save. store.save_sector runs insert_sector in one transaction, with rows written in multi-row batches and ids taken from id_blocks: it reserves a unique sector name, inserts the sector with its grid address, inserts every system (insert_star_system, which inserts stars, planets, moons, belts and comets), marks bright stars filled, inserts phenomena with their galaxy-frame placement, and refreshes the sector's stats.

After the run. A galaxy run saves its sectors without linking them and then does the shared steps once for the whole run: link_after_run (store.link_sector_neighbors: containment, nearest systems and quadrants for the new sectors and the lists of those around them), the scatters, backfill_after_run (the bright stars the new sectors need from the space around them), the population pass, and settle_after_run (db/sector_paths.py: the path of every body in the new sectors and their neighbours, so each path sees the final set of neighbours).

planetgen system and planetgen sector build the same objects without a galaxy (a cube sector, no address). planetgen system --output FILE writes the page and saves nothing.

Population (optional). Species, civilizations, polities and territories are a separate pass over what is already stored, so system generation does not change and an old galaxy can be populated without a regenerate. It is off by default: it runs from planetgen population, as a stage of a planetgen galaxy run, or when someone answers y to the installer's prompt (Flow 5).

Flow 2: storing and migrating the database

There are two schemas. The content schema (schema.sql) holds one galaxy; a server can host several, chosen by name prefix. The control schema (control_schema.sql, default planetgen_control) holds admin accounts for the whole deployment. Each has its own version table.

    ES --> Content[("content schema")]

    RO["read-only callers<br/>(db.query.open_readonly, API)"] --> NoDDL["get_connection<br/>ensure_schema=False"]
    NoDDL --> Content

    Ask -->|"N"| Mig["planetgen.cli.migrate<br/>store.migrate_database<br/>each Alembic revision"]

Creating. Any read-write connection (store.get_connection with its default ensure_schema=True) applies schema.sql. Every statement is CREATE ... IF NOT EXISTS, so a new database comes out at the current SCHEMA_VERSION and an existing one is untouched. Read-only callers pass ensure_schema=False, since their account may lack CREATE.

Migrating. schema.sql always describes the current shape. An older database is moved forward by store.migrate_database, which runs every Alembic revision (planetgen/db/migrations/versions/, run through planetgen.db.alembic_runner) above the stored version, in order. A revision's id is its schema version, so SCHEMA_VERSION is the head revision's number. Databases older than v130 (the baseline) are refused with SchemaTooOldError rather than migrated, and so is a database with tables but no recorded version (SchemaVersionMissingError). planetgen.cli.migrate is the CLI wrapper with a progress bar. A change to a sectors column rebuilds the whole table, because the FULLTEXT index on sectors.name rules out ALGORITHM=INSTANT (DB.84): such changes are batched into as few revisions as possible, each saying in its docstring that it rebuilds sectors, and the index stays. A schema change therefore touches schema.sql, a new revision file, the regenerated planetgen/db/models.py (scripts/generate_db_models.py), and database-schema.md; the steps are in src/planetgen/db/migrations/README.md.

Control schema. After the content migration, planetgen.cli.migrate calls admin.auth.bootstrap_control_schema. It creates the control database if needed, applies control_schema.sql, and seeds an admin user with a random password when there is none. planetgen.cli.migrate prints that password once.

The sector-grid switch. Revision 0091 converted the cylinder sector grid to shells, bands and wedges in place (renumbering the object IDs from the new sectors). The migration turns maintenance mode on, which closes the site and the API to everyone but the admin until the Galaxy Map has been rebuilt; revision 0092 made the block totals on shells, and planetgen warm turns that maintenance off again once the opening view is built (planetgen/admin/maintenance.py, planetgen.cli.maintenance). An admin's own maintenance stays on.

Other writers. planetgen.cli.reset truncates generated tables. planetgen.cli.orbits advances orbits (store.advance_orbital_phases, advance_galactic_positions, refresh_after_motion). The population pass (Flow 1) writes species, polities, system_owners and population_state; the work queue's progress and job counters live in Redis, not MySQL (see redis-and-the-work-queue.md). The API's system writes go through store.add_system_to_sector (a new system in a stored sector, placed clear of the others' Hill spheres, with containment and nearest systems filled in) and store.replace_star_system_content (regenerate a system's bodies in place, keeping its id, name, position and links). Page text is not stored; db/render.py renders it from rows when asked.

A page. wsgi.py builds the app with web/app.py's create_app, which installs the maintenance gate first (while maintenance mode is on anyone but a signed-in admin gets a 503 and the "being updated" page), then registers the API blueprints and calls web.init_app. A page view (for example web/sector_page.py) calls an apiclient function. Because transport.install() ran at startup, the call goes straight through the app's own WSGI callable: same route, validation and auth as over HTTP, without a socket. The API route reads through planetgen.db.query (listings, details, search, nav) or store.load_*. The view then builds map data with lib/ helpers and renders a Jinja template. Errors become HTML pages (web/errors.py); under /api they stay JSON.

The page cache. Before a public GET (one that sends no cookie, so every visitor gets the same answer), apiclient._request asks the app's pagecache.ResponseCache (installed by web.init_app). A hit skips the API and the database; a miss stores the raw JSON body with the data tags it read and their counters (planetgen.db.dataversion, in Redis), also in Redis so every worker and the warm-up share it. A copy is served only while its counters stand. Any successful POST, PATCH, PUT or DELETE under /api bumps the tags it changes before the response goes out (pagetags.change_for_write), so only the answers that read them are rebuilt; the population pass, the orbital update and generation do the same when they finish. At most once per stamp_seconds per database, the cache reads the same content stamp the tile cache uses (GET /api/galaxy/changes), the backstop for a change nobody recorded: sectors and systems added by a direct database edit are seen within 15 seconds by default. Nothing is kept past max_age_seconds (5 minutes by default) in a process. It fails open (no Redis, no cache), and page_cache in config.json tunes or disables it. The warm-up fills the shared copies after an update (planetgen warm, cache-warm-up.md).

Admin writes from the pages. The system page's facility form (web/system_facilities.py) previews a placement against planetgen.population.facilities.check_facility and GET /api/facilities/orbit, then saves with POST /api/facilities or removes with DELETE /api/facilities/<id>, each a plain CSRF-checked POST with a 303 back to the page. Like every API write it bumps the data tags it changes (the page cache).

The Galaxy Map. /galaxy (web/galaxy_views.py) draws the 3D map on the shell grid, and the sector page's Sector Map is the same map locked to its sector. The pieces:

  • Nodes. static/galaxymap3d.js fetches the sector-block nodes that static/galaxynodecut.js picks for the camera (a block opens into its children as it grows on screen; MAP.261) from /galaxy/nodes, a packed binary body (web/lib/tilepack.py writes it, static/tilepack.js reads it; MAP.159), and keeps them in IndexedDB (planetgen-nodes), with only a small record of the cache stamp in localStorage. A node is a block of the ladder below, not a cube of space; its glow comes from the stored galaxy_block_lights table (db/block_lights.py, MAP.259) and its read is db/nodes.py (MAP.260).
  • Named regions. A region is a 9-block of the ladder that holds a generated sector (galaxy/named_regions.py: name, anchor, framing sphere, extent); region_stats (db/region_stats.py, DB.107) stores its sector count, capacity (so the share charted), extent and summed mass, kept by the same hooks as galaxy_block_stats. The mass of a sector (sector_stats.total_mass_kg, db/sector_mass.py, DB.108) is the sum of its bodies; a block and a region add up the sectors'.
  • The block ladder. The drill-down's stages (/galaxy/stage) and data windows (/galaxy/window, MAP.151) are blocks of 243, 81, 27, 9 and 3 shells (galaxy/drill.py, galaxy/window.py, docs/design/galaxy/spherical-block-ladder.md). db.query.galaxy_stage and galaxy_window read each block's totals from the stored galaxy_block_stats table (schema 92, kept by db/block_stats.py) and the sectors of a level-3 block from sectors and sector_stats. The totals are sums of each sector's sector_stats figures, and three things keep them true (DB.83): a galaxy run refreshes the blocks above the sectors it saved once at its end, a sector visited or regenerated and a sector deleted refresh the chain above it, and an edit that changes what a sector holds (db.edits.save_system_edits, the system delete) first states the sector's figures again from its rows (store.refresh_edited_sectors) and then refreshes the chain. The orbit update does not: a system it refiles into another sector stays counted where it was generated, as check-db's count warning says. planetgen fill-block-totals makes the block rows again from the sectors' figures.
  • Address bar. A sector designation (such as C8030005), shell/band/wedge or shell N band N wedge N, x, y, z in parsecs or a name. A name goes to /galaxy/locate, which calls db.query.galaxy_locate through the API.
  • NAV course. The NAV result links to /galaxy?course=<from>,<to>. galaxy_views._course_from_args asks nav_page.galaxy_course for the waypoints. "Start Here" and "End Here" in an object's panel (static/navpick.js, NAV.29) and a pick mode (?pick=to&from=...) work as before.
  • Territories. /galaxy/territories merges /api/territories (owned systems and capitals) with /api/polities (names, colors, counts); the button and legend appear only when /api/polities counts at least one polity.

Login. The /login page posts the form through apiclient.auth_login to POST /api/auth/login. That route is limited per IP (10 a minute), then checks the lockouts (api/loginguard.py, planetgen/admin/throttle.py): 3 failures from one address lock it for 5 minutes, doubling up to a day, and 10 for one username lock it for 1 second, doubling up to 15 minutes, both kept in Redis (SEC.30). The password is checked against the control schema (admin.auth.authenticate). On success admin.auth.create_session stores only a hash of a new token, and the raw token goes back as the session cookie. admin_pages.py relays that Set-Cookie onto the page response.

Every later request. api/authz.py resolves the admin from the session cookie or a Bearer API key. require_admin(fresh=True) also refuses an admin who still has to change the seeded credentials (/account does that). Page forms carry a CSRF token checked by web/csrf.py on every non-API POST.

Jobs. /admin/generate turns a form into a list of command lines (generate_page.py) and calls web/jobs.start_job. That writes job.json into a new job directory, takes the one-job lock (a hash in Redis), queues web/job_runner.run as an RQ job and starts a burst worker for it, detached from the web server, so a request timeout or a server reload does not stop it. The runner runs each step with the site's database in PLANETGEN_MYSQL_* and PLANETGEN_PROGRESS_FILE set; it writes state.json and output.log, and planetgen writes progress.json. The page only reads those files: the status (/admin/generate/status, polled by static/generatejobs.js) and the job's log (/admin/generate/jobs/<id>/stream, a live stream that ends on purpose every few seconds, and .../log, shown by static/joblog.js in a terminal box). Cancel writes a cancel file the runner watches. A lock left by a dead runner is cleared by the next start_job. The job itself is only that list of steps; the work a step does is a run on the Redis work queue (below), and the Queue page, the job's page and cancel read and act on the runs in Redis (queue/runview.py, queue/runcontrol.py: a run started under a job is listed under it, and canceling the job cancels its runs). See redis-and-the-work-queue.md for the design and how it was built (PERF.86).

Planning runs the bright-star scatter as its own step (planetgen plan --bright-stars-only after plan --no-bright-stars), so the job shows its progress bar and count; "Skip all scatters" leaves it out, and "Rebuild the bright stars" runs it alone on the stored plan. Each step of a planetgen galaxy, plan, scatter, sector or system command is a stage of a run on the Redis work queue: the wrapper (queue/wrapper.py) turns the arguments into the list of commands to run (queue/commands.py), writes the run's record in Redis (queue/runrecord.py: its stages, counters, results, log events) and cuts the first stage into units; a unit is an RQ job on the bulk queue carrying JSON, run by the idle-timeout workers (queue/workers.py, planetgen.cli.worker) that ensure_workers starts, and the unit that finishes the last of a stage queues the next stage, so the command that started the run only follows it. A chunk of sectors, a chunk of a shell scatter and a backfill block are each one unit. Generate neighborhood (on the Sector Map and the Galaxy Map, static/generatebuttons.js) asks for a radius in light years, 13 to 652, and asks again past about 5,000 sectors.

The one-off system page (/admin/generate/system, web/system_page.py) does not use jobs: it runs planetgen system --output in a temporary directory and waits, since a system takes about a second.

Install. install.sh (Linux and macOS) follows numbered steps. Shared steps live in scripts/deploy-common.sh, so install and update cannot drift. Libraries come from scripts/install-python-deps.sh (pip with --require-hashes from requirements.lock, or apt on an externally managed Python). Redis must answer at redis.url: ensure_redis installs and starts redis-server on a local address when nothing does, and check_redis_settings only warns about settings that do not suit planetGen (examples/redis/planetgen.conf). The database step is planetgen.cli.migrate (Flow 2). After it (in install.sh, after the NLTK corpus, which the species names need), offer_population_pass asks whether to run planetgen population. The answer defaults to No after 30 seconds, and with no terminal the question is skipped. POPULATION=1 runs it without asking. The update script never asks or runs it (OPS.7). install.sh --skip-database skips both. The examples/apache/ helpers set permissions and create the tile cache, jobs directory and debug log.

Update. update.sh forces the checkout to the branch tip (untracked files such as config.json are kept), then run each check and change only what is missing. The maintenance timers in examples/maintenance/ can run it, and planetgen.cli.orbits, on a schedule. It ends by warming the Galaxy Map's opening view (warm_galaxy_map, planetgen warm, MAP.134).

Releases. A PR never edits the version. It adds one note under changes/ named <short-name>.<patch|minor|major>.md; release-note.yml checks it with bump_version.py --check-pr. After the merge, stamp-version.yml runs bump_version.py --commit: each pending note becomes its own release (oldest merge first), bumping src/planetgen/_version.py, the README **Version:** badge and CHANGELOG.md together, and the bot pushes Release x.y.z to main. test_version_sync.py checks the three stay in step. Servers pick the release up on their next update.sh.
