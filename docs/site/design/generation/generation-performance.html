Status: reference (measured at release 8.0.1930 for PERF.146; the numbers are repeatable with planetgen benchmark --suite).

The earlier generation-performance-study.md profiled three phases on a scaled-down galaxy. This note covers every generation step of a whole galaxy, from the plan to the cache warm-up, at four galaxy sizes, with the suite that measures them, the fixes that came out of the first round, and a ranked list of what is left.

How to run it

planetgen benchmark --suite --size small --workers 3 --step-timeout 90 --output suite.json

It builds a scratch galaxy (planetgen_suite_*, dropped at the end), runs each step as its own child command, and measures the child's wall time, the machine's CPU (from /proc/stat, less the database and Redis servers), the MySQL server's CPU, the peak memory of the planetgen processes, the MySQL counters (questions, rows read, inserted and updated), the stages the step reports, and what it made, so the time per star or per cell can be read off. --repeats N runs the whole suite N times and prints the fastest, median and slowest run of each step. --steps a,b runs only some (a step needs the ones before it to have run). --step-timeout MINUTES stops a step that runs away and records it as not finished. docs/reference/cli.md has the options. A test (src/tests/test_benchmark_suite.py) runs the first step on the tiny size and checks the JSON's shape.

The sizes grow by the galaxy's mass (--mass): tiny 2e6, small 3e7, medium 4e9 (the size a seed draws), large 5e10 solar masses. Even tiny is not tiny: the galaxy's 157 globular clusters and 11 satellites exist at every mass, and the 6.4e9 systems of the satellites make millions of phenomena and hundreds of thousands of band stars whatever the galaxy's mass. The tiny size is for checking that the suite runs, not for timing.

The numbers below are from a 4-CPU machine with a 128 MB InnoDB buffer pool, MySQL 8.0.46, three workers. They are about the shape, not the seconds: another box will differ, and the run-to-run spread of one step is 4% to 15%.

The profile recipe

py-spy (pip install py-spy; it is not a project requirement) attaches to a running worker; the horses the worker forks are its children, so --subprocesses follows each unit:

W=$(pgrep -f 'planetgen.cli.worker' | head -1)
py-spy record --pid "$W" --subprocesses --duration 60 --format raw -o worker.raw

The supervisor (the planetgen scatter ... process) is the one that expands units serially; profile it with --pid alone. The raw output is stack count lines; summing the counts by frame, once as inclusive (every frame of the stack) and once as self (the last frame), gives the tables used here. Profile a step only while nothing else runs, and read the step's steady state, not its first minute (a worker warms its caches before its first fork).

What the first round fixed

All of these leave every drawn value as it was (the generator epoch is untouched); each has a test that compares the new path with the old one bit for bit.

Fix Before After
A queue worker builds the galaxy's component field and the sampling tables once, before it forks a job. The horse is a fresh process per unit, so each unit was rebuilding the field from about 22,000 stored clusters and satellites. massive-star scatter at the default size over 2 hours (stopped) about 3 minutes
The mean system mass at an age (mean_system_mass_at_age_solar) works out the remnant states and the turn-off mass once, and the lifetime terms once per metallicity. 1.0 4.4 times faster
The scatter's band tiers are looked up together: one pass over the density arrays for every place a component's stars land in, and one for the marked cells of a shell, instead of one band at a time. The longitudes use Python's math trig, so the floats are the loop's own. 86% of a bright-star unit the bright-star step 5.2 min to 2.8 min at small
The giant branch's metallicity terms (a27 .. a32, b9 .. b13) are worked out once per metallicity. 0.36 s per 20,000 branches 0.07 s

Whole small suite: 30.4 minutes with the first two fixes, 25.7 with all four. The spread of one run is 4% to 15%, so smaller differences are not shown by one run.

Ranked: what to speed up next

Each cost's share is of the small run above. "Value-neutral" means the drawn values stay as they are; a change that alters a drawn value needs its own item, a generator epoch bump and Boss's word, and goes to a later version.

  1. Warm the caches, 31% and it fails. (a) The deep-tiles phase builds 1,044 tiles in 320 s and reads 95.9 million rows doing it (the whole step, about 92,000 rows a tile): a tile reads far more than it draws. (b) The search check (/search) answers 202 (the page is slow enough to be queued as a job, see slow-page-answers.md) on a galaxy of 3.1 million phenomena, and the warm-up counts a 202 as a failure, so the step stops after its fourth phase. Either the warm-up should wait for the job or the search should not need one. Value-neutral. A bug and a cost, filed as both.
  2. The band scatter, 20%. Steady state, per unit: about 53% drawing each star's member tree (scatter_companions.star_trees into multistar.place, the stability checks), about 19% writing it (executemany), the rest drawing the stars. The tree draw is the generator itself, so a change to it changes values; the writes are not: the step makes 348,000 UPDATE statements (one per row) that could be batched, and the row writes could go in larger groups. The batching is value-neutral; its saving is not measured.
  3. The phenomenon scatter, 17%, for 3.1 million rows in a 3e7 galaxy. 3.3 million rows written, 234 s of server CPU (the database is the cost, not the Python). Ideas: larger insert batches, fewer secondary indexes while the rows go in (add them after), and the question of why a dwarf galaxy holds 3.1 million phenomena (the satellites' 6.4e9 systems at every galaxy mass: a modelling question, not a speed one).
  4. The scatter supervisors, 8% + 11%. The massive and bright-star steps use 1.3 and 1.7 of the machine's 4 cores: the supervisor expands the 65,536 shells serially, so the workers idle. Value-neutral; expanding in the workers or in larger groups would use the cores.
  5. Fill the map luminosity, 5%. 3.1 million single-row updates and 6.2 million rows read, 162 s of server CPU against 45 s of client CPU. One set-based UPDATE ... JOIN per block would do it. Value-neutral.
  6. Tier lookups in the far-reach scatter (bright_stars._reach_spots) still ask tier_at per candidate; the component pass was batched in this round. Small at small, grows with the reach.
  7. The nebula field, 2.6%, for about 1,400 clouds (30 ms each), and clear-scatter --nebula-field (11 to 15 s): both small; the suite runs the clear untimed.
  8. The plan, 1.2% (18 s): the field build and storing the 22,000 components. Fine at this size; check at large.
  9. The fill, 3% at 7.7 seconds a system: too few systems at this size to say anything; the fill needs a size of its own to be measured (the next version of the suite should fill a fixed count of sectors).

The plan stage at the default size (PERF.163)

Boss's plan of a default galaxy (4e9 solar masses, 22,267 clusters and satellites, 1,089 shells) took 264 s against a 3.7 s skeleton at release 8.0.1961. The plan log now ends with a table of where the unit's time went (util/step_timer.py), costliest first. On the 4-CPU test box, release 8.0.1960 (before PERF.146) took about 2 minutes for the whole plan command, the release after PERF.146 about 30 s, and the release with this table about 25 s (three runs each, on a machine that is not Boss's, so the seconds differ and the ratios are the finding). The table of the last run, 12.3 s of the unit:

Step Seconds Share
The component field (the mean system mass of each of 22,267 clusters and satellites) 4.5 36.7%
Storing the clusters and satellites (22,267 rows) 3.1 25.3%
Storing the 1,089 shells 1.1 8.8%
The report lines (pins, halo, outline) 1.0 8.4%
The young open clusters (22,099 drawn) 0.7 5.6%
The outline (the skeleton's shells; the "3.7 s" of Boss's log) 0.7 5.6%
The galaxy's shape 0.6 5.1%
The globular clusters, the satellites, the rest 0.5 4%

The rest of the 25 s is outside the unit: the command's start-up and argument checks (about 3 s, 0.6 s of it plan_shape run once for the check and once for the unit), the start-up math check (2 s), and starting the queue and its workers (about 6 s).

What was wrong: the cache of mean_system_mass_at_age_solar held 512 ages while a plan asks for 22,267 distinct ones (every open cluster rounds to its own age), so the log line that prints the clusters' system counts paid the whole bill a second time (4.4 s here, about 3 times that on Boss's box). It now holds 65,536 ages; the search for the mass of a given lifetime also reads the metallicity's terms once instead of once per bisection step. Neither changes a value (tests compare with the plain loop bit for bit). Together with the 4.4 times faster mean system mass from PERF.146 this brings the plan to about a fifth of its time at 8.0.1960.

What is left, ranked: (1) the mean system mass of each age costs 0.2 ms, mostly the 50-step bisection for the turn-off mass (youngest_progenitor_sol): a table of the turn-off mass by age, or a root finder with fewer steps, would change the last bits of the answer, so it needs its own item and a generator epoch; (2) storing the 22,267 components takes 3 s, about 0.14 ms a row; (3) the plan's start (the plan_shape check run twice, the math check, the queue's workers) is about 10 s of the 25 s. GEN.624 will cut the satellites' systems; the component field's cost depends on the number of components, not their size, so it will not shrink.

The plan's start and its storing (PERF.165)

PERF.163 left three suspects: the 22,267-row component insert, plan_shape run twice, and the 2.5 s start-up math check. Measured on the 4-CPU test box (plan --mass 4e9, a machine with nothing else running):

  • The insert is MySQL's work, not the driver's. A profile of replace_galaxy_components puts 3.2 of 3.3 s in waiting for the server. The driver already writes multi-row statements with its values formatted in Python (PERF.82), so batching further gains nothing. The server cost is the stored cell_key expression, the three secondary indexes and the check constraints: a fresh table takes 2.5 s with every index, 1.6 s with two of them dropped, and an INSERT ... SELECT of the same rows inside the server 0.9 to 1.4 s. Dropping indexes is a DDL statement, which commits the open transaction, so the store (which promises not to commit) does not do it. The insert stays as it is.
  • plan_shape twice costs under a second. The first call in a process is 0.57 s (the disc history and the cohort means fill their caches), the second 0.04 s. The check runs in the command and the unit in a worker process, so the unit pays the cold cost again, and sharing it would mean passing the shape between processes for about 0.6 s. Not done.
  • The math check (2.5 s, 60 checks) was the gate in front of every bulk generation (TEST.68). Making it skippable was a policy change, so it was filed as a question (PERF.170). Boss's answer (1:14 PM EDT 2026-10-23): no check before a generation; the check runs at every update (update.sh, which already did) and from the Admin page ("Check the math"). The gate in the command, the Generate page's first step and the Sector page's route are gone; check-math stays.

What was wasted was another read. The containers step (_store_containers) read every stored cluster back, 37,402 rows at this size (the 157 globular clusters and the young open clusters), to keep the 157 the containers are made from. It now asks the database for the King-profile clusters only (get_galaxy_components(..., profile=)). The containers are the same (a test builds them from both reads and compares). The table of the unit, before and after, two runs each:

Step Before After
Storing the containers 2.5 s and 3.1 s 1.4 s and 1.6 s
The unit in all 16.4 s and 18.5 s 12.4 s and 12.6 s

The unit's other rows moved with the machine's load between the runs (the component field 2.9 to 4.3 s), so only the containers row is the change; the rest of that drop is run-to-run noise. What remains in the containers step is the superbubble field (0.9 s, the gas tracer of 2,209 columns).

The plan's report lines (PERF.169)

The "report lines" row of the plan's table (the pins, the halo, the outline's crest, share and sector counts) read 3.5 s of a 12.4 s unit in one run and 1.1 to 1.7 s in the others on the same box, so most of it was cold caches, not arithmetic. Two things are in it. The outline's figures integrate the model's density over a 240 x 240 x 24 grid, and they did it twice: once for the planned share and again, with the same shape, energy and radius, for the sectors that expect a system. They now integrate once and hand the figures to the second (plan_figures.reaching_sectors(..., figures=)); the share and the sector count are the same to the last bit (a test compares them), and the step's warm cost goes from 0.4 s to 0.18 s. The other part is the first count of the candidate sectors, which adds up the wedges of every band of all 1,386 shells (533,000 _wedges_at calls, 0.65 s). It is cached for the storing of the shells that follows, so it is paid once, but it grows with the square of the shell count: an inlined sum is twice as fast and gives the same totals for shells 2 to 1,500, and it is the next step if the large galaxy's plan shows it. It duplicates the wedge rule, so it is left until it matters.

The large galaxy's phenomenon scatter (PERF.167)

After GEN.624 and GEN.369 (release 8.0.2015, the satellites drawn from the halo) the large galaxy (5e10 solar masses, 9,407 components) holds 63.0 million phenomena, all but 25,000 of them stellar black holes of 14 to 20 solar masses, so the count is the galaxy's, not a fault of the scatter. At that release the step did not finish in the suite's 90 minutes: when it was stopped the table held all 63.0 million rows and all five secondary indexes, so it was in the last steps (the index build and the stamp). Three findings:

  • Drawing is nothing. A shell's rows are drawn at 3.8 us a row, and the companions and the statement text come to about 40 us. A worker's wall time per row is about 250 us; the rest is waiting on MySQL.
  • Two indexes were kept while the rows went in. The scatter dropped the address and class indexes (PERF.73) and kept the cell index (cell_key and the three position columns) and the due-time index. A row lands at a random place in each, so once they outgrow the buffer pool (128 MB here, the default) every insert reads pages. Over 4.2 million rows into the table, one connection, the writes took 266 s with them kept and 145 s without (4.3 s per 100,000 rows rising to 8.5 s, against a flat 3.4 s), and building both afterwards takes 22 s. The gap grows with the table.
  • Fix, value-neutral. Both are now dropped with the other two and built after the last row, one at a time (the cell index 13.5 s and the due-time index 8 s per 4.2 million rows, so about 5 minutes for the 63 million). The rows and their ids are those of before; only the indexes' building moves.

Result on the same large galaxy, same seed, same box, 3 workers: 72.7 minutes from start to finished, the indexes included, against over 90 minutes (stopped at the cap in its last steps). The write count fell from 13.9 million to 6.4 million InnoDB data writes for the same 66.7 million rows inserted. The galaxy's other steps are as in the table above. What is left is MySQL's work per row: the stored cell_key expression and the primary key, about 30 us a row with every secondary index off, which the three workers and the server share four cores for. The same trick would help the bright-star scatter (its due-time and cell indexes), not measured.

The warm-up, the member counts and the shell weights (PERF.156 to PERF.161, PERF.171)

Measured with planetgen benchmark --suite --size medium (4e9 solar masses, release 8.0.2039, 3 workers, one run) and on a kept galaxy of the same build (plan, the three scatters and the band run one by one into a database of their own).

  • The warm-up counted a loading page as a failed visit (PERF.156). A slow page (the search, the phenomena list) answers 202 with a progress bar while a queued job builds it (UX.118), and the warm-up's visitor, which wants the answer cached, took the 202 for a page that "did not answer" and stopped planetgen warm after its fourth phase. The warm-up is not a visitor: slow_route now builds in its own request when the app is the warm-up's (config.WARMUP), so the answer is cached when the unit ends. At medium the warm-up now reaches its fifth phase (it stopped in the fourth before, after 27.8 minutes at this size).
  • Two tile pieces read most of the rows (PERF.157). Over 83 sampled deep tiles of the medium galaxy the tile builder read 342,755 rows a tile, 22.4 million of the 28.4 million in the scattered points and 2.4 million in the bright stars; the rest are under 3,000. The scattered-points query listed a range of shells and read every band and wedge of them when the box reached more than 64 shells, and for a 256 pc tile at the centre the optimizer chose a scan of the whole 3.6 million row table. It now lists a range per shell with the bands the box reaches (up to 1,000 shells): the same rows, 1.6 million instead of 22.4 million. The bright-star piece chose between its two ways of reading (the luminosity index or the addresses) by the box's share of the disc's area, which says nothing about height: a 1 kpc box a kiloparsec above the plane looked like a share of the disc and was read by walking the whole population index, 380,000 rows to find 60 stars. It now chooses by the box's share of the outline's cells and longitudes, with the walk's real cost (its 16 arms of four lists' worth each). The estimate that decides whether a box is answered from the galaxy-wide sample is as it was. Over 237 sampled deep tiles: 79.5 million rows to 22.7 million and 125 s to 75 s; over all 329 built-level tiles 41.2 million to 27.7 million and 279 s to 142 s. The warm-up as a whole: 10.8 minutes in the suite before, 6.5 minutes after (3 workers). What changes in a tile. The tile builder stops a piece that runs past 3 seconds and serves the tile marked incomplete; of 660 sampled tiles 58 lost their bright stars that way before, 1 after (the time limit makes this vary with the machine's load). Of the tiles that did not time out, 6 in 660 list a different set of cut-band stars: the two ways of reading hand the thinning (_even_pick, MAP.251) different candidate pools, so a tile whose choice moves can pick other, equally valid, stars of its cut band. Everything else in every tile is as it was.
  • The band scatter's 592,000 single-row UPDATEs (PERF.158). Each scattered multi-star system's member_count and system_mass_solar were set one row at a time (165 s of server time over the step, 592,313 statements at medium). They are one UPDATE ... JOIN (VALUES ROW(...), ...) for the batch now (453 statements, 25 s). The band step 617 s to 536 s; the values are the same bits (a test sets a row both ways and compares). The massive and luminosity scatters write the same way: 39,684 and 20,666 single-row updates before.
  • The map-luminosity fill (PERF.160) was already set-based. Its 40 statements each update an id block (MAP_LUMINOSITY_BATCH_IDS); the 3.6 million rows the step "updates" are the suite emptying the column before the step (Pipeline.prepare), as a fill after the column's migration would find it. A scatter writes the value with the row. Nothing to batch.
  • The scatters weighed their shells in one process (PERF.159). --mass and --luminosity cut their work by weighing every shell of the outline (brightStars.shell_weight samples the density at a few dozen places, about 10 ms a shell, 2,607 shells at medium) before the first unit started, 21 to 40 s a pass in the supervisor with the workers idle. The shells go to up to 8 forked processes in runs now (run_plan._shell_weights; fewer than 64 shells, one CPU or no fork stay in the process). Each shell is the same call on the same numbers wherever it runs, so the weights and the units are those of the loop (a test compares them; the medium galaxy gives identical units). The expansion takes 11 s on 4 cores.
  • _reach_spots calls tier_at per candidate (PERF.161): measured, left as it is. Over the 25 units that draw beyond the outline at medium (3,154 shell runs, 21.0 s of CPU in all) tier_at is 5.2 s, about 0.5 ms a call because every call is a cache miss (1,973 of 2,285 in one unit) that probes the band's densities on its own. The component pass could batch its places because it knows them all first. A reach candidate's place comes from four draws of the stream, and the draws after it (the keep test, the population pick) are made only for the candidates that pass, so the next candidate's place depends on the last one's outcome: the places cannot be listed ahead without changing the stream (an epoch), and a per-call memo never hits. The saving possible is under 5 s of CPU spread over the workers; no code was changed.
  • The bright-star scatter's indexes (PERF.171): dropping them while the rows go in does not pay at medium. The band step (804,795 rows added, 3 workers, one run each, table 451 MB against a 128 MB buffer pool): 525 s with the indexes kept, 508 s with the five secondary indexes dropped (the cluster index stays: a foreign key needs it) plus 16 s to build them again, 524 s. The luminosity pass (26,291 rows) is no different. Nothing was changed. The phenomenon scatter gained at 4.2 million rows and up (PERF.167); this table is 0.9 million rows at medium, so a larger size may differ and was not measured.
  • Seen, not fixed here: every unit's connection runs the schema check (GET_LOCK, the CREATE TABLE IF NOT EXISTS list and CREATE OR REPLACE VIEW), 861 times over the band step, about 130 s of server time. The suite's --keep is accepted but the scratch databases are dropped on success (so a kept galaxy has to be built command by command, as here).

Storing the galaxy shape (PERF.176)

Boss's plan log showed "storing the shape" as 19.99 s of a 38.63 s plan (51.8 percent). save_galaxy_shape writes one row; what took the time is the generator battery's digest, which a plan with a new seed records with the galaxy (DB.6, OPS.58): generator_battery.running_digest(), seven canned cases, no database, 9.0 s on the 4-CPU test box under load (about 5 s idle), paid in the middle of the store. A plan on a free box spent 8.25 s of 15.27 s there (54 percent), the rest being the component field (1.5 s), the report lines (1.0 s), the shape (0.9 s), the containers (0.8 s) and the clusters and satellites (0.7 s).

The battery uses nothing of the process that runs it, so the plan starts it in a process of its own as soon as the seed is settled (generator_battery.start_running_digest, a spawn process) and waits for the result just before the store, when it has run for the whole of the plan's other work. The plan then spent 0.65 s waiting and 0.01 s storing, the digest the same one (a test compares it with the one made in-process). A plan that keeps its stored seed starts nothing. If the process cannot be had the digest is worked out where it is asked for, as before. No stored value changes, so no generator epoch. The steps after it (the component field, the clusters and satellites, the containers) are 1 to 3 s each and were left as they are.

The link and settle stages in units (PERF.113, PERF.114, PERF.115)

Measured on the kept medium galaxy with planetgen galaxy --shell 100 --limit 100 --population (100 sectors, 3,370 systems, 25,550 sector paths, 3 workers, one run each, release 8.0.2070):

Stage Seconds Per sector One unit before?
Generate the sectors 324.6 3.2 s no, a unit per run of sectors
Link the neighbours 7.0 70 ms yes (link-neighbors), cut into chunks by PERF.113
Backfill 7.0 3.5 ms (2,018 sectors) no
Population 0.2 yes, but it had no species to name here
Settle the sector paths 18.2 182 ms yes (settle-sector-paths)

settle is the stage that grows with a run: one process settling every sector in turn, a minute at 330 sectors and the 5-minute unit ceiling (PERF.155) at about 1,650. It is cut into static chunks of SETTLE_UNIT_SECTORS (100) sectors now (run_galaxy.expand_save_sector_paths): the sectors to settle (the run's and those around them) are found once in the expansion, in order, and each unit saves its chunk's paths with expand=False. A path depends only on the final point masses of the sectors around its own and is written with its own sector, so the chunks cannot collide; the same settle on the 100 sectors gave the same 51,100 knot rows (a checksum of the stored rows before and after) with the stage at 11 s instead of 18 s on 3 workers. A stage of at most 100 sectors stays one unit and keeps its --workers for a crowded sector's bodies (PERF.80); a longer one gives each unit one process.

The link (PERF.113) is cut the same way, into chunks of LINK_UNIT_SECTORS (500, about 35 s) sectors in neighbourhood order (store.link_order), each unit linking its chunk with the run's other sectors as skip. Linking is serial by design: every batch of 20 sectors holds the neighbour lock (store.link_sector_neighbors), so units take turns and the cut bounds a unit's length, it does not shorten the stage (15 units of 7 sectors took 17 s against 7 s as one unit; at 500 sectors the overhead is a few seconds in 35). The stored links are the same whichever order the units run: a sector's lists are computed whole from the placed systems, and a system merged into the lists around it is the same whichever batch merges it. Checked on the 100 sectors: all 76,749 nearest_systems rows deleted and linked again in units, the checksum of the rows is the one before.

The population pass (PERF.114) took 0.2 s here because the sample has no species to name (0 new species); it stays one inline stage and is to be measured again when generation produces species.

The fill of the map luminosity (PERF.117) and the habitability re-score (PERF.116) are already a unit per run of ids (fill-map-luminosity, rescore-habitability), as PERF.160 found.

What medium and large show (PERF.164)

Same 4-CPU box, three workers, release 8.0.1973, seed ...BEEF, one run each. The container restarted during the medium run, so it ran in three pieces over the same scratch databases (--resume); the steps that were run twice differ by 10% to 30% between the two runs (the plan 29 s and 35 s, the band scatter 10.5 and 14.3 min), which is the spread to read these by. The medium numbers below are from the complete pass of each step.

A galaxy 130 times heavier (small to medium) takes under 3 times as long: the cost is the count of things drawn (components, shells, phenomena), and the clusters and satellites exist at every mass. Medium to large (12 times the mass) adds 11% to 48% to the first three steps (the plan 29 to 43 s, the massive stars 3.6 to 4.0 min, the bright stars 8.8 to 11.2 min). The per-star times therefore do not carry from one size to another: the massive-star scatter costs 4.95 ms a star at small and 3.1 ms at medium, the band 0.64 ms and 0.79 ms. A real default-size run is the medium column; its steps in a real run are the same commands, so these times are what a real run takes on this box, plus the whole sector fill (the benchmark fills only 6 or 12 sectors).

The warm-up is the largest single cost at both sizes and still fails: at medium its deep-tiles phase builds 1,665 tiles in 948 s, and the /search check answers 202 again (see the ranked list, item 1). At large the phenomenon scatter was still running when the 60-minute cap stopped it, with 66.0 million rows stored (ten times the medium galaxy's 6.7 million by the time it was stopped, and not done), so the steps after it were not run: the large galaxy's run is at least 1.3 hours on this box (16 minutes for the first three steps, then the phenomena), with the phenomena the first thing to speed up (ranked list, item 3). The cap is the suite's --step-timeout, 240 minutes by default; the run used 60.

The unit-length ceiling (PERF.155)

No unit of a stage is expected to run longer than queue.unit_ceiling_seconds (default 300, 5 minutes) unless the stage is one unit by nature. The ceiling bounds how long a worker keeps its place when a lane that needs it asks for it (the lend rule of PERF.150) and how long a cancel waits for a running unit. It is held three ways:

  • Every queued command in queue/commands.py is either whole=True (the stage is one unit: the skeleton plan, the clear of a scatter, one system, the cache-warm families, the database checks) or declares unit_seconds, the seconds its longest unit runs at the default galaxy size. test_unit_ceiling.py fails for a command that is neither, and for one whose figure is over the setting's default.
  • The run record keeps the longest unit of every stage (longest_unit in the stage hash, set by runrecord.unit_done). When a stage ends, wrapper.finish_stage writes a warning to the run's log (kind unit.long) if that unit ran longer than the setting, naming the stage and how many units it was cut into. That check is the one that holds at any galaxy size: a stage cut into units of a fixed size has longer units when something in each unit grows.
  • The splits themselves are PERF.113 to PERF.117, PERF.159 and PERF.115; this item adds no new split.
