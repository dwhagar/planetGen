This guide takes you from nothing to a running planetGen site with a generated galaxy, on Linux or macOS. It covers the install scripts, where the example configs live, and what to do after the first install. For what planetGen is and how to use it, see the README.

The whole path at a glance

  1. Check the requirements.
  2. Get the code as a git checkout.
  3. Create the MySQL database and account.
  4. Write config.json.
  5. Run the installer for your platform.
  6. Set up the web server from the example config.
  7. Turn on HTTPS and change the admin login.
  8. Generate the galaxy.
  9. Check the server.
  10. Keep it up to date.

Do not install planetGen with pip install .. The installers put its libraries in a virtual environment (/usr/local/planetgen/venv) built from a hash-checked lock file, where the web server can use them and the system Python stays untouched. They then install the checkout itself as an editable package (pip install -e), so the site and the command line run the checkout's code and a git pull takes effect without a reinstall.

Swap

Turn swap on before you generate anything. A host with none (many cloud servers ship that way) has nothing to absorb a burst of memory, and the kernel then kills whichever big process it finds first, usually MySQL; with swap the server slows down instead. One command makes an 8 GB swap file, switches it on and adds it to /etc/fstab so it stays on after a reboot (it does nothing when swap is already on):

sudo scripts/enable-swap.sh            # 8 GB at /swapfile
sudo scripts/enable-swap.sh 16G        # another size
sudo scripts/enable-swap.sh 8G /mnt/disk/swapfile   # another place, when the system disk is small

swapon --show and free -m show the result. install.sh and update.sh warn when the host has no swap.

Memory guards

Some hosts run a memory guard (earlyoom, systemd-oomd, nohang) that ends the biggest process with SIGTERM when free memory runs low, before the kernel's own killer ends it with SIGKILL. A planetGen work unit (the warm-up, a generate run) is often the biggest process, and a unit ended this way fails with status 15. install.sh and update.sh say when one is running, and a warm-up that fails prints what the kernel and the guards logged meanwhile. Every ended work process is also written, with its signal, unit and run, to error.log in the log folder (/var/log/planetgen/error.log), so the cause is on record. What to do about it, in this order: keep swap on (above), because a guard acts when swap is nearly used up as well as memory; give the guard something to protect, for example earlyoom started with --avoid '(^|/)(mysqld|redis-server|apache2|httpd)$' so it picks a work unit before the database, the queue or the web server; and, if the host is small, lower queue.max_host_workers in config.json (0 sizes it from memory; see docs/reference/config.md) so fewer units run at once.

On a 16 GB host that also generates, innodb_buffer_pool_size = 4G in /etc/mysql/mysql.conf.d/mysqld.cnf keeps MySQL near 5 GB at most and leaves the rest to the workers (about 250 MB each, up to the worker count on the Generate page) and the web app.

On a machine that runs the whole test gate (scripts/test.py full, many tests writing in parallel), raise innodb_redo_log_capacity from its 100 MB default to 2 GB in the same file (innodb_redo_log_capacity = 2G, or at run time SET GLOBAL innodb_redo_log_capacity = 2147483648;, which MySQL 8.0.30 and later accept without a restart). At the default the log checkpointer falls behind under that load (log_checkpointer lagging in the MySQL error log, 84 warnings in one gate), the gate slows, and tests can lose their connection. A galaxy run does the same: the redo log must hold the writes of its busiest half hour or the checkpointer lags (MY-014084 in the error log).

Ubuntu 24.04 and 26.04 LTS

Both releases are supported, with Ubuntu's own packages. One line installs everything the installers expect to find (they add mod_wsgi and Redis themselves when missing, but not MySQL or Apache):

sudo apt update
sudo apt install git python3 python3-venv mysql-server apache2 libapache2-mod-wsgi-py3 redis-server

Leave out mysql-server when MySQL runs on another machine. What each release ships:

Ubuntu 24.04 LTS Ubuntu 26.04 LTS
Python (the venv is made from it) 3.12 3.14
MySQL 8.0 8.4
Apache / mod_wsgi 2.4.58 / 5.0.0 (Python 3.12) 2.4.66 / 5.0.2 (Python 3.14)
Redis 7.0 8.0
  • MySQL 8.4 does not load mysql_native_password. The account in step 2 uses the default login (caching_sha2_password), which both versions support; do not add IDENTIFIED WITH mysql_native_password.
  • mod_wsgi and the venv must be the same Python. The installers make the venv from the system python3, which is what Ubuntu builds mod_wsgi for, so they match; update.sh warns when they do not.
  • Upgrading from 24.04 to 26.04 in place: run sudo ./update.sh after the upgrade. The old venv's Python (3.12) is gone, so update.sh makes the venv again from the new python3 (3.14) and reinstalls the locked libraries; nothing else changes. Check that apache2ctl configtest passes and that your vhost still has python-home=/usr/local/planetgen/venv.

1. Get the code

Clone the repository where the site will run from. The guides use /var/lib/planetGen:

sudo git clone https://github.com/dwhagar/planetGen.git /var/lib/planetGen
cd /var/lib/planetGen

Keep it a git checkout: the update scripts update it by fetching and resetting to the tracked branch.

On macOS, install the Homebrew packages first: brew install python@3.12 nginx mysql@8.4 redis (then brew services start redis).

2. Create the database and account

planetGen uses one MySQL account for everything: the generator, the migrations and the website. It creates its own tables and a second control schema (planetgen_control: admin logins, sessions, API keys, audit log), so it needs full rights on every planetgen% schema:

CREATE DATABASE planetgen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'planetgen'@'localhost' IDENTIFIED BY 'a long random password';
GRANT ALL PRIVILEGES ON `planetgen%`.* TO 'planetgen'@'localhost';

Use 'planetgen'@'%' (or the web host's address) when MySQL is on another machine. The admin Generate page's New galaxy and Reset actions empty the tables, so a less privileged web account still needs DROP. More in MySQL accounts.

3. Write config.json

sudo cp config.json.example config.json
sudo ${EDITOR:-nano} config.json

At minimum set:

  • mysql.host, mysql.user, mysql.password, mysql.database;
  • secret_key is optional: left empty, the update makes one and keeps it in the state folder (secret_key, mode 0600);
  • site_name and base_url for your site;
  • proxy_fix when a separate web server proxies to the app (nginx, Caddy, macOS): {"x_for": 1, "x_proto": 1, "x_host": 0} (why). Apache with mod_wsgi does not need it.

Every setting, and the PLANETGEN_* environment variable that overrides it, is in docs/reference/config.md. config.json is gitignored, so updates never overwrite it, and the installers make it readable only by administrators and the web server's account.

4. Run the installer

The installer prints the first admin password once, in a box, when it creates a new database. Write it down.

Linux (Debian or Ubuntu)

sudo ./install.sh

It runs eight steps and prints each one:

  1. Installs the Python libraries into planetGen's own virtual environment, /usr/local/planetgen/venv, from the hash-checked lock; the system Python is left alone (planetGen's own Python). It also adds a planetgen command in /usr/local/bin. The Apache vhost needs python-home=/usr/local/planetgen/venv on its WSGIDaemonProcess line (the example has it); update.sh checks that, the process group, application-group=%{GLOBAL} and that Apache's user can read the venv, and only warns (the rules).
  2. Creates or migrates the database schema, and prints the admin password on a new database.
  3. Fetches the NLTK words corpus into /usr/local/share/nltk_data.
  4. Makes the scripts executable.
  5. Installs mod_wsgi if needed and enables Apache's wsgi, headers and deflate modules.
  6. Locks down the code tree and config.json for Apache's account.
  7. Creates the Galaxy Map tile cache (/var/cache/planetgen/tiles) and the Generate jobs directory (/var/lib/planetGen/jobs).
  8. Creates the debug log (whether or not debug is on) and the activity log's folder, each with its logrotate config.

After the eight steps it checks that the web app imports as Apache's user, and checks the Redis server (below).

After step 3 it also offers to run the optional population pass (species, civilizations and territories: planetgen population, then planetgen territories; y/N, defaulting to N after 30 seconds). sudo POPULATION=1 ./install.sh runs it without asking, and those two commands run it any time later. A new galaxy has no worlds yet, so there is nothing for it to do on a first install.

The Redis check installs redis-server with apt and starts it when nothing answers at redis.url; then the installer checks its settings and prints a warning, with the exact line to add, for the append-only file, the memory policy and limit, and the bind address; copy the lines from examples/redis/planetgen.conf into your Redis config and restart Redis (it never edits that file; see deployment). It also warns while Redis lets anyone on the machine in without a password; the next section is the fix.

Give Redis a user and a password (new and existing installs)

A job on the work queue names a function that a planetGen worker runs, so any user on the machine who can reach a passwordless Redis can make a worker run planetGen code with arguments of their choosing. redis.url should therefore name a Redis user with a password, and the passwordless default user should be off. examples/redis/planetgen-acl.conf has the two lines; the installer cannot do this for you (it never edits your Redis config, and the password is yours to choose). Until it is done, install.sh and update.sh print "any user on this machine can use Redis without a password" with these same lines, and carry on.

Do it in this order, on a new install after install.sh has finished and on an existing install when nothing you care about is running (the restart in step 4 stops the runs and workers using Redis; queued jobs are kept because of the append-only file):

  1. Choose a password: openssl rand -hex 24 prints a good one.
  2. Copy the example next to your Redis config and put your password in place of A-LONG-RANDOM-PASSWORD in the user planetgen line (only there). Redis alone must read it: sudo cp examples/redis/planetgen-acl.conf /etc/redis/planetgen-acl.conf, then sudo chown redis:redis /etc/redis/planetgen-acl.conf and sudo chmod 600 /etc/redis/planetgen-acl.conf.
  3. End /etc/redis/redis.conf with the line include /etc/redis/planetgen-acl.conf (after the include of planetgen.conf, if you added one: later lines win). This is the file that switches the default user off.
  4. Put the same password in the URL planetGen uses, in config.json: "redis": {"url": "redis://planetgen:YOUR-PASSWORD@127.0.0.1:6379/0"} (or set PLANETGEN_REDIS_URL; a password with characters such as @ or / must be percent-encoded, which is why a hex password is the easy choice). config.json lives in the state folder with mode 640 (the web user and its group), so other users cannot read the password, as with the database password it already holds; edit the linked file with sudo.
  5. Restart Redis and the web server: sudo systemctl restart redis-server && sudo systemctl restart apache2.
  6. Check it: redis-cli ping now answers NOAUTH Authentication required. (the passwordless user is off), and redis-cli --user planetgen --pass YOUR-PASSWORD ping answers PONG. Then sudo ./update.sh prints "Redis: answering at ..." and no longer warns about the password; any other line it prints about Redis is one of the settings of planetgen.conf and has the line to add.

To go back, remove the include line from redis.conf, put the plain redis://127.0.0.1:6379/0 URL back and restart both services. update.sh keeps printing the warning until this is done; it does not stop the update. The user may do everything planetGen does and none of the dangerous commands (FLUSHALL, KEYS, CONFIG SET, SHUTDOWN, ACL and the like): for those, edit the Redis config and restart Redis, as above.

sudo ./install.sh --skip-database leaves out step 2 and the population question when the database isn't ready yet; run sudo ./update.sh once it is. The installer never writes the web server's site file; it prints what to do next.

macOS

sudo /var/lib/planetGen/install.sh

The same script as on Linux (the virtual environment at /usr/local/planetgen/venv is made from Homebrew's python3), with macOS's own pieces: _www ownership, newsyslog for the debug log, and gunicorn installed and started as a launchd daemon on 127.0.0.1:8000, plus the planetgen command. nginx stays yours (next step). See the macOS guide.

5. Set up the web server

Each platform has a guide and example files. Copy the example, set the host name, check the paths, and enable it.

Apache on Linux (the reference setup):

sudo cp examples/apache/planetgen.conf.example /etc/apache2/sites-available/planetgen.conf
sudo ${EDITOR:-nano} /etc/apache2/sites-available/planetgen.conf   # set ServerName
sudo a2ensite planetgen
sudo systemctl reload apache2

nginx on macOS: copy examples/macos/planetgen-nginx.conf to $(brew --prefix)/etc/nginx/servers/planetgen.conf, set server_name and the certificate paths, put user _www _www; at the top of nginx.conf, then sudo nginx -t && sudo brew services start nginx.

6. HTTPS and the first admin login

The admin pages only work over HTTPS. With Apache, sudo certbot --apache; each guide says how for its server.

Then open https://<your site>/login and sign in as admin with the password the installer printed. You are sent to /account to choose your own username and password; the other admin pages stay locked until you do. Lost the password? See Resetting the admin login.

7. Generate the galaxy

A new site has an empty galaxy. Use the browser or the command line.

In the browser: as an admin, open Generate (/admin/generate) and choose New galaxy. It plans the galaxy's shape, places its bright stars (shown as their own step with a progress bar), and generates a first neighborhood around a random start, as a background job you can watch and cancel. Generate sectors adds more later, and so do the Generate buttons on the Galaxy Map and Sector Map.

On the command line, from the checkout:

planetgen plan                  # the galaxy's shape; once, before anything else
planetgen scatter --mass        # every star of the mass limit or more, placed across the whole galaxy
planetgen scatter --luminosity  # the lighter stars bright enough to see from afar
planetgen scatter --phenomena   # the neutron stars, black holes and the rest
planetgen galaxy                # a random start and every sector within 100 ly of it

The installer adds the planetgen command.

The scatters take a while and need space. The two star scatters place every star of 500 solar luminosities or more across the whole galaxy, about 60 million stars and 10 GB in the database, before any sector is filled, so the Galaxy Map shows the spiral arms from the start: roughly 20 minutes of drawing plus the database load. For a quick test galaxy, raise the threshold (planetgen scatter --mass --bright-star-min-luminosity 5000) or leave the scatters out and run them later on the stored plan. Going the other way, --bright-star-min-luminosity 100 places about 220 million (about 35 GB).

Then browse the Galaxy Map, the sectors and the systems on the site. See Usage for the other commands.

8. Check the server

Run the server checklist: it confirms the code, schema, indexes, web server config, cache and permissions are all right, with commands for each platform.

Keeping it up to date

sudo ./update.sh

It pulls the latest code (a git reset --hard to the tracked branch; config.json and other untracked files are kept), checks the Python libraries and installs only a missing or too-old one, checks the NLTK corpus, runs the generator's math check (a failure only warns, and bulk generation refuses to start until it passes), migrates the database and records the version key, re-applies folders, permissions and the logs, checks that the site imports, and checks Redis as the installer does. It never reinstalls what is already there. Last, it builds the site's caches (planetgen warm: the Galaxy Map's opening view, the lists, the sector, system and phenomenon pages and the search, each its own command run in order, in two stages, each with a time limit of 4 hours, WARM_STAGE_SECONDS), so the first visit after an update is fast. Each warm-up leaves its record in warmup.log in the log folder, in local time with its zone.

When the update includes a schema migration, it first asks whether to delete the galaxy data instead (y/N, defaulting to N after 30 seconds; admin logins are kept either way). Answer y when the release notes say to regenerate, then generate the galaxy again (step 7). The update never runs the population pass; run planetgen population by hand when wanted. On Linux, update.sh reloads Apache itself when Apache is running (and restarts it when it just enabled a module); only if Apache is not running, or with nginx or Caddy in front of gunicorn, does it print the command to run. On macOS it prints the SIGHUP to send to gunicorn.

sudo ./update.sh --kill-all first does a full stop (planetgen queue stop-all --no-hold, the same routine as Stop everything on the admin Queue page): it cancels every run and job, empties the queues and ends every planetgen worker and command process, including ones nothing lists any more. It only does so when you give it; without it the update stops only the work it lists, and refuses while other work runs unless you answer y or add --yes. To stop everything and keep it stopped, use sudo planetgen queue stop-all (or the Queue page) and planetgen queue resume when you are ready.

Do not use a plain git pull: it skips the migration and can drop the scripts' executable bits.

The Update button (Linux)

The admin pages can start update.sh without anyone holding a root shell (SEC.43). The web server's user only creates an empty file, update.request, in the state folder. The root-owned unit planetgen-update.path sees it and starts planetgen-update.service, which deletes the request and runs update.sh as root. The file is never read and the command has no argument, so a request can do nothing except run the update. A press made while an update runs waits for it and runs after it; the update guard decides whether running work is canceled or the update refuses. install.sh and update.sh install and enable both units with this checkout's path and state folder (the same step installs the maintenance timers below); install-maintenance-timer.sh --skip-update-button leaves the path unit out. The Owner presses it on the admin Update page (/admin/update, after typing the password again; the page shows the state and the end of update.log and reloads itself while an update runs). Progress is in update.log in the log folder and journalctl -u planetgen-update.service. If a request file cannot be removed, the service stops after ten tries in ten minutes; clear it with sudo systemctl reset-failed planetgen-update.service.

Scheduled maintenance

On Linux with systemd, install.sh and update.sh install the timers themselves (OPS.110) and enable the monthly orbit update (planetgen.cli.orbits, at 03:30 on the 1st) and the nightly tile rebuild below. The unattended monthly update (at 03:00) is installed but left off, because it deploys whatever is on the tracked branch with no review; every deploy says how to turn it on while it is off: sudo systemctl enable --now planetgen-update.timer. Every unit file is rendered for the checkout the script runs from and the virtual environment (PLANETGEN_VENV, default /usr/local/planetgen/venv), so the installed copies name the real paths; a path with a space or a special character is refused. A unit that differs from the rendered one (an older copy, or another install location) is replaced, and the log says so. A deploy enables only a unit it installs for the first time, so a timer you disable stays disabled. Run the installer by hand to choose the databases or leave a timer out; on macOS it is the only way to get the launchd daemons:

sudo examples/maintenance/install-maintenance-timer.sh                      # Linux (systemd) and macOS (launchd); this one also turns the update timer on
sudo examples/maintenance/install-maintenance-timer.sh --skip-update-timer  # orbits only

The gunicorn unit of an nginx or Caddy host is the exception: copy it by hand and edit its two paths (the checkout and the virtual environment; nginx.md).

An unattended update deploys whatever is on the tracked branch with no review, and keeps the data when a migration is pending.

On Linux the installer also sets up the nightly rebuild of the whole Galaxy Map tile cache (PERF.233, planetgen.cli.tiles, at 05:00, after the orbit update); --skip-tiles-timer leaves it out. It builds every node of every level into a new cache beside the live one and swaps it in when it is complete, so visitors never meet an empty cache and a run that is killed leaves the old cache serving; then planetgen warm rebuilds the lists, objects and search. The disk needs room for both caches while it runs: the run refuses to start unless twice the projected size is free, and says the figures (about 80 KB a generated sector and 30 KB a block; reports/perf233-tile-cache-cost-2026-11-04.md). Run it by hand, as the web server's user, with python3 -m planetgen.cli.tiles.

Nightly memory smoke run

sudo examples/maintenance/install-maintenance-timer.sh --with-smoke-timer   # Linux (systemd)
python -m planetgen.cli.smoke                                               # once, by hand

It builds the Generate page's New galaxy job for a small neighborhood (12 pc) in scratch databases, runs every step, and watches the memory of MySQL, the planetgen workers, each step and the host while each one runs (a Memory peak: line after each step in every job log, and memory.json in the job folder). It exits 1 when a step peaked above a budget (tuning.SMOKE_BUDGET_MB; --budget mysql=2000 overrides one) and 2 when a step failed. Run it on a quiet host with a database account that may create and drop databases. The timer fires at 04:30 every night; the report is in journalctl -u planetgen-smoke.service.

Command line only

The generator does not need the website. Run the installer anyway (it sets up the libraries, database and NLTK corpus) and skip step 5. Then run planetgen, the command the installer adds.

Development setup

For working on planetGen itself, use a virtual environment and an editable install with the test extras:

python3 -m venv .venv
. .venv/bin/activate
pip install -e ".[test,api]"
scripts/test.py changed       # the tests your change touches; `full --check` runs everything
python3 src/html/wsgi.py      # the site at http://127.0.0.1:5000/

Set admin_cookie_insecure in config.json to log in over plain HTTP locally. Database tests need a MySQL server, and the work-queue tests need Redis (PLANETGEN_TEST_REDIS_URL); both skip without one. A machine that runs scripts/test.py full needs innodb_redo_log_capacity = 2G in MySQL (see Requirements), or the checkpointer lags and tests lose their connection. See docs/reference/testing.md.
