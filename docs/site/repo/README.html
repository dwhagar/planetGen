planetGen generates a galaxy: stars, star systems, planets, moons, asteroid belts and exotic phenomena, placed in a physically modeled spiral galaxy and saved to a MySQL database. A website on top of it lets you browse and search the galaxy, fly around it on 3D maps, and copy any system's write-up as Markdown. It was built for the Molten Aether FFRP game.

To install it, see INSTALL.md.

What it does today

  • Stars drawn as physics: a mass from the Kroupa initial mass function, an age from the galaxy's star-formation history, then how the star has evolved by now (main sequence, subgiant, giant, supergiant or white dwarf). The result matches the real galaxy: about three in four stars are M dwarfs and supergiants are about one in a million. A star can also be pinned to a type such as G2V.
  • Binary systems, both close (circumbinary) pairs and wide pairs where each star keeps its own planets. The two stars are born together, and orbits respect published stability limits.
  • Planets and moons from 25 planet classes, placed in physically plausible orbits and named from their system (Sol III, Sol IIIa). They follow their star's history: a very young star has only belts, and a giant has swallowed its inner planets.
  • Habitable worlds and life: which life chemistries a star supports, and a speculative evolutionary timeline for each living world.
  • A whole galaxy: a density model of a spiral galaxy, with young, old and bulge star populations, cut into 4 pc (13 ly) sectors on a grid of spherical shells, bands and wedges around a round core. Planning the galaxy also places every bright star (500 times the Sun's luminosity or more, about 60 million in a Milky Way) so the spiral arms exist from the start. Sectors are then filled a neighborhood at a time, where and when you need them, with star ages that follow where each sector sits.
  • Exotic phenomena at research-based interstellar rates: black holes, neutron stars, nebulae (classed A-Q, including planetary nebulae) and supernova remnants (R-W) with what fills them, rogue planets in four mass bins plus free-floating brown dwarfs, interstellar comets, and runaway and hypervelocity stars. Nebulae come with the stars that make them: H II regions around O and B stars, a white dwarf at the heart of each planetary nebula. Each object records the cloud it sits inside (which squeezes the heliosphere of systems within it), its sector octant and its three nearest systems. Every galaxy has a supermassive black hole at its center, or one time in ten an active quasar.
  • Facilities: starbases, stations, colonies and outposts on planets and moons, in orbit, in belts or in open space, placed by an admin from a system's page or through the API.
  • Population (optional, off by default): a pass that names the dominant species of worlds with complex life, dates civilizations and their eras, and gives each spacefaring species a polity whose territory claims the systems around it.
  • Time passes: a monthly update moves planets and moons along their orbits and every system and phenomenon along its galactic orbit, carrying anything that drifts into another sector over to it.
  • A website to browse it all: sector and system pages, faceted search, 3D maps of the galaxy and of each sector, a System Map that measures routes around planets and stars, a NAV page that plots courses between systems, a JSON API, and admin pages to generate the galaxy from the browser.

Requirements

  • Python 3.12 or later, with numba (the compiled numeric kernels; install.sh and update.sh install it, and there is no fallback without it). This replaced the old Python 3.9 minimum with numba (OPS.42).
  • MySQL 8.0.19+ (MariaDB is not supported).
  • Redis (any recent version): the Generate page's jobs, the work queue behind --workers above 1, the rate limits and the login lockouts run on it. install.sh and update.sh install and start it on Debian and Ubuntu and check its settings.
  • For the website, a web server: Apache2 with mod_wsgi on Debian or Ubuntu (the reference setup), nginx or Caddy on Linux, or nginx on macOS.
  • Install and update scripts: install.sh and update.sh on Linux and macOS.
  • Windows: see docs/deployment/WINDOWS.md.

INSTALL.md lists the full requirements and walks through the install.

External files

The generator reads a few large published data sets that are not in this repository (raw data sets are never committed). install.sh and update.sh download them once at setup, as root, with python3 -m planetgen.cli.datasets fetch; nothing downloads while the site or the generator runs. Each file is requested over https, must have the exact size and sha256 the catalogue (src/planetgen/datasets/catalogue.py) states, and is kept by an atomic rename. They go in the cache folder /var/cache/planetgen/datasets (one sub-folder per set below), or in the folder PLANETGEN_DATA_DIR names. The licence and citation of each set are in DATA-LICENSE.md.

  • Fetched at setup: every set listed below. Provided by hand: none; the program reads no other external file.
  • See where each stands: python3 -m planetgen.cli.datasets status fetches nothing, says which sets are present, prints the URL of every missing file, and exits 1 while one is missing. fetch prints one line per file with its URL and what happened to it (fetched, kept or failed with the reason), and update.sh and install.sh show those lines.
  • When a file is missing: a bulk run (galaxy, plan, population, sector with more than one sector, the Generate page's jobs and the Sector page's neighbourhood button) refuses to start, writes nothing, and names each missing set, why, every file with its URL and the setup command (python3 -m planetgen.cli.datasets fetch KEY). Unless it is told, in so many words, to disregard missing files (--disregard-missing-data on any subcommand, the "Disregard missing data files" box on the Generate page, or "disregard_missing_data": true in the neighbourhood request): it then starts, uses the labelled fallback listed under each set below, and prints the fallbacks in the run header. One system, one sector or one phenomenon is not gated.
  • Installing a set by hand (the host is down, or the machine has no network): download each URL listed under the set on a machine that can, check the file's size and sha256 against the catalogue entry, copy it into the folder <cache folder>/<set key>/ under the name shown, make the folder readable for the web server's user, and run python3 -m planetgen.cli.datasets fetch KEY: a file already there with the right size and sha256 is kept and not requested again (one that fails the check is requested again), and a set that is reduced to a smaller file (the "kept after setup" file) is reduced from it.

The list below is written from the catalogue by scripts/readme_external_files.py --write, and a test fails until it matches, so a new set cannot skip it.

Usage

The website

Once installed, the site's front page leads to:

  • Galaxy Map: the whole galaxy in 3D, with every bright star as a tiny point in a big soft glow and nebulae as translucent clouds. It opens on a drill-down: pick a slab of the galaxy, then a block, then smaller blocks down to single sectors, with a breadcrumb, keyboard keys, and a link for every stage so Back and Forward work. Type a sector, a shell/band/wedge address, coordinates or a name to fly there. A NAV course can be drawn on it, and once population has run, a Territories overlay shows who holds what. As an admin, click an empty sector to generate it, a neighborhood of a radius you choose, its column or its whole shell, or generate a whole small block or one of its layers.
  • Sectors and Systems: every generated sector and every system, 50 to a page. A sector has a 3D Sector Map (with the same Generate buttons for admins, and Nav from/to on any system) and a Contents list; a system has its stars, planets, moons and facilities, the cloud it sits in, its nearest systems, a System Map, and its write-up ready to copy as Markdown. Phenomena have pages too, with their class, what fills them, and a view that suits each one (a neutron star's spinning beams, a black hole's accretion disk).
  • Classes: a reference page for every kind of class the generator gives out: stars, planets, nebulae, asteroid fields and more.
  • Species and Polities (once the optional population pass has run): every species with its homeworld and era, and every polity with the systems it holds. They stay hidden until there is something to show.
  • NAV: a course and distance between any two systems or phenomena, picked from their pages, the Sector Map or the Galaxy Map, with "Show on Galaxy Map" to see it drawn there.
  • Search: filter by object type, star class, planet class, life chemistry, phenomenon and phenomenon class, or search by name from the box in every page header.
  • Admin (after logging in): Generate plans the galaxy and generates sectors as background jobs you can watch and cancel; Generate a one-off system makes a single system with every command-line option and never saves it; plus your account, API keys and server stats. Times show in your own time zone.

docs/reference/html-interface.md describes every page and docs/reference/api.md the JSON API.

The command line

planetgen.cli.generate, in the checkout, is the one entry point for every generator. On Linux and macOS the installer adds a planetgen command that runs it. Each subcommand saves what it makes to the database unless told otherwise:

planetgen plan         # plan the galaxy's shape (once, before galaxy)
planetgen scatter      # draw one scatter on the plan: --mass, --luminosity, --phenomena (before galaxy)
planetgen galaxy       # generate sectors in the galaxy
planetgen sector       # one or more standalone sectors
planetgen system       # one star system
planetgen phenomenon   # one exotic phenomenon
planetgen population   # optional: species, civilizations and polities
planetgen territories  # optional: which polity owns which system (after population)

Common examples:

# A random neighborhood: a random start and every sector within 100 ly of it
planetgen galaxy

# One whole shell, one band of it, or one sector (shell 12, the equatorial
# band, wedge 5)
planetgen galaxy --shell 12 --limit 500
planetgen galaxy --shell 12 --band 0
planetgen galaxy --shell 12 --band 0 --wedge 5

# A span of shells and bands (negative bands lie south of the plane)
planetgen galaxy --shells 10:12 --bands=-2:2 --limit 500

# A quick test galaxy: scatter fewer pre-placed bright stars
planetgen scatter --mass --bright-star-min-luminosity 5000
planetgen scatter --luminosity

# A single system with the odds of a habitable world raised (it may come out without one), printed as Markdown on request, not saved
planetgen system +habitable_world --format markdown --output -

# A system built from a specification file
planetgen system --system-file examples/systems/solar_system.json

Most options use a +name/-name form: +moons forces moons, -moons forbids them, and leaving it off leaves it to chance. planetgen <command> --help lists every option, and docs/reference/cli.md is the full reference, including the system specification file format and the incompatible option pairs.

Other tools

Each runs as python3 -m <module> from planetGen's own virtual environment (/usr/local/planetgen/venv/bin/python -m <module> on a server install.sh set up; a bare python3 there finds none of the libraries); --help shows its options:

  • planetgen.cli.orbits advances the galaxy by the time elapsed since the last run: planets, moons and orbiting facilities around their hosts, and every system and phenomenon along its galactic orbit. Run it monthly; the maintenance timers in INSTALL.md do.
  • planetgen.cli.migrate brings the database schema up to date. The install and update scripts run it for you.
  • planetgen.cli.reset deletes all generated galaxy data (asks for the database name first) so you can start a new galaxy.
  • planetgen.cli.query searches the database from the terminal.

A note on accuracy

planetGen aims for plausibility, not a simulation. Forcing extremes (a large star with the most planets it can hold, say) can give systems with worlds thousands of AU out; edit those by hand before using them.

Contributing

Every pull request adds a release note under changes/ instead of bumping the version; a workflow stamps the version after merge. A change that alters what a seed generates also bumps the generator epoch (python -m tests.golden_update --reason "..." --affects fill, changes/README.md). Run the tests with scripts/test.py changed while you work and scripts/test.py full --check before merging a finished piece of work; both need MySQL and Redis (docs/reference/testing.md). Plain pytest -n auto still works.
