This document describes config.json, the single per-deployment configuration file for the whole planetGen project -- the command-line tools (planetgen, planetgen.db.query, planetgen.cli.migrate, planetgen.cli.orbits, planetgen.cli.reset, ...) and the Flask app (the API in ../src/planetgen/api/ and the pages in ../src/planetgen/web/) all read it -- and ../config.json.example, the committed template it's copied from.

What it's for

Before this file existed, every one of those entry points read its own handful of PLANETGEN_* environment variables (planetgen.db.store.MySQLConfig, ../src/planetgen/api/config.py, ../src/planetgen/web/lib/apiclient.py), each with its own hardcoded default. That works, but it means a deployment that just wants "one MySQL server, one account, one API base URL" still has to either edit code or set half a dozen SetEnv/ EnvironmentFile lines to get there. config.json is a single JSON file, edited once per deployment, holding every one of those settings in one place.

It is loaded by ../src/planetgen/util/settings.py: one Pydantic model, Settings, holds every option with its type, default, help text, unit, whether it is a secret, whether a change needs a restart and which environment variable overrides it. A config.json that only sets the fields it needs to change is enough; anything it omits keeps its default value, a value of the wrong type stops the program with a message naming the field, and python3 -m planetgen.cli.config check validates the file without starting anything (an option name it doesn't know is an error there, so a typo such as ratelimt is caught). The debug switch and the two log locations are read by the standard-library-only ../src/planetgen/util/logpaths.py instead, because the installers run it as root before any virtual environment exists.

Location: repo root

config.json lives at the repo root -- next to src/ -- rather than inside ../src/html/ itself (its example template, ../config.json.example, lives at the repo root too, since a template holds only placeholder values, not secrets). This mirrors how Apache's DocumentRoot for this application is ../src/html/ alone (see ../examples/apache/planetgen.conf.example), and the other web servers only serve src/html/static/ from disk (see deployment/), so config.json, outside those trees, can never be requested over HTTP no matter how the site's rules are written. This matters because config.json holds real MySQL credentials, unlike the placeholder fields its now-removed predecessor (webconfig.json) only ever reserved for them.

It also has to be unreadable by other local users. install.sh and update.sh (through examples/apache/set-permissions.sh) keep it in the state folder (/var/lib/planetGen/state/config.json), owned by <apache user>:<apache group>, mode 640 (the code tree is root's since SEC.37, so only the state folder can be written by the web app); the file in the checkout, /var/lib/planetGen/config.json, is a root-owned link to it, and an old plain config.json is moved there by the next install.sh or update.sh. The web app (www-data for Apache and the gunicorn unit alike) can read and replace it, root can read it, nobody else can. The macOS guide sets the same rule by hand. A login user who runs the generator or the maintenance scripts from a shell without sudo needs to be in Apache's group (sudo usermod -aG www-data <user>, then log in again) to read it. After creating or copying a new config.json, re-run sudo examples/apache/set-permissions.sh (or sudo ./update.sh), or set it by hand: sudo mv config.json state/config.json && sudo ln -s state/config.json config.json && sudo chown www-data:www-data state/config.json && sudo chmod 640 state/config.json (from /var/lib/planetGen).

Precedence

Every setting below has up to four sources, checked in this order:

  1. An explicit function/CLI argument (e.g. planetgen sector --mysql-password ..., or a test building its own MySQLConfig(...) directly) -- always wins.
  2. The matching PLANETGEN_* environment variable, if set and not empty (a MySQL option set to an empty value counts).
  3. config.json, the one file that holds all program configuration. It is your own copy of config.json.example: the example is only a template that documents every option and its default, and nothing ever writes to it or overwrites your copy (update.sh leaves config.json alone, and an option added in a later release has its default in the code, so an older copy keeps working). The Admin settings page (ADM.43) and python3 -m planetgen.cli.config set edit config.json itself; see Saving settings. If the file does not exist they say so and create nothing.
  4. The built-in default (matching config.json.example's values).

Environment variables are still checked before config.json rather than being replaced by it, so a single shared config.json can still be overridden per-process where that's needed -- most notably planetgen-orbits@.service's per-instance PLANETGEN_MYSQL_DATABASE=%i (see ../examples/maintenance/), which relies on one templated systemd unit overriding just the database name per timer instance while everything else comes from the shared credentials file (or now, config.json).

Saving settings

The writer (planetgen.util.settings_writer) is the only thing that writes config.json; the command line and the Admin settings page (/admin/settings, below) both use it. The file lives in the state folder, which must belong to the web server's user (update.sh and set-permissions.sh see to that), so the page can replace it; when it doesn't, the page lists the options and says so instead of offering a Save button.

  • Who may change what. The web (an admin) changes the options the table marks "any admin"; the Owner (from 8.2) the "the Owner" ones; only the command line, run on the server, changes "command line only" options: the database, the secrets that open the host (secret_key), jobs.python, the log paths. A secret can be replaced but never read back: pages, diffs, audit rows and logs show (set), (empty) or (changed).
  • Checked first. An option that doesn't exist, that the caller's role may not change, or whose value doesn't fit its type or range is refused, each at its own option name, and nothing at all is saved. What is stored is the value the model parsed ("30" is stored as 30). An option left equal to its default is not stored.
  • Everything else stays. The file is edited as parsed JSON: keys the model doesn't know and the order of the keys are kept; only the changed options move.
  • Written atomically. A temporary file in the same folder, fsync, the old file's mode, a rename, then fsync of the folder: a reader sees the old file or the new one, never half of one. A lock file next to it keeps two saves (two admins, or the page and the command line) from interleaving.
  • Backed up. Just before a save, restore or import replaces the file, a settings-only backup archive is taken (backups below): the old file, who is making the change and when. The newest settings.backups_kept (default 20, 1 to 200) archives are kept. A restore from the web puts back only the options an admin may change; the command line puts the whole file back.
  • Audited. One admin_audit_log row per changed option (config.update, config.restore; target config:<option>; detail {"old":..,"new":..}) and one DB line in the activity log. A secret's values are written (changed).
  • Restart. The result lists the changed options marked "after a restart".

The settings page

/admin/settings (Admin, Settings tab; ADM.84) lists every option of the model from the model itself, so an option added with settings.opt(...) appears there with its help, default, limits and unit and needs no page code. Each shows where the value in use comes from: the default, config.json, or an environment variable (which still wins over the file; the page and the review say so). Change what you want and press Review the changes: a bad value is sent back with its message at its option and nothing is saved; a good form shows the old and new value of each changed option, marks the ones that need a restart, and Save these changes writes it as described in Saving settings. Use the default removes a key from the file; a secret's box is write-only (empty keeps it, typing replaces it, Clear it removes it). While a saved option still needs a restart of the web server, every admin page shows a banner naming it; the banner goes when the server restarts. The page is described in html-interface.md.

Update config.json

A release that adds an option does not touch a site's own config.json (the file is never overwritten), so an older file simply lacks the new keys and the program uses their defaults. The Update config.json link on the settings page (/admin/settings/update, ADM.140; any admin) brings the file up to the version without losing what the site has set. It shows a preview first and writes nothing until its one button is pressed:

  • Settings to add. Every option the model has and the file lacks, with the default it will be written with. An option the web cannot change (the database section) is added with its default too and never altered otherwise. A secret is added with its default and its value is never shown.
  • Recommended, not set. The options a site should have in its file whatever the default is (should_set in settings.opt), each with the reason. One that also names a value (recommended) has a box, ticked to begin with, and a ticked box writes that value instead of the default; an option only the site can fill, such as base_url, is listed with its reason and no box. An option the file already has any key for is never listed and never changed.
  • Stale keys. Keys the model no longer knows, shown by name only. They stay in the file unless their box is ticked.

Every value already in the file is kept exactly, and so is the order of its keys. The write is the settings page's own (see Saving settings): a settings-only backup archive of the old file first, an atomic replace, and one admin_audit_log row per key added or taken out (config.update_file). A file changed by someone else after the page was drawn is refused, and a failed write leaves the old file. The API is POST /api/admin/settings/update/plan (nothing written) and POST /api/admin/settings/update (api/settings.py).

Backups

planetgen.backup (ADM.87) takes every backup as one backups/<UTC time>.tar.bz2 in the state folder (/var/lib/planetGen/state, PLANETGEN_STATE_DIR moves it), mode 0600, owned by the web user (set-permissions.sh keeps the folder 700). It holds manifest.json (format 1, time, who, why, the version and, per part, its folder, sizes and SHA-256) and one folder per part: settings/ (a copy of config.json, secrets included, which is why the archive is private and its download is for the Owner) and parity/ (DB.40: a copy of the sector repair file, sector-parity.pgpr, taken with the file locked against every save and cut at its last whole record; the manifest keeps its size, the sectors it covers and the groups as the part's info; the option settings.backup_parity, on by default, switches it off for a very large galaxy), and control/ (the control database) when that part arrives in 9.0. A save on the settings page takes an archive of the settings part alone; python3 -m planetgen.cli.backup take takes every part. A parity copy is refused, with the reason, when the live file is damaged behind its last record (planetgen repair-db makes it again from the database).

python3 -m planetgen.cli.backup restore --part parity ARCHIVE puts the copy back (DB.41). It is refused, before anything is backed up or changed, while a save is writing parity, when the galaxy database cannot be reached, and when the part is empty or its file is damaged. Otherwise a safety archive of the live file is taken, the copy is written beside the live file, synced and renamed over it, and then it is checked against the database (the check of DB.8, with the stale-record rule of DB.9): a record that no longer matches the rows because the database changed since the backup is made again from the rows and is not damage, a member whose sector is gone is let go, and the result says how many sectors the copy holds no record of (unprotected until their next save or planetgen refresh-parity) and which sectors are damaged (for planetgen repair-db).

Retention is the option settings.backups_kept: the newest archives are kept, the rest deleted, but never the newest archive that holds every part. A restore verifies the archive first, backs up what it is about to replace in a safety archive, then restores the whole archive or only the parts named; a part this build has no provider for is skipped and reported, and the archive keeps it. The galaxy database is not in an archive: it is regenerated from its seed or repaired from parity.

The backups screen, export and import

/admin/settings/backups (ADM.85; a link on the settings page) is the one screen for archives. It lists them newest first (when, who, why, which parts and how big), and Back up now makes one of every part. Compare and restore opens an archive: it is checked against its hashes, the settings part is compared with today's config.json (every option a restore would change, a secret as (changed), a backup that no longer fits the model refused with the reason), and the parts ticked are restored: the whole archive, or one part. The restore makes a safety archive of what it replaces first, writes a config.restore audit row per changed option and a backup.restore row, and from the web puts back only the options an admin may change. Download is the Owner's, from 8.2 (an archive holds every secret); until then archives are read on the server.

Export downloads the options set in config.json that an admin may change, as JSON in the file's own layout with config_version: never a secret and never a command-line-only option. Import takes such a file and checks it exactly as an edit is checked (each option's role, type and range; unknown keys and keys an admin may not set are errors; a file from a newer release is refused), shows the review diff, and saves it as config.import with a backup first. It sets the options the file names and leaves every other option as it is; one bad value changes nothing.

Web, link previews and search engines

The site, web, icons, seo and og sections (ADM.44) set what the pages tell browsers, search engines and chat programs. All of them apply to the next page view with no restart; the settings page shows them under Site, Web pages, Icons, Search engines and Link previews. They are all read at request time by planetgen.web.seo.

  • The address. Canonical links, og:url, og:image, the sitemap and the robots.txt Sitemap: line are built from base_url (the Owner changes it), never from the request's Host header. While it is still http://localhost/ none of those absolute addresses is written and /sitemap.xml is a 404.
  • The title and tab. web.title_template ({title} - {site_name}), site.language (the lang of every page and the Open Graph locale), site.tagline (under the home page heading, and the description of pages that give none), the theme colours.
  • What may be indexed. seo.indexing is off (robots.txt disallows /, every page says noindex), top_pages (the home page, the class, species, polity and galaxy pages and the lists) or all (also the system, sector and phenomenon pages); seo.detail_pages = index does the same for the generated pages alone. Millions of generated pages look like scaled content to a search engine, so they stay out by default. The data and tool routes (search, navigation, the Galaxy Map's nodes, the /scene and /table data) answer X-Robots-Tag: noindex and are disallowed in robots.txt; the admin, login and account pages say noindex,nofollow. A page that has a query (?page=2, a filter) is not indexed but its links are followed, and its canonical link drops tracking and sort parameters. A page the code has not classified is treated as a tool route, and a test fails until it is classified on purpose (planetgen.web.seo).
  • robots.txt. Generated from the routes: every tool and private route is disallowed with * wildcards, block_ai_crawlers adds the AI crawlers, robots_extra is appended and robots_override replaces the whole file. A line that is not a directive is refused where it is typed; an override that disallows / while indexing is not off is allowed but warned about, since it hides the site.
  • Sitemaps. /sitemap.xml is an index of /sitemap-pages.xml and, when the generated pages may be indexed, /sitemap-systems-<n>.xml and /sitemap-sectors-<n>.xml of at most seo.sitemap_max_urls addresses each, built from the database 500 at a time and kept for seo.sitemap_cache_hours. Phenomena are not listed. The number of files comes from a count that may be an estimate, so the last may be empty.
  • Other files. /.well-known/security.txt and /humans.txt serve the text in seo.security_txt and seo.humans_txt (404 while empty); /site.webmanifest is served while icons.manifest_enabled; seo.privacy_note is shown on the account page.
  • Link previews. og.enabled adds Open Graph and Twitter tags to the public pages (never the admin, login or account ones). The picture is og.default_image, else the built-in 1200 by 630 one. og.generated_cards is for a per-system and per-sector card: with it on, /og/<system|sector>/<id>.png draws the card with a renderer installed by planetgen.web.seo_pages.register_card_renderer (the drawer is VIEW.3; with none, every page uses the default picture), caches it in og.card_cache_dir (the state folder's og-cards by default) up to og.card_cache_mb, and falls back to the default picture when it can't draw.
  • Icons and pictures. The icon options hold the name of an uploaded file, not a path: upload on the Images page (/admin/settings/images, linked from the settings page). A picture is checked on upload (PNG, JPEG, ICO or a sandboxed SVG; size and squareness where they matter; at most 1 MiB), stored as <16 hex digits of its SHA-256>.<ext> in web.assets_dir (the state folder's assets by default) and served at /site-assets/<name> for a year (its name is its content). Uploading and removing save the setting through the same writer, so they are backed up and audited. These site pictures take no GIF; an account's own picture (docs/reference/api.md, POST /api/auth/avatar) is the one place a GIF is accepted.

Options

The table is generated from the settings model (src/planetgen/util/settings.py, ADM.42); change an option there and run python3 -m planetgen.cli.config docs. Next to each option: its type, default, whether a change applies at once or after a restart, who may change it from the web ("command line only" means on the server only) and the environment variable that overrides it.

Equivalent to PLANETGEN_API_BASE_URL.
debug Debug mode. When true, every part of planetGen writes everything it decides: each planetgen command (and each other command: python3 -m planetgen.cli.*) writes every decision, random draw (with its source line and the probabilities it refers to), SQL statement, run, stage, unit, worker and cache event to stdout, with an ISO timestamp to the millisecond, and the same lines go to log_file along with the html/ pages', the API's and the workers' (every web request, API call and admin access check, and every error with its traceback). The output is large (a single system writes about 265 KB) and the run takes a quarter to two thirds longer, so install.sh/update.sh install a logrotate config for the file (daily, or past 100 MB; 7 compressed copies kept); debug_areas limits what is written. A command whose result goes to stdout (--output -) writes its debug lines to stderr; --quiet still silences the console. The web interface never shows tracebacks on its pages, debug or not; with debug on, a 500 page says the traceback is in the debug log. See ../src/planetgen/util/log.py. Empty, the default, writes everything but branch, which logs every conditional jump in planetGen's own code (hundreds of thousands of lines for one system, about 15 times the run time) and is written only when named (branch, or all,branch). "system" leaves it to logrotate or newsyslog (the program reopens the file after it is moved); "app" makes the program rotate it itself (100 MB per file, 30 old copies). "auto" means "system" where install.sh/update.sh installed /etc/logrotate.d/planetgen-log or /etc/newsyslog.d/planetgen-log.conf, else "app". No environment variable.

The activity log

Separate from the debug log, planetGen always writes a short record of who did what to planetgen.log in log_dir (SEC.28, ../src/planetgen/admin/activity_log.py): sign-ins, refused requests, every change to the database and every API call. It is on whatever debug says; with debug on, each line is copied into the debug log too. Passwords, session tokens and API keys are never written.

Every line has the same shape, so a tool such as fail2ban can match it (deployment/fail2ban.md has a ready filter and jail):

2026-10-01T04:00:00-0400 planetgen[1234]: AUTH login.failed ip=203.0.113.5 user="admin"
2026-10-01T04:00:09-0400 planetgen[1234]: DB sector.update ip=203.0.113.5 user="boss" target=sector:42 detail="{'name': 'Home'}"

That is: the time local with the offset of its zone, planetgen[<process id>]:, the category, the event, ip= (the client address, or - with none, as on the command line), user= (always quoted; the admin, the username as typed, or the login name that ran a command; - when nobody), then any further key=value fields. The address always comes before anything a visitor typed and is written only when it is a real IPv4 or IPv6 address (else -). Every value that isn't a plain number or token is quoted, with " and \ escaped and control characters written as \xNN, so a crafted username can't start a new line or fake a field; quoted values are cut at 200 characters.

Category Events
AUTH login.ok; login.failed (wrong username or password); login.locked (refused unchecked while the address or username is locked, with scope=ip or scope=user and retry_after=); lockout.start (a failure that started a lock, with scope=, subject= and seconds=); login.ratelimited (past the per-address limit); logout; credentials.changed (with old_user= after a rename); password.failed (a wrong current password on /account); login.password_ok (right password, two-factor code still to come); totp.failed (a wrong two-factor code); totp.recovery_used (with left=); totp.enabled, totp.disabled; apikey.create, apikey.revoke
AUTHZ login.required (an admin route with no session or key); session.invalid (an expired, ended or unknown session cookie); apikey.invalid (an unknown or revoked API key); credentials.unchanged (an admin route refused until the first credentials are changed); admin.required (an admin-only page action refused); csrf.failed (a form token that doesn't match); each with path=
DB every write through the web interface or API (sector.create, system.update, star.rename, facility.create, lockout.lift, ...: the same action names as admin_audit_log, with target= and detail=; planetgen.cli.lockouts writes lockout.lift, devices.revoke and totp.reset too); migrate (each schema migration step, db=, from_version=, to_version=)
GEN generate.start and generate.finish for each planetgen run that writes the database (command=, db=; the finish line adds status=ok/failed/interrupted, seconds=, sectors=, systems=, phenomena=); job.start and job.cancel for the admin Generate page
API call for every request to /api/... (API.15), written when the answer is ready: user= (the owner of the API key, the signed-in user, god for a command-line tool, or -), via= (key, session, anonymous or console), method=, route= (the matched route, - for none), path=, status= (the HTTP response code), ms=, bytes_in=, bytes_out=, rid= (also sent back as X-Request-Id), ua=, client_api= (the API version the client sent), and when they apply key_id= and key_prefix= (never the key), internal=1 (a call a web page made to the API in-process, about six for each page view) and ratelimited=1. A command-line tool that does what an API route does writes the same line with user="god", via=console and status=200 or 500

The API lines use HTTP response codes, for parity with the web server's own logs; a request the web server refuses before it reaches the program (a 413 from LimitRequestBody, a failed TLS handshake) appears only in the web server's log. api_log.internal set to off leaves out the calls the web pages make to the API in-process; the default logs all of them. Request bodies, tokens and Authorization headers are never written. The address is the client's full address, kept as long as the file is (the rotation below: 30 copies of up to 100 MB).

Failed and locked sign-ins and wrong current passwords also go into the control database's admin_audit_log (kept 90 days), which the admin Stats page lists under "Failed sign-ins".

Rotation: install.sh/update.sh (as root, through examples/apache/setup-debug-log.sh) install the system's own rotation, so nobody has to edit these by hand. For a setup without the installer, the samples are:

Linux, /etc/logrotate.d/planetgen-log (the user and group are the web server's: www-data on Debian and Ubuntu, apache on RHEL and Fedora):

/var/log/planetgen/*.log {
    daily
    maxsize 100M
    rotate 30
    missingok
    notifempty
    compress
    delaycompress
    dateext
    dateformat -%Y%m%d-%s
    su root www-data
    create 0660 www-data www-data
}

macOS, /etc/newsyslog.d/planetgen-log.conf (newsyslog runs every hour by itself; $D0 rotates at midnight, the size column in KB rotates sooner past 100 MB, J compresses with bzip2, N means no process to signal):

# logfilename                              [owner:group]  mode count size(KB) when flags
/Library/Logs/planetgen/planetgen.log      _www:_www      660  30    102400   $D0  JN

The program reopens the file after either tool moves it, so no restart or copytruncate is needed. A process that can't open the file carries on without it and prints one warning to stderr (only when the folder exists, so a development checkout stays quiet). A login user who runs planetgen from a shell needs to be in the web server's group to append to it, as for the debug log.

Why the real file is gitignored but the example isn't

config.json (the real, per-deployment file) is listed in ../.gitignore, next to the existing *.db/db.sqlite3 entries -- it's deployment-specific configuration that holds real MySQL credentials, and committing it would either leak those values or force every deployment to share one repo-tracked file. ../config.json.example is the opposite: a template with placeholder values, meant to be committed so a fresh checkout always has a shape to copy from, exactly the same split already used for ../examples/apache/planetgen.conf.example (committed template, edited into a site-specific vhost file that itself doesn't live in the repo).

Setup

Copy the template at the repo root and edit it for this deployment:

cp config.json.example config.json

Then fill in mysql.host/mysql.user/mysql.password/mysql.database (and control_database, if this deployment names its control schema something other than the default -- see deployment/README.md) for this deployment's actual database server. site_name/base_url are cosmetic and safe to leave as-is.

If config.json doesn't exist at all, planetgen.util.settings.get_settings() falls back to the built-in defaults shown in config.json.example, so every entry point keeps working (against 127.0.0.1:3306 as user planetgen) without this step -- exactly the environment-variable-only behavior this project had before config.json existed.

Relationship to PLANETGEN_* environment variables

config.json doesn't replace the PLANETGEN_* environment variables -- see "Precedence" above. In short: config.json is where a deployment sets its defaults once; environment variables (the web server's or service's own environment -- not an Apache SetEnv, which never reaches os.environ under mod_wsgi -- a systemd EnvironmentFile, a launchd EnvironmentVariables, or a shell export) remain the way to override one of those defaults for a single process, most importantly the per-instance database name planetgen-orbits@.service needs.

PLANETGEN_WORKERS: not a config.json option

The number of worker processes a generation run uses is set by --workers N on the planetgen command, else by the PLANETGEN_WORKERS environment variable (a number, or auto); with neither, a run uses 80% of the cores (one fewer when the database is on the same machine, so it keeps a core). A positive number is used as given. More than one worker needs the Redis server in redis.url; without it a run generates one sector at a time. The admin Generate page's jobs run planetgen, so they use it too. The test suite sets it to 1 (testing.md).
