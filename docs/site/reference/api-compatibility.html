API compatibility

docs/reference/api-compatibility.md

The API has a version of its own, one integer that is not the release number (src/planetgen/api/version.py, API.22). Every /api answer carries it in the X-PlanetGen-API-Version header, GET /api/health reports it as api_version, and the User-Agent of everything the software sends names it (PlanetGen-API/<n>). It goes up by one, by hand, in the pull request that makes a breaking change to an endpoint: a removed or renamed route or field, a changed meaning or type, a new required parameter. Additive changes (a new route, a new optional field or parameter) leave it alone. That pull request also adds the row below to docs/reference/api-versions.json, a line to the change list in api.md, the route snapshot src/tests/fixtures/api_routes.json and api-version: changed to its release note; the stamp fills in the release. src/tests/test_api_compatibility.py fails when any of them is missing.

Clients and the servers they talk to

Client Where Speaks Talks to
The web pages static/apiversion.js (adds the version header to each call a page makes), web/lib/apiclient.py the API version of the release they ship in the server they were served by: pages and server are one release, so they always agree
Remote generate (generate.py --remote, API.3) not built yet the API version of the release it is run from a server of the same API version (API.5 widens this to the current major and, for one release cycle after a major bump, the previous one, for upload payloads only)
The command line (planetgen ...) src/planetgen/cli/ none: it opens the database directly no server involved

A client of one API version used against a server of another is not supported until API.5 adds the check and the converters for older upload payloads (GET /api/version, the PlanetGen-API-Version header both ways, a refusal 400 api_version_unsupported).
