Every option of planetgen, the one entry point for every generator. For what planetGen is and a short tour, see the README; for installing it, INSTALL.md. The installer adds a planetgen command that runs it. planetgen <command> --help prints the same options.

Subcommands

planetgen is the single command-line entry point for every generator in this project — one command, with a subcommand per generation scale:

planetgen system [options]      # one star system
planetgen sector [options]      # one or more independent sectors
planetgen sectors [options]     # sectors of the planned galaxy, in one of the modes, and nothing else
planetgen galaxy [options]      # many sectors placed as one galaxy
planetgen plan [options]        # the galaxy's density skeleton
planetgen scatter --KIND        # one scatter on the plan: --mass, --luminosity, --phenomena, --nebula-field, --band
planetgen clear-scatter --KIND  # empty one scatter, so scatter can draw it again: --mass, --luminosity, --phenomena, --nebula-field
planetgen fill-map-luminosity   # fill the map luminosity of the scattered phenomena
planetgen rescore-habitability  # re-derive every stored habitability score
planetgen refill-effect-ledger  # write again the light and ultraviolet rows of the effect ledger
planetgen clean-nebula-field    # count, or with --apply drop, the field clouds the keep rates now reject
planetgen link --since TIME     # link the sectors saved since TIME to their neighbours
planetgen backfill --since TIME # the bright-star backfill out from the sectors saved since TIME
planetgen settle --since TIME   # save the paths of the sectors saved since TIME and of those around them
planetgen phenomenon [options]  # one exotic stellar phenomenon
planetgen population [options]  # species, civilizations and polities
planetgen territories [options] # which polity owns which system
planetgen population [options]  # species, civilizations and territories
planetgen bring-to-epoch [--dry-run] [--no-wide-binaries]  # bring a stored galaxy to the running generator epoch without a full regeneration
planetgen refresh-parity [--compact] [--limit N]  # make the sector parity file current (settings: parity)
planetgen repair-db [--shell N] [--sector SHELL BAND WEDGE] [--dry-run]  # rebuild damaged sectors from the parity file
planetgen repair-db --salvage TABLE | --reload TABLE [--restore-sectors] [--dump-dir DIR]  # rebuild a table with an unreadable page
planetgen check-math [-v]       # the math check (update.sh runs it)
planetgen fingerprint [options] # a digest of the generated content, to compare two builds
planetgen check-db [options]    # look for damage in the database (writes nothing)
planetgen versions              # the version keys the updates recorded
planetgen benchmark [options]   # time where generation spends its time, in scratch databases
planetgen warm [FAMILY|PHASE ...]     # build the site's caches ahead of the first visit
planetgen queue stop-all|resume|status  # stop everything and hold, lift the hold, or show it
planetgen commands              # every command the work queue can run
planetgen command-run KIND ARGS # one unit of one of them, alone

Run planetgen <command> --help for that command's own full option list. system, sector, galaxy, plan, phenomenon, population and bring-to-epoch save what they generate to the database; refresh-parity writes only the parity file and the checksum marks, and repair-db writes only the rows of sectors it finds damaged. check-math, fingerprint, check-db and versions write nothing, and benchmark writes only to scratch databases of its own. system and sector are runs of one command through the work queue (a Redis server must be running, as for galaxy): they appear on the Queue page like any other run, and a system --output run, which saves nothing, does not take the generation slot.

The sector parity file (refresh-parity, DB.46). With parity.enabled on (config.json; off by default), every saved, edited or deleted sector updates a parity file kept outside the database (parity.dir, /var/lib/planetGen/parity when empty; keep it off the database's own disk if you can). The file holds, for each group of up to parity.group_size (32) sectors of about the same size that are far apart in sector id, parity.parity_blocks (2) Reed-Solomon parity blocks over the sectors' exports, so that two damaged sectors of a group can be rebuilt from the other thirty (the rebuild is repair-db, below) at about 7 percent of the sectors' size in disk space and a few milliseconds a save. A save, an edit or a deletion commits first and then updates the parity; a crash between them leaves the sector marked (parity_dirty), which the check reports as unprotected, never as damaged. planetgen refresh-parity builds the file for a galaxy made before, or catches up after a crash: it protects every sector that is marked or was never sealed, every sealed sector the file does not hold, and lets go of members whose sector is gone; a sector whose group has a damaged member is left marked and the command exits 1. --compact rewrites the file with only the latest record of each group (a record is appended on every update, so the file grows until it is compacted). --limit N makes at most N sectors current per run.

Rebuilding damaged sectors (repair-db, DB.47). check-db reports a sector whose rows no longer hash to the checksum sealed for it as damaged. planetgen repair-db finds those sectors (the same test, --shell and --sector limit it) and, for each, reads its group in the parity file: the other members are checked against what the record holds for them, and up to parity.parity_blocks (2) unusable blocks of a group, damaged sectors included, are rebuilt together. The rebuilt block must hash to the stored checksum before anything is written; then the sector's rows are made those rows in one transaction (differing values updated, lost rows inserted, rows the sector never had deleted) and the sector is checked again before the commit. Only the columns the checksum covers are written: the columns the orbit update rewrites (phases, positions, velocities) stay as they are on every row that still exists, and a row that has to be inserted gets them as zero, to be carried on by the next orbit update. A sector whose record is behind the database as well (damage and a stale record at once), a sector in no group, a group with more damage than parity blocks, and a table the server cannot read at all (the next paragraph) are listed with the reason and left as they are; the command exits 1 while any is left. If the damaged part is the parity file itself (a record that fails its checksum), the file is compacted and made again from the database, which protects only sectors that still hash to their checksum. --dry-run says what would be rebuilt and writes nothing. It exits 2 when there is no parity file.

Rebuilding a table with an unreadable page (repair-db --salvage and --reload, DB.48). When the server cannot read a page of a table's clustered index (repair-db lists the sectors in it as unreadable and names the tables), nothing can be fixed from SQL: the server has to be told to skip the page, and while it does InnoDB refuses inserts, updates and deletes. So it is two steps with a restart between. (1) Stop the website and any generation, add innodb_force_recovery = 1 to the [mysqld] section of the server's configuration, restart the server and run planetgen repair-db --salvage TABLE: every readable row of the table is written to a dump file in --dump-dir (default: a salvage folder in the parity folder; the values are written exactly, nothing is rounded), the file is synced, and only then is the table dropped and made again empty. It refuses, changing nothing, if the table cannot be read and the server is not in force recovery (and says to restart it that way), if a dump is already waiting for a reload, or if a normally running server counts other rows than were dumped. (2) Remove innodb_force_recovery, restart the server normally and run planetgen repair-db --reload TABLE: the rows are inserted again with their original ids, the count is checked, the dump is renamed .loaded, and the sector repair above runs: a sector that lost rows with the page no longer hashes to its checksum, and the parity file rebuilds it, lost rows included. An interrupted reload is finished by running it again. Only the tables a sector's checksum covers can be rebuilt (the parity file is what brings the lost rows back); a damaged secondary index needs no parity, only a rebuild of the index. A page holds neighbouring rows, which are neighbouring sectors, which the parity groups keep apart, so one lost page costs each group at most a block or two; if more than parity.parity_blocks sectors of one group lost rows, the others are listed as unrepairable. Losing the sectors table's own rows is the one loss check-db cannot see (a sector with no row is on no list): --reload sectors --restore-sectors also puts back the sector rows the parity file holds and the table lacks, and is opt-in because a sector deleted while parity.enabled was off is still a member of the file and would come back. The columns the orbit update rewrites come back as the table's defaults on a row the repair has to insert, as above.

Bringing a galaxy to the running epoch (bring-to-epoch, GEN.764). An epoch bump (src/tests/golden/epochs.json) says generated output changed; a galaxy stored under an older epoch is not redone by the update. planetgen bring-to-epoch redoes the part the epochs in between changed (each epoch lists the stages it altered, affects, and each stage of a stored galaxy records the epoch it was made under: the plan in galaxy_shape, each scatter in scatter_epochs, each sector in sectors, each species in species). --dry-run says what it would do and changes nothing. It generates again, in address order, every galaxy-placed sector whose fill is behind (the sector is deleted and made again from its address and the galaxy's seed, then the paths around it are settled), makes the species of an older population epoch again (a species edited by hand is kept) and runs the population pass; it says each sector and species step. It leaves a sector with admin edits alone and lists it: the admin audit log is the record of edits, so an edit of something later deleted cannot be traced to its sector, and a sector edited before the audit log was kept looks unedited. A scatter that is behind is drawn again by the same run (GEN.845), with the settings it was drawn with (the luminosity floor, the stellar mass limit and the compact object limit, read before the clear forgets them): the massive stars first, the bright stars after them (they are split from the massive ones at the mass limit, so a redraw of either redraws the bright stars), then the phenomena and the nebula field. A scatter never adds to a sector already filled, so the sectors to be generated again are emptied first, the scatters cleared and drawn, and the emptied cells generated after; a sector left alone keeps the objects it was made with. If the scatter fails the emptied sectors stay empty, the run says so and planetgen scatter for the kinds cleared, then planetgen sectors, finish it. It refuses, naming the epochs, when the plan was made under an epoch that changed the galaxy's shape (a full regeneration is needed) or when a stored scatter setting is one planetgen scatter no longer accepts (draw that scatter by hand). Wide binaries (GEN.229). The run also reads every wide (S-type) binary, even when the galaxy is at the running epoch, and makes again those that break the stability rule GEN.228 put on new ones (a planet beyond its star's stable orbit limit, or the two stars' outermost bodies too close at the pair's closest approach: planetgen check-db --deep --wide-binaries counts them). Only those systems are redone, not their sectors: a system is drawn again as a wide binary for its sector's stellar population from a seed of its own (the galaxy seed and the system's Object ID, so the same galaxy gives the same new system), keeps its row, name, Object ID and place, and its bodies take the slots of the old ones. The console says, for each, the system and the bodies that broke the rule and what the re-roll made. A system that hosts facilities (they would be deleted), is built around a bright star the scatter placed, or lies in a sector with admin edits is left alone and named. --no-wide-binaries skips this stage. An interrupted run is resumed by running it again, since each sector records its epoch when it is saved. Object IDs follow the galaxy's seed and the sector's address, so a sector keeps its IDs when the redo gives it the same bodies; DB.75 (IDs that survive a changed body count) is not built yet.

The math check runs at every update. check-math runs planetgen/physics/mathcheck.py (known answers from real astronomy, identities, and sampler distributions; see testing.md) and exits 1 if a check fails; -v / --verbose lists every check. A run does not repeat it (PERF.170, Boss 1:14 PM EDT 2026-10-23): update.sh runs it after updating and warns (and skips the population pass) if it fails, the website runs it once when it starts, and the admin page (/admin, "Check the math") runs it whenever an admin asks and shows the result. The bulk runs (galaxy, plan, population, and sector --num-sectors above 1), the Generate page's jobs and the Sector page's "generate the neighbourhood" button do need the downloaded data files (the Generate page's first step, "Check the data"; see datasets) and refuse to start without them, writing nothing, not even the activity log line. One system, one sector or one phenomenon is not gated.

To generate a new star system:

planetgen system [options]

To generate a whole sector of star systems at once, see Sector Generation below.

Options

Most system options use a +name/-name tri-state syntax (these forcing options are for a single system only; sector and galaxy refuse them): +name forces that feature to be present, -name forces it to be absent, and leaving it off the command line leaves it up to chance. Two options are the exception: +habitable_world and +intelligent_life only raise the odds of their outcome (the draws that lead to it are kept more often) and never force it, so a system may come out without one and says so.

  • --version: Prints the program's version, repository URL, and license, then exits immediately.
  • +habitable_world / -habitable_world: Raise the odds of / forbid a habitable world in the system. The option raises the odds, never forces: no planet is placed or adapted for it, and the system's habitable_request says unmet when none came out.
  • +asteroid_belt / -asteroid_belt: Force / forbid the generation of an asteroid belt in the system.
  • +comets / -comets: Force / forbid comets in the system.
  • +large_star / -large_star: Force / forbid the generation of a large star.
  • +moons / -moons: Force / forbid moons on the system's planets.
  • +max_planets / -max_planets: Force the system to the maximum, or the minimum, number of orbital objects it can support.
  • +intelligent_life / -intelligent_life: Raise the odds of a planet with intelligent life / forbid one. The option raises the odds, never forces: a civilization is never forced, and one needs a world whose timeline reaches it. Either implies +habitable_world.
  • +binary_system / -binary_system: Force / forbid a binary star system.
  • +wide_binary / -wide_binary: Force an S-type (wide) binary, or force a P-type (close) one instead. Only meaningful together with +binary_system; if omitted, one of the two is chosen at random.
  • +planets / -planets: Ensure the system has at least one planet or asteroid belt, or none at all (star only).
  • --system-file, -f <path>: Load a system generation specification from a JSON file (see below). Any of the options above, or the value options below, given on the command line override the corresponding value from the file.
  • --num-orbits <int>: Force an exact number of orbital slots (planets and asteroid belts combined) to be generated.
  • --stars <int>: Force the number of stars in the system, from 1 up to the cap (GEN.267). 1 is a single star, 2 a pair, more a tree of pairs; the system file's stars key does the same. Carried in the config for the member-tree host (GEN.630) to read, which is not built yet, so until it lands a system still comes out a single star or a pair whatever the count. Stored with the config (system_configs.stars).
  • --max-stars <int>: The most stars a system may hold, the cap on the star-count draw (default 12, at most 64; the system file's max_stars key). Stored with the config (system_configs.max_stars). Also on sector and galaxy.
  • --format <text|markdown|document>: How --output writes the system: plain text for the terminal (the default), Markdown (the same description the site shows; UX.106) or the Document as JSON.
  • --output, -o <file>: Writes the system's description (in --format) to file instead of saving the system to the database; - writes it to stdout. The admin site's one-off system page (/admin/generate/system) does the same from the browser.
  • --star-type <type>: Force the generation of a specific star type (e.g., G2V).
  • --name <name>: Specifies a name for the star system, overriding the default random generation. Everything in the system is named from it: planets are numbered in orbit order (Sol I, Sol II, ...), moons add a letter (Sol IIIa), a close binary's two stars are the system's A and B (Sol A, Sol B, with planets named for the system), and a wide binary's two stars are two words sharing the system name's first word (Sol Kelmoor, Sol Pikkita; the second star's word sounds like a diminutive). A wide pair's primary numbers its planets after that shared word (Sol I) and its secondary after its own word (Pikkita I). Asteroid belts aren't numbered.
  • --age <young|old>: Specifies the age of the star system (young or old).
  • --flavor-chance-system <float>: Overrides the default system-level flavor text chance (0.0 to 1.0).
  • --flavor-chance-planet <float>: Overrides the default planet-level flavor text chance (0.0 to 1.0).
  • --max-planet-flavor: Sets the maximum flavor text total for planets to 99.
  • --debug [file]: Debug mode for this run. Writes every decision the run makes, however small, to stdout, one line each, with an ISO timestamp (2026-10-23T17:29:42.729-0400 DEBUG worker.py[2142] [draw] star.py:688 generate | message, always in this one format, the area in brackets (draw, sql, queue, ...) being the thing to filter on): every random draw (the call, its arguments, the result, the source line that asked for it and the probability or threshold it was compared against), every narrated choice and why, every stage and unit of the run and every worker it starts, every SQL statement with its timing, cache hits and misses. The lines of the queue workers that do the run's work reach this stdout too, as they are written (they are relayed through Redis to the command that started the run, so a worker's own stdout, which goes nowhere, does not matter). If file is given, the same lines are also written to file. Available on every subcommand, and on every other command in this document (python3 -m planetgen.cli.*, the worker included); the Generate page has a Debug box for a job. A run whose result goes to stdout (--output -) writes the debug lines to stderr instead. The detached helpers a run starts (the background planetgen warm, an auto-started worker's own start and exit) have no stdout, so they write the debug log file only. The output is large (about 265 KB of text per system) and takes a quarter to two thirds longer; --debug-areas cuts it down. For the same output on every command without the flag, and in the debug log file, set "debug": true in config.json (see docs/reference/config.md).
  • --debug-areas <areas>: Limits --debug (and debug mode in config.json) to some kinds of output. Areas: decision (narrated choices and timings), draw (random draws), sql, queue (runs, stages, units, workers), cache, web (requests, API calls, authorization), lib (other libraries' logging), branch (every conditional jump in our own code: the source line, where it went and the values it refers to; about 750,000 lines and 15 times the run time for one system, so off unless named: --debug-areas branch, or all,branch for everything). Comma separated; a leading - leaves one out (-draw). Normal output, warnings and errors always show. Not given, every area but branch is written. Also "debug_areas" in config.json and PLANETGEN_DEBUG_AREAS.
  • --record-file <file> / --record-json: Also writes every log line of the run to <file> as a record (UX.122, docs/design/operations/logging-standard.md): one per line, ts=2026-10-24T18:40:00.123Z level=info component=generate msg="..." and any key=value fields, the time always in UTC; --record-json writes JSON lines instead. A web job sets PLANETGEN_RECORD_FILE (and PLANETGEN_RECORD_FORMAT=json for JSON lines) for each of its steps, which does the same. The form of every log line (time, severity, component, message, fields, stage markers) and where each kind of log is found are described once in logging.md.
  • --quiet / --silent: Suppresses all output except errors. Available on every subcommand. Combined with --debug, a filename is required (there would otherwise be nowhere for debug output to go).
  • --disregard-missing-data: Generates even though a downloaded data file is missing (GEN.599; see datasets). Available on every subcommand; one that reads no downloaded data ignores it.

Note on Incompatible Options:

  • -planets cannot be combined with +moons, +max_planets, +habitable_world, or +asteroid_belt (on the system command this also covers the same keys, num_orbits and slots, in a --system-file).
  • --star-type cannot be combined with +large_star.
  • +intelligent_life/-intelligent_life cannot be combined with -habitable_world.
  • +habitable_world and +asteroid_belt together cannot be combined with -large_star (both objects require the room a large star provides).
  • --num-orbits cannot be combined with -planets.
  • --stars must be a whole number of at least 1, and no more than --max-stars (12 unless raised; --max-stars itself is from 1 to 64). The error says which: "stars 13 is more than the cap of 12 stars; raise the cap with --max-stars (at most 64)".
  • --stars 1 cannot be combined with +binary_system or +wide_binary (a single star has no companion), and --stars 2 or more cannot be combined with -binary_system. --stars 3 with +binary_system is allowed: the system has a companion, and the rest of the tree is the host's. --system-file keys are checked the same way, against the command line's values when both give one.
  • --num-orbits must be from 0 to 500 (the generator's own ceiling on objects in a system).
  • --flavor-chance-system must be a float between 0.0 and 1.0.
  • --flavor-chance-planet must be a float between 0.0 and 1.0.

A forced body some stars can't host (a habitable world around a hot O or B star, for example) is tried on up to five whole systems. If none of them has it, system exits with an error and saves nothing.

System specification files

--system-file/-f loads a JSON file describing exactly what to generate. Any key may be omitted, in which case that aspect is generated normally. The tri-state options above become true/false/omitted JSON keys, e.g.:

{
  "star_type": "G2V",
  "name": "Sol",
  "age": "young",
  "num_orbits": 5,
  "stars": 3,
  "max_stars": 12,
  "habitable_world": true,
  "asteroid_belt": true,
  "slots": [
    {"type": "planet", "planet_class": "M", "moons": 1},
    {"type": "asteroid_belt"},
    null,
    {"type": "planet", "planet_class": "J", "moons": 4},
    null
  ]
}

slots is an optional, per-orbit list: each entry is either null (generate that slot normally) or an object with a required "type" ("planet" or "asteroid_belt") and, for planets, an optional "planet_class" (e.g. "M") and/or "moons" (an exact moon count, 0 for none). The list doesn't need to cover every orbit — slots past the end of the list are generated normally too.

Sector Generation

planetgen sector generates a whole sector of independently-random star systems in one pass, reusing planetgen system's own generation logic for each one:

planetgen sector [options]

Some of system's options work here too, and apply uniformly to every system in the sector: --star-type G2V makes every star in the sector a G2V, and so on. The +name/-name forcing options are for a single system only: sector and galaxy refuse them with an error naming the option (a saved or queued command line that still has one gets the same message). --system-file, --num-orbits, and system's own per-system --name aren't offered here either, since those describe one specific, hand-crafted system rather than a sector of varied ones; use planetgen system for that.

Sector-specific options:

  • --num-systems <int>: How many star systems the sector contains. Defaults to 10.
  • --name <name>, -n <name>: Hard-sets the sector's own name, overriding the default random two-word name (e.g. "Voranthis Kelmoor") generated the same phoneme-salad way as star names.
  • --density <x>: Scales the number of systems by a multiplier on the real local stellar density (1.0 is a realistic sector this size, 2.0 twice as dense). The count is drawn from a Poisson distribution, so it still varies from sector to sector. Cannot be combined with --num-systems.
  • --min-habitable <int>: Guarantees at least this many systems in the sector have a habitable world, chosen randomly among them — without forcing every system to have one. Extra systems can still turn out habitable by chance on top of this minimum. Cannot exceed --num-systems.
  • --directive <minimum>, --directive-attempts <n>: Redraws each sector until it holds at least this much: systems>=N, habitable>=N or type:X>=N (X is one of O B A F G K M wd bh ns). Repeat --directive for more than one minimum. After --directive-attempts draws (K, tuning.DIRECTIVE_ATTEMPTS, 200 by default) a habitable>=N minimum still missed is met by a forced fill (GEN.180): the sector is built once more with --min-habitable N, a habitable world forced into N systems (the sector then has N systems at least), and the run says met_forced; any other minimum the closest draw misses is reported as unmet with the closest sector kept. A minimum no sector can reach (a sector of 3 systems asked for 9, or a habitable count the compound-Poisson table puts below one in a billion and that the forced fill cannot reach) is refused before any drawing, with the reason, as a usage error; a galaxy or sectors run is judged against its densest possible sector.
  • --star-mix <single> <close> <wide>: The share of systems, in percent, with one star, a close binary and a wide pair; the three must total 100. It replaces --prevalence for binary_system and wide_binary, which it cannot be combined with.
  • --num-sectors <int>, --yes, --estimate-only, --workers <int>, --strict: A run of more than one sector works as a galaxy run does (see Size and time estimates and Parallel generation); --strict turns the warnings the console would otherwise go ahead after into errors that stop the run with nothing generated.
  • --prevalence <feature>=<percent>: Makes a feature more or less common across every system the run generates, as a percentage of its normal chance: --prevalence comets=+50 gives 1.5 times as many systems with comets, --prevalence binary_system=-100 none at all. Repeat it for more features (also on galaxy). The features are the forcing options' names: habitable_world, asteroid_belt, comets, large_star, moons (each planet's chance of moons), max_planets (the chance a star gets the most orbits it can hold), intelligent_life (the population pass's chance of a civilization), binary_system, wide_binary, planets and multi_star (the chance of five or more stars: --prevalence multi_star=+100 doubles it, -100 allows none; GEN.267). Each system stores the setting with its config. --max-stars <int> sets the cap on the star count for every system (see system); --stars is for a single system only and is refused here.
  • --mysql-host <host>, --mysql-port <port>, --mysql-user <user>, --mysql-password <password>, --mysql-database <database>: Where the generated sector is saved. Each defaults to the matching $PLANETGEN_MYSQL_* environment variable, or a built-in default (127.0.0.1:3306, user/database planetgen) -- see database-schema.md.

Each run saves the whole generated sector — every system, star, planet, moon, and asteroid belt, plus any exotic phenomena — to the MySQL database described in database-schema.md, printing only a short status line and summary per saved sector to the console (--debug shows more). The wiki page is rendered from those rows whenever it's viewed, not stored.

Sector-Level Exotic Phenomena

Every generated sector also seeds a realistically sparse population of exotic phenomena: black holes, neutron stars, nebulae (including molecular clouds and planetary nebulae), supernova remnants, rogue planets and free-floating brown dwarfs, and interstellar comets. Each type is drawn per star from the research densities in design/systems/interstellar-object-rates.md (program_constants.PHENOMENON_DENSITY_PC3, with a PHENOMENON_RATE_SCALE dial per type), so most sectors hold none of the rarer kinds, as real space this size usually doesn't. Isolated asteroid fields are not generated in sectors (they disperse); planetgen phenomenon --type asteroid-field still makes one on request. In a galaxy, molecular clouds (classes M-Q) belong to the galaxy rather than to one sector: they are drawn per 50 pc cell from the galaxy seed, more on the spiral arms and near the plane, and a sector gets every cloud that reaches it, stored once whichever sector it reaches is generated first (GEN.47). On an arm at the Sun's distance about one sector in eight sits in one, between the arms about one in twenty-five. Nebulae come with the stars that make them: every O star and half the B0-B2 stars sit in an H II region, and every planetary nebula has its own new hot white dwarf at the center. A galaxy's nucleus is active 10% of the time (program_constants.QUASAR_ACTIVE_NUCLEUS_CHANCE): then the core ball (shell 0) gets a quasar at the galactic center; otherwise it gets a quiescent supermassive black hole.

Black holes and neutron stars are real, stellar-mass gravitating bodies, so they're placed the same Hill-sphere-aware way every star system itself already is: never within a neighboring star system's or another compact remnant's own Hill sphere (see "Minimum separation (Hill spheres)" in planetgen/galaxy/sector.py's own module docstring). Every other phenomenon type has no comparable gravitational footprint at this scale and is placed at a random point in the sector's cell instead.

Galaxy Generation

planetgen galaxy generates and persists many sectors as one galaxy, placed in real galaxy-frame 3D space (see docs/design/galaxy/spherical-sector-coordinates.md):

planetgen galaxy --shell I [--band J [--wedge K [--radius-pc R]]] [--limit N | --yes] [options]
planetgen galaxy [--shells A:B] [--bands C:D] [--wedges E:F] [--limit N | --yes] [options]
planetgen galaxy --block M.SHELL.BAND.WEDGE [--limit N | --yes] [options]
planetgen galaxy --center-sector ID --radius-pc R [options]
planetgen sectors --around X Y Z --radius-pc R [--grow-shells K] [--unit-sectors N] [options]
planetgen galaxy (--center-sector ID | --shell I --band J --wedge K) --region [options]
planetgen galaxy --course FROM TO [--course-border] [--yes] [options]
planetgen galaxy [--radius-pc R] [--max-shell I] [--neighborhoods N] [options]   # random start

It reuses planetgen sector's own generation logic per sector, so a sector generated here and one generated by planetgen sector directly are built by the same code path — the only difference is a real galaxy-frame position (and, in turn, the same sparse exotic-phenomena population every sector gets — see "Sector-Level Exotic Phenomena" above).

Sectors sit on a spherical grid with one standard sector size, 4 parsecs (about 13 ly). The core is a ball, shell 0; every other shell is a hollow sphere 4 pc deep around it, numbered outward from 1. A shell is cut into bands (horizontal strips of latitude, signed: band 0 is the equatorial band that holds the galactic plane, positive bands are north, negative south, and the two end bands are the circular polar caps), and each band is cut into wedges (vertical slices from pole to pole). A sector is one (shell, band, wedge) address. Every band of every shell has 6 times m wedges, where m has no prime factor above 7 and is picked so each sector is close to 4 pc across. The grid covers all of space out to its reach (262 kpc by default); the galaxy's outline (below) says where the disk and bulge expect a system, which is where random starts, the maps' planned sectors and a neighborhood around an outline sector look: every shell out to the last one whose equatorial band could still hold a star, and in each shell the bands the galaxy still expects a star in. A sector that is asked for outside it is generated from the profile of its place (galaxy/profile.py).

--shell I generates every not-yet-generated sector in shell I that the outline holds; adding --band J narrows it to one band, and adding --wedge K too generates exactly that one sector (and, with --radius-pc R, its neighborhood within R parsecs as well). A single address is generated wherever the grid's reach holds it, inside the outline or out in the halo (its density comes from the sector's profile, so a halo sector is usually saved empty); one beyond the reach, or in a band its shell does not hold, stops with exit status 1, and one that was already generated reports its sector ID. A range named in a span (--shells, --bands) is taken as named anywhere in the reach; a span with no range means the outline's cells. A --center-sector neighbourhood around a halo sector takes every cell of the reach within the radius and says how many sectors that is, and how many systems they expect, before it runs. A whole shell is usually thousands of sectors, so past 2,000 sectors a run needs --limit (generate only the first N) or --yes. The span form picks sectors by range instead: --shells FIRST:LAST, --bands FIRST:LAST (negative south of the equator, so write --bands=-2:2) and --wedges FIRST:LAST (only with exactly one shell and one band; a range whose first is past its last wraps through wedge 0, as in 50:5). Each of the three defaults to everything the outline holds, so --bands alone fills those bands out to the galaxy's edge. --block M.SHELL.BAND.WEDGE (GEN.310) fills one block of the Galaxy Map's ladder, given by the key the map's stage links carry (m is 243, 81, 27, 9 or 3; docs/design/galaxy/spherical-block-ladder.md): every not-yet-generated sector that the stored outline holds inside the block, shell by shell outward so the inner sectors come first, with the same estimate, progress and cancel as a shell or a span, and --limit and --yes as for them. The map starts the same fill through POST /api/galaxy/blocks/<key>/generate. A block the outline does not reach holds nothing to generate. It cannot be combined with --shell, --band, --wedge, a span, --radius-pc or --center-sector. --around X Y Z --radius-pc R (GEN.1128, region mode) generates every not-yet-generated sector a sphere of R parsecs around the point (parsecs from the galactic center) touches: a sector is in when its center is within R plus three quarters of a sector edge. --grow-shells K adds K whole shells of one edge. The sectors are cut into units of at most --unit-sectors (default 27) consecutive wedges of one shell and band, the nearest unit first; a unit is the retry and resume grain, and a rerun after a stop builds only the sectors not saved. The same seed gives the same sectors whatever the point, the radius, the unit size or the order regions are run in. It cannot be combined with another mode, --limit or the random-start options. --center-sector ID --radius-pc R generates every not-yet-generated sector within R parsecs of an already placed sector's own center, the sector at the center first and the rest outward (GEN.101): the sectors are laid on a lattice of one sector edge around the center, cut into blocks of four sectors a side, and the blocks come nearest first, in Hilbert order among blocks the same distance away and inside a block, so the same neighbourhood always fills in the same order. A ball cannot always be walked step by step between neighbouring sectors, so the run says how many of its steps are not (a step of more than two and a half sector edges), with their mean and longest length: about 97% of them are between neighbours in a 50 pc ball. --region (GEN.826) with --center-sector or --shell --band --wedge fills one whole region: the center moves to the anchor sector of the region (the 9-block of the map's block ladder, about 780 sectors) that holds it, and the standard 12 pc sphere about that anchor (about 109 sectors) is generated, so the finished run charts the region and the map names it. It takes the place of --radius-pc, which it refuses; a --center-sector run with it generates the anchor sector first when it is empty, as the single-address mode does. The Generate page's "This region" box asks for it. --course FROM TO (NAV.48) generates the uncharted sectors that block the NAV course between two objects (a system's object ID, or <kind>:<ID> for a body or phenomenon): the cells of the route's hops through unknown space, inside the galaxy's outline, not every cell on the straight line. --course-border adds the uncharted cells that share a face with them. Past 5,000 sectors it needs --yes; the size and disk checks are the same as for any run. The NAV page (/nav/chart, admins) starts it as a Generate page job.

Run with none of --shell, --shells, --bands, --block, --course and --center-sector (random-start mode, no arguments at all), planetgen galaxy picks a uniformly random (by volume) sector address inside the galaxy's planned outline in a region with no generated sector yet (GEN.826), starts at the anchor sector of that region (at the drawn address where the anchor is outside the outline's reach or beyond --max-shell), generates it, and then generates every not-yet-generated sector within 12 pc (about 39 ly) of it too, in every direction — a whole small starmap around a fresh, randomly chosen starting point in one run. Every sector any galaxy mode generates (and every sector the map generates on a visit) first gets the bright stars around it: each sector within 100 ly is given every star from its distance tier's floor up to what was already placed there, once per sector, leaving filled sectors alone (GEN.23, GEN.44). --max-shell bounds how far out the random starting address can land (defaults to anywhere inside the galaxy's stored outline), --radius-pc overrides the default 12 pc neighborhood radius, and --min-start-density requires the randomly chosen starting sector's own real density to be at least that many times local (e.g. --min-start-density 1.0 for at least as dense as the galaxy's own real local density) before accepting it, retrying otherwise — useful for skipping past the galaxy's own vast, sparse outskirts to start somewhere with more to look at. A high threshold combined with a large --max-shell can take many retries to satisfy, since a volume-weighted random draw favors the sparser outskirts to begin with. --neighborhoods N generates N random neighborhoods instead of one; each start lies inside the galaxy with its whole neighborhood and at least twice the radius from every other start, so they never overlap. --neighborhood-gamma G biases the starts toward dense space (a start is kept with probability min(1, relative density)^G; the default 0 keeps every one, so starts are uniform by volume), and --avoid-filled-space drops any start whose neighborhood touches a sector that is already generated.

Each of these has an upper bound, so a typo can't start a run that never ends: --radius-pc at most 200 (about 650 ly), --shell, --shells and --max-shell at most 100,000, at most 100 --neighborhoods, and --limit at most the number of sectors in shell 100,000. The web Generate page and the API check the same bounds (src/planetgen/generation/limits.py).

A galaxy run does every stage (PERF.123), with no option to leave one out: the sectors, the link to their neighbours, the galaxy-wide scatters, the backfill, the population pass, the territories pass and the paths. After the sectors it scatters the bright stars galaxy-wide, as planetgen scatter --mass and scatter --luminosity do, and then the phenomena, as scatter --phenomena does, leaving out every sector already generated, so the scatter never draws stars for sectors the run filled; --bright-star-min-luminosity (9000 solar luminosities by default), --phenomenon-min-mass and --compact-min-mass set the scatters, as on scatter, which is described below. Once every sector of the run is generated, the bright stars around the run's edge are backfilled: four steps outward around the generated sectors (a face apart, no diagonals) get every star born from 1 solar mass up in the nearest step, 2 in the next, then 5, then 8, and a sector already generated never gets any. Last it saves the path every star system, rogue planet and comet takes through its sector, for the sectors it created and the ones around them. Whoever wants fewer stages runs the commands in turn: planetgen sectors, then link, scatter, backfill, population, territories and settle, as the Generate page does.

Parallel generation

planetgen sector (with --num-sectors) and every planetgen galaxy mode fill several sectors at once, each in its own worker process: by default 80% of the machine's cores, one fewer when MySQL runs on the same machine (3 workers on 4 cores without a local MySQL, 2 with one). Workers run at a lower priority (nice 10), so the web site and anything else on the machine come first. Each worker generates a whole sector and saves it in one transaction; the run prints each sector as it's saved, so sectors can finish out of order. --workers N sets the count (PLANETGEN_WORKERS does the same for every run), and --workers 1 generates one sector at a time in the run's own process, as before. The workers are RQ workers on the Redis server at redis.url (config.md), started by the run for its own tasks and gone when it finishes. Without a Redis server the run says so and generates one sector at a time. A task whose worker dies (killed, out of memory) runs once more on a fresh worker before the run fails. On a 4-core machine with MySQL local, 60 sectors of one ring of the old cylindrical grid took 16.5 s on one worker and 9.8 s on the default two (the grid has since changed; the speed per sector has not been measured again).

planetgen plan draws its bright stars the same way, one shell of the galaxy per task, densest shells first (--workers works there too). Each shell draws from its own random stream, so the same seed places the same stars on any number of workers. The seed is the galaxy seed that planetgen plan --seed <32 hex digits> sets (see "The galaxy seed" under Size and time estimates); each shell's stream comes from it and the shell's address.

Every progress bar shows the time elapsed and the time remaining until it's done. The remaining time comes from a decaying average of how many sectors (or shells) finished per second, weighted toward the last minute or so, so it follows the run's current speed and doesn't jump about when several workers finish at once. The Generate page shows the same estimate ("about 4 m 10 s left").

A galaxy or plan run that does more than one stage also draws one "Whole job (stage 3 of 7)" bar at the top of the display (PERF.55). It counts the time since the run began against the stored time of all its stages (the same stage times the Generate page's overall bar uses), so it shows the time left across every phase; with no stored time for a stage it shows only the elapsed time. A run that outlasts its estimate keeps the bar just short of full. When the run ends it stores two more rows in the stage history, with the run's settings: "Whole job" (the seconds of the whole run, the stages it ran and the shells the scatter stages visited, those that placed nothing included, per second; generation_stats.job_shells_per_second) and, when scatter stages ran, "All scatters" (their operations, shells, objects and seconds, per shell and per operation). Each stage's own row also carries its seconds per shell. A scatter with no stored time of its own is estimated from the "All scatters" figure, so every bar and estimate reads the one stored-time function (generation_stats.stage_seconds).

The bright-star bar ("Bright stars (12 of 1,271 shells)") shows a share done rather than a count: before the scatter starts, every shell gets an expected star count from the same density model the scatter draws from (a quick sample of its bands, a second or two for a whole galaxy), plus a small allowance per band, so the nearly empty outer shells count for little and the dense inner ones for a lot. Shells in progress report their stars a few times a second and the bar moves with them, so the time left follows the work left rather than the shells left. While shells take longer than 30 seconds each, a second bar appears under it with the stars of the shells being drawn, done of their estimate, and its own time left ("Shell 0: stars"); it goes again once shells finish faster than one every 20 seconds. Sector fill keeps its one bar. The Generate page shows both lines too.

Only one run's workers use the machine at a time: a run started while another is generating (from the command line or the Generate page) says it's waiting and starts when the other finishes (PERF.154: it takes a place in the one waiting list in Redis, up to queue.max_waiting entries, 8 by default, shared with the Generate page's waiting jobs; a run past that is refused with the list named, and one that has waited queue.wait_minutes fails naming the run it waited for). Redis keeps the run and its units (the run record, planetgen/queue/runrecord.py); the Queue page reads them from there. A run stopped with Ctrl-C, or Cancel on the Generate page, stops its workers mid-sector (each sector is saved in one transaction, so an unfinished one is rolled back, never half written), queues nothing more and is recorded as canceled, and the machine is free at once; a run that was killed outright is cleared once it shows no sign of life. A worker that dies fails the run.

Size and time estimates

Before a bulk run writes anything (planetgen galaxy in every mode, planetgen sector --num-sectors), it works out how big and how long it will be and prints it:

Estimate for shell 12: About <size> and <time> for <N> sectors (~<n> star systems,
~<n> stars, 2 workers). <free> GB free of <total> GB.

(The figures depend on the galaxy, the density and this server; the line names the run, shell 12 band 0 for a single band, and so on.)

  • Systems come from each sector's expected density (the galaxy's skeleton, or --density/--num-systems).
  • Size is those systems times this galaxy's own bytes per system, measured from its tables after every run (about 62 KB on a test galaxy, over half of it moons), plus 10%.
  • Time adds up each sector's expected systems times this server's measured seconds per system at that density, divided by the workers. The speed is kept per density bucket (two per decade from 0.01) as a decaying average of every sector ever filled, in the control database (generation_stats), so dense sectors aren't priced like sparse ones. Until a bucket has been measured the nearest measured one is used, and before anything has been measured a default of 0.2 s per system (the estimate says so).
  • A run of more than 20,000 sectors is estimated from 200 of them, spread evenly through the run, and the line says so ("worked out from 200 sampled sectors"); its sectors are resolved as they are queued, never all held in memory. A radial fill (--center-sector and --radius-pc) asked for by the Generate page's estimate, or the sector page's neighborhood action, stops at 2 million sectors in the ball and says to choose a smaller radius; the command line has no such limit.

On a terminal, a run of more than one sector then asks Generate these N sectors? [y/N] (--yes skips the question). Off a terminal (the Generate page's jobs, scripts and cron) it prints the estimate and carries on; the Generate page shows the estimate and asks first.

A run is refused, with nothing written, when it would take more than a quarter of the database disk or leave less than 5 GB free; the message says how much it needs. The disk is the one holding MySQL's data directory, asked of the server itself (SELECT @@datadir) and never assumed to be the boot drive; the estimate names the path and the mount measured, with symlinks and bind mounts resolved. A server on another machine is measured only if that directory is visible here; otherwise the disk shows as "unknown" with the reason and nothing is refused for space. --yes never overrides a refusal; generate fewer sectors (--limit, a smaller radius) instead.

--estimate-only prints the estimate (and any refusal) and stops without writing anything, ending with one ESTIMATE {json} line. In random-start mode it is the estimate for one random start, so the real run's start (drawn again) differs.

Most of the galaxy is never actually visited or generated; planetgen plan builds a small, cheap-to-recompute density "skeleton" (one singleton shape row plus one row per shell, from the core outward, naming the highest band that shell reaches; the outline is symmetric about the plane) that planetgen galaxy consults to decide, per address, whether anything exists there at all before generating it lazily on demand (the galaxy_shell table in database-schema.md). Every planetgen galaxy mode checks its address against this outline before generating anything, even when --density or --num-systems is given, so nothing is ever placed outside the galaxy: an address outside it is refused with the reason, and a neighborhood near the edge simply leaves out the sectors past it. planetgen galaxy refuses to run until planetgen plan has been run.

The galaxy seed. The first planetgen plan stores the galaxy's 128-bit seed, shown as 32 hex digits (Galaxy seed 3F2A...C901 (drawn at random)). --seed <32 hex digits> sets it instead; a later plan keeps the stored seed, and a different --seed is refused once any sector exists. Each sector, the bright-star scatter, each band added with scatter --band and each backfill block draws from its own seed, the SHA-256 of the galaxy seed and its address (sector:12/3/0 is shell 12, band 3, wedge 0), so one seed fills a sector the same way at any --workers count and in any run that reaches it, on the same PlanetGen release. Two systems that draw the same name are still told apart in save order, and the bright-star backfill still depends on which sectors are filled first (both phase 1, GEN.57). The galaxy also records the version key of the code that made it (22 hex digits: release, Python version, OS and architecture), and every run that changes it adds a row to generation_runs (command line, the run's own seed, version key, start, end and outcome; DB.6). Every run's first line names the galaxy seed, the release with its key, and the command line without the --mysql-* and --debug options, for example Galaxy seed 3F2A...C901, PlanetGen 7.127.352 (0007007F000160030C0300), run: galaxy --shell 3 (none yet before the first plan; OPS.10). It goes to the console, the --debug file and the debug log, and a Generate page job's log starts with the same line for the job before its first step. The Generate page shows the same line under the shape dials; it asks /admin/generate/shape-report, which works the numbers out with the same code (generation/plan_outline.py).

The galaxy holds the systems its stellar mass makes (no point of it is pinned to the local density, GEN.404). --max-shell caps how far out the shells are walked (100,000 by default) and --seed <32 hex digits> sets the galaxy seed. --workers is how many shells of bright stars are drawn at once.

planetgen scatter places the galaxy's stars and phenomena on the stored outline, before any sector is filled (PERF.121). It draws exactly one kind of scatter per run, so each kind is a command of its own that a job can queue, retry or leave out:

  • --mass places every star born at the stellar mass limit or more, whatever its luminosity. --phenomenon-min-mass is one of 8, 10, 12, 14, 16, 18 or 20 solar masses (14 by default).
  • --luminosity places the stars born lighter than the mass limit that are at least --bright-star-min-luminosity bright: from 2500 to 4,000,000 solar luminosities, 9000 by default (the Generate page offers presets). A lower level places far more stars and takes longer, and the run prints an estimate first. It works at the mass limit the mass pass stored, and stops with "run 'planetgen scatter --mass' first" when there is none.
  • --phenomena places the neutron stars, black holes and the rest. --compact-min-mass is the lowest mass of a neutron star or black hole placed galaxy-wide: one of 1, 2, 4, 6, or star for the stellar limit, which is the default. A lower limit stores far more rows, and scatter --help lists the sizes. The stars are left alone and the central black hole or quasar is always rebuilt.
  • --nebula-field draws the nebula_field table of molecular clouds again from the galaxy seed.
  • --band --down-to N adds a band of dimmer stars (described below).

Each star is a finished star at a fixed point in its sector, stored in bright_stars, so the Galaxy Map can show the bright stars tracing the spiral arms right away. Filling a sector later builds a full system around each of its bright stars first, then draws the rest of its systems from dimmer stars only, so its expected total is unchanged. Every system's age comes from the stellar population mix where its sector sits (young stars crowd the arms near the plane; the bulge is old). Every option belongs to one kind and is refused with another. planetgen plan takes none of them, and a plan alone places no stars (and empties what an earlier plan's scatters left); galaxy runs the kinds as steps of one run.

A scatter draws only where none of its kind is stored (Boss's F7): it stops and names the clear to run first, so nothing is replaced by accident. planetgen clear-scatter empties one kind and nothing else: --mass (refused while the bright stars are stored, which are split from the massive stars at the mass limit, so clear --luminosity first), --luminosity (the band goes with it), --phenomena or --nebula-field. To redo a scatter at a new setting, clear it and draw it again; to change the mass limit, clear --luminosity and --mass, then draw --mass and --luminosity. Clearing a kind with nothing stored says so and changes nothing.

--cell-star-ceiling and --fill-luminosity-cap (GEN.281, plan) set, for the whole galaxy, how deep a crowded cell is filled: a cell that expects more systems than the ceiling (default 5,000) is filled only with the stars at or above the cap (default 100 solar luminosities, raised for a cell those stars would still fill past the ceiling, never under the brightest white dwarf), and the rest is reported as unresolved on its sector page and in the API (unresolved). Ordinary space never reaches the ceiling. Both are stored with the galaxy and apply to sectors generated afterwards. --core-min-luminosity, --core-mass-limit and --halo-min-luminosity (DB.54, plan) store the scatter limits by place: the core's luminosity floor and mass limit (unset, they are the baseline's times 1.1, 9,900 and 15.4 at the defaults) and the halo's luminosity floor (default 500, from 50 to 4,000,000; the halo has no mass limit of its own). The tiers that read them are GEN.333's. The satellites and clusters (galaxy_components) are drawn only by a full plan, so a galaxy planned before GEN.159 and GEN.237 has an empty component table until a full plan runs. --timing (plan, UX.162) prints a table of where the plan's time went, step by step with its share, the costliest first; --debug prints it too, and a plain plan does not. The measured cost of a full scatter is in generation-performance-study.md.

planetgen clean-nebula-field (GEN.205) brings an existing galaxy's stored molecular clouds in line with the current nebula keep rates (tuning.NEBULA_FIELD_KEEP): without --apply it counts, per class, the stored field clouds the rule now rejects and changes nothing; --apply deletes them (everything inside them loses its inside_nebula_id, and containment is refreshed in the sectors they reached). A nebula that was not made by the field is left alone. planetgen scatter --nebula-field then draws the nebula_field table again.

planetgen sectors (PERF.123) is the sector-generating part of galaxy as a command of its own: it takes every mode and sector option galaxy does (--shell, --band, --wedge, a span, --course, --center-sector, the random-start options, --limit, --yes, --estimate-only, and the generation options) and none of the later stages' options (the scatter limits). It saves the sectors unlinked and says the run's start time on the database's clock; planetgen link, backfill and settle then take that time as --since.

planetgen link, planetgen backfill and planetgen settle (PERF.123) are the last three stages of a galaxy run as commands of their own, each for the galaxy sectors saved at or after --since TIME (YYYY-MM-DD HH:MM:SS on the database's clock; a sectors or galaxy run says its start time near its start; without --since, the start of the newest sectors or galaxy run). link links those sectors to their neighbours (containment, nearest systems and quadrants, and the new systems merged into the sectors around them). backfill draws the bright stars out from them, each sector only where it is not drawn yet. settle saves the path of every body in them and in the sectors around them. Each is one run through the work queue, takes only --since, --workers and the connection options, can be run again, and does nothing (starts no run) when no sector was saved since TIME.

The sky tiers (VIEW.25) are part of the backfill: --sky-limit MAG (galaxy, sectors and backfill; 2 to 9, 0 for none; without it the queue.sky_limit setting, 7.5 unless the deployment changed it) sets the limiting magnitude, and for each 50 parsec observer cell the new sectors lie in, the luminosity bands and mass rings of the table for that limiting magnitude (generation/sky_tiers.py) are drawn out to their reach, one sphere at a time in the galaxy, brightest band first, and recorded in sky_tier_draws. A sphere already drawn is not drawn again, and a stopped draw goes on from its last batch. The census line says the rows and the seconds a backfilled sector cost.

planetgen fill-map-luminosity (DB.23, GEN.201) fills phenomenon_scatter.map_luminosity_sol, the luminosity a star of a row's mass would have on the Galaxy Map, for a galaxy scattered before schema v84: id-range batches of 200,000 rows, each its own short statement and commit, resumable (it only fills rows still empty). A new scatter writes the value with each row. planetgen rescore-habitability (GEN.217) re-derives the stored habitability numbers of every planet and moon from its stored conditions: the flux swing of a body in a double-star system (loading that system, as generation does), the PHI-6 index, the six domains and their tiers, the survival equipment levels and the note. It is for a galaxy generated before a change to the rules (GEN.148, GEN.207, GEN.215), so the planet chip, the search page and the facet counts agree with the description, which is worked out from the same conditions whenever a page is drawn. Nothing else is touched; each batch of 500 systems is its own transaction and the result is the same however often it is run, so a stopped run is started again. A gas giant and a body saved before schema v76 (no score) are left alone. Both take only --workers and the connection options. The admin Queue page starts either one from its Start a fill panel (ADM.129). planetgen refill-effect-ledger (GEN.1498) writes again the light and ultraviolet rows of the effect ledger (GEN.1465) of every system from its stored stars, planets and moons, at the floor of the running code (tuning.EFFECT_LEDGER_FLOOR), for a galaxy generated before the ledger existed or before its floor or formulas changed. It takes only the systems whose system_summary.ledger_stamp is not the running code's (--all takes every system), writes nothing but the light and ultraviolet rows and the stamp (the rows of the other effects are left as they are), runs each id range as one transaction, and so can be stopped and run again. It takes --workers and the connection options, and has no Queue-page button yet.

planetgen fill-nebula-blocks (MAP.172) makes the nebula totals of the Galaxy Map's blocks again (nebula_block_stats: for every block of the ladder, the nebulae in it, their volume, centroid, families, dominant class and cover) from the nebula_field table and the stored nebulae, in one transaction. planetgen scatter --nebula-field makes them with the field, and a galaxy run adds the nebulae it stored at its end; this is for a galaxy whose field was drawn before the totals existed, or after anything else changed the nebulae. It can be run again, and takes only --workers and the connection options.

planetgen fill-block-totals (MAP.258, MAP.259) makes the totals of the Galaxy Map's blocks again, in three tables: galaxy_block_stats (what each block's generated sectors hold, with their summed mass, DB.108: the sectors' own masses are made again first, and a sector that holds a body with no stored mass is listed in the log and left out of the sums), region_stats (DB.107: the sectors, share charted and extent of each named region, a 9-block that holds a generated sector) and galaxy_block_lights (the count, summed luminosity, center of light and mean temperature of the pre-placed bright stars and scattered phenomena nothing was built from). A galaxy run brings in the sectors it saved at its end, a scatter, a clear and fill-map-luminosity make the light totals at theirs; this is for a galaxy whose totals were never made, or after a run stopped before it finished. It can be run again (the light is made a unit of shells at a time and each unit is committed), and takes only --workers and the connection options.

The scatter always leaves the sectors that are already filled out (they would never get their bright stars).

The scatter can go down in stages. scatter --band --down-to N keeps every bright star already placed and adds only those from N up to (not including) the galaxy's star-fill level, the threshold already scattered (9000 by default), then lowers that level to N. So a quick test galaxy scattered at 9000 can later go down to 5000 without redrawing anything brighter:

planetgen scatter --band --down-to 5000

Sectors already filled get none of the new stars: their own systems were drawn below the old level, so they already hold stars that bright. Asking for a level at or above the current one does nothing and says so. The Generate page shows the current level and offers the same step as "Add a dimmer step of bright stars".

Exotic Phenomena Generation

planetgen phenomenon generates a single exotic stellar phenomenon on demand, independent of any one sector (see "Sector-Level Exotic Phenomena" above for the population every generated sector gets automatically):

planetgen phenomenon --type {black-hole,neutron-star,nebula,supernova-remnant,rogue-planet,comet,asteroid-field,quasar} [options]

Omitting --type picks uniformly at random among the first seven; a quasar is only made when asked for by name, and --sector-id only accepts a shell-0 (galactic core) sector for one, placing it at the galactic center; there is one per galaxy. --anchor-system (black hole/neutron star only) builds a full star system around the compact remnant instead of describing it standalone — real pulsar planets exist (PSR B1257+12) — reusing all of planetgen system's own orbit-placement logic; since a compact remnant's near-zero luminosity naturally collapses the disk-physics planet-count estimate toward zero (matching the real rarity of confirmed planets around black holes/neutron stars), pass --num-orbits to force orbiting bodies. --sector-id (any type except an anchored one) links the generated phenomenon to an already galaxy-placed sector — for nebula/asteroid-field/black-hole/neutron-star, it also computes a real galaxy-frame position near that sector, instead of leaving it unplaced; other types are linked only (no placement columns of their own) — see database-schema.md's "v18"/"v21" notes. --name <name> forces the phenomenon's name. phenomenon only generates and saves the phenomenon (PERF.124). A black hole or neutron star can bend the paths of the bodies around it, so after --sector-id run planetgen settle --sector-id ID, which saves the paths of that sector and the sectors around it (settle takes --sector-id in place of --since; the two cannot be combined). --debug/--quiet/--silent, and the --mysql-* connection options all work the same way they do on planetgen system.

Population

planetgen population is an optional pass over what is already stored: it names the dominant species of every world with complex life, gives technological civilizations an age and an era (Industrial through Elder) and founds one polity per spacefaring species. Which systems each polity owns (reach up to 100 ly from its capital) is the territories pass, its own command (PERF.125). Neither runs on its own except as stages of a galaxy run.

planetgen population                     # scan what isn't scanned yet
planetgen population --rescan            # forget everything and start over (new names, ages and borders)
planetgen territories                    # work out who owns which system, from the polities stored (run after population)

planetgen sector does not run it (PERF.124: sector only generates; the --population option is gone), and planetgen galaxy runs it, and then the territories pass, as stages. --rescan forgets the polities and with them the territories, so run planetgen territories after it. Each pass is a one-unit command of the work queue (run-population, run-territories). The install scripts offer it (y/N, default N after 30 seconds; POPULATION=1 or -Population runs it without asking). The website hides species, polities and the Galaxy Map's Territories overlay until it has made something to show (GET /api/population). The --mysql-*, --debug and --quiet options work as on the other subcommands. Design and decisions: design/habitability/population-and-politics.md.

Fingerprint

planetgen fingerprint prints a canonical SHA-256 digest of each sector's generated content, one line a sector (shell band wedge digest, unplaced sectors last), then the plan's digest and the region's. Two builds of one galaxy are the same when their digests match; a sector whose line differs is where they part. It writes nothing and isn't logged as a run.

planetgen fingerprint                      # the whole galaxy, plan included
planetgen fingerprint --shell 3 --shell 4  # every sector in shells 3 and 4
planetgen fingerprint --sector 12 3 0      # one sector: shell 12, band 3, wedge 0 (repeatable)

It compares what design/generation/reproducible-galaxies.md section 2 defines: every object's address, position, properties and name, with their child rows and the cell's bright stars and phenomenon scatter. Row ids, timestamps, each row's update clock, the nearest systems and the location text written from them, sector paths and stats, population data and bookkeeping are left out; a foreign key counts as what it points at (a sector's address, an object's unique ID). It reads the galaxy as stored; comparing a rebuild with the stored galaxy is internal testing only.

Check the database

planetgen check-db looks for damage and changes nothing: the schema revision, table health (CHECK TABLE), rows without parents, ids, impossible values, sector counts and version keys. It ends with one pass or fail line per check, exits 1 when it found damage and 2 when a check could not run (DB.8, DB.21, PERF.126). The Generate page runs the same checks.

Each check is a command of its own (check-revision, check-tables, check-tables-extended, check-orphans, check-ids, check-values, check-counts, check-version-keys, check-storage, check-systems, check-object-index; planetgen commands lists them). check-db only builds the list of them and the wrapper queues them one after the other as a check run on the Redis queue, so it needs Redis (and a worker running as part of it) like every queue run, never holds up a generation run and shows no banner to the site's visitors. Name the checks to run only those. object-index is not in the default list: it compares the object index with the tables (PERF.140) and warns when the index has not been built yet.

planetgen check-db                              # the default checks, the whole database
planetgen check-db ids orphans                  # only those checks, in the order the list keeps
planetgen check-db --shell 12                   # values, counts and version keys of one shell's sectors (repeatable)
planetgen check-db --sector 12 3 0              # the same for one sector: shell 12, band 3, wedge 0 (repeatable)
planetgen check-db systems --estimate-only      # print the time the systems check would take, then stop
planetgen check-db tables-extended systems --yes   # the slow checks: CHECK TABLE ... EXTENDED, then every star system
planetgen command-run check-ids '{"database": {...}}'   # one check alone
  • Without a name the list is revision tables orphans ids values counts version-keys storage; tables-extended (CHECK TABLE ... EXTENDED) and systems (validates every star system) are the slow ones and run only when named.
  • systems is slow, so its time is estimated first and a yes is asked for; --yes goes ahead after the estimate without asking (needed off a terminal), and --estimate-only prints the estimate and stops (the Generate page uses it).
  • --wide-binaries (with systems): validates only the wide binaries (S-type pairs), to count the pairs whose orbits overlap (GEN.228).
  • --shell and --sector scope values, counts, version-keys, storage and systems; the other checks always look at the whole database.

Version keys

planetgen versions lists the version key each update recorded for the galaxy database, newest first (OPS.13): the release, the Python version, the operating system and the architecture that made the galaxy, in the 22 hex digits explained under the galaxy seed. It takes only --mysql-*, --debug and --quiet.

Benchmark

planetgen benchmark times a small galaxy from the plan to the finished fill in scratch databases and prints the time and database work of every stage, at each worker count asked, with an optional profile of the fill (PERF.31). It makes a scratch database and a scratch control database, runs the real plan and galaxy commands against them in child processes with a fixed seed, and drops both afterwards unless --keep is given; nothing is written to the real database.

planetgen benchmark                          # 2 sectors in shell 12, one worker
planetgen benchmark --sectors 20 --workers 1,2,4 --profile --output bench.json
  • --sectors N: the sectors the fill makes (2 by default). --shell I: the shell the fill starts in (12 by default; a lower shell is denser). --max-shell I: the plan's outermost shell (12 by default, a small galaxy). --seed HEX: the galaxy seed (32 hex digits).
  • --workers N[,N...]: the worker counts to run at, one run each (1 by default).
  • --profile: also profiles one single-worker fill and lists its costliest functions. --keep: leaves the scratch databases in place. --output FILE: writes the results to FILE as JSON.
  • --suite: the performance suite of every generation option instead (below).

The performance suite

planetgen benchmark --suite (PERF.146) times every part of a galaxy run on its own, at a size you pick, in scratch databases of its own, and writes the result as JSON for the next run to compare with. Where planetgen benchmark times one small fill, the suite runs these steps one after another, each as the real command in a child process (so a worker's cost is in it): plan, scatter-mass, scatter-luminosity, scatter-phenomena, scatter-nebula-field, scatter-band, fill-nebula-blocks, fill (one planetgen galaxy --shell run, with the time of each stage it records), population, territories, rescore-habitability, fill-map-luminosity (after emptying the column it fills) and warm.

planetgen benchmark --suite --size small --workers 3 --output small.json
planetgen benchmark --suite --size medium --repeats 3 --output medium.json
planetgen benchmark --suite --size small --steps plan,scatter-mass
  • --size tiny|small|medium|large: the galaxy's stellar mass, which sets the clusters, shells and stars every step meets: tiny 2e6 solar masses (for tests), small 3e7, medium 4e9 (a default-size galaxy) and large 5e10 (Milky-Way size). --mass M_SUN and --fill-sectors N replace the size's own numbers. --seed HEX is the galaxy seed, fixed by default, so two runs make the same galaxy.
  • --steps STEP[,STEP...]: only these steps, in the suite's order; a step needs the ones before it to have run, so a list starts from plan.
  • --repeats N: runs the whole pipeline N times in fresh databases and reports each step's fastest, median and slowest run and the spread.
  • --step-timeout MINUTES (240): a step still running then is stopped and recorded as not finished; later steps are not run.
  • Each step prints a line when it ends, so a run that is stopped (a container restart, a closed terminal) keeps what finished. A run in which a step failed, did not finish or was stopped leaves its scratch databases (planetgen_suite_<SUFFIX>_r0 and planetgen_suite_control_<SUFFIX>, the suffix printed at the start). --resume SUFFIX carries on in them: give --steps the steps left to run (a step that was stopped in the middle may need planetgen clear-scatter of its kind first). Drop the two databases by hand when done.
  • Each step records the wall time and its share of the run, the CPU the machine spent (less the database server's and Redis's own share), the statements and rows the database server counted, the peak memory of the generation processes (together and the largest), what it made (stars, systems, rows) and the time per thing made, and the stage rows the command stored.

The suite stops the queue workers before and after each step, so every step starts with cold ones, and it turns the automatic cache warm-up off (PLANETGEN_WARM_ON_CHANGE=0). The machine must be the suite's alone while it runs: the CPU and database counters are the machine's, and the Redis queue is the real one. It needs Linux (/proc), the Redis queue and a database account that can create databases. The numbers of a run, the ranked costs and the optimizations they led to are in design/generation/generation-performance.md.

Warm the caches

planetgen warm builds the site's caches so the first visitor after a release does not wait for them (MAP.134, PERF.104, PERF.127; design in cache-warm-up.md). update.sh runs it in the background after every update; run it by hand after clearing a cache, as the web server's user so Apache can read what it writes. Each cache family is a command of its own, listed by planetgen commands and runnable alone with planetgen command-run KIND ARGS: warm-cluster-field (the galaxy's cluster field: the mean system mass of each age worked out in small parts, then the field kept as a file in the state folder that the web reads; PERF.225), warm-object-index (the object index: one row per object of every kind the site lists, written when it changed since the last run; built whole after planetgen orbits or a new epoch, because those move objects between sectors without touching their rows' modified_at; PERF.140), warm-galaxy-map (the opening nodes and stage, the shape, the sector and phenomena lists), warm-galaxy-nodes (the Galaxy Map's sector-block nodes: every populated block of level 243 and above, cut into chunks of 64 nodes that the workers build; PERF.130, MAP.260), warm-galaxy-deep-nodes (the zoom run in to the galaxy's center, down to blocks of tile_cache.warm_zoom_floor shells; PERF.141, MAP.261), warm-lists (the first page of every list and its counts), warm-sectors, warm-systems and warm-phenomena (every page of that kind, nearest the galaxy center first, up to page_cache.warm_max_objects of each) and warm-search. planetgen warm only builds the list of them (every family in that order, or the families named) and hands it to the wrapper, which queues them one after the other on the Redis queue as a maintenance run: it does not wait for a generation run, holds none up and shows no banner to visitors. A list of every family ends with end-map-rebuild-maintenance, which opens the site if the sector-grid switch closed it (UX.112). It waits for a running update to finish, prints one line per family (how many pages it warmed, how many answers it built, how many were already cached and how many the cap left out), and exits 1 naming the command that failed, or when Redis does not answer or another warm-up is running; there is no silent skip.

planetgen warm [FAMILY|PHASE ...] [--cap N]

The warm-up runs in five phases (PERF.141): opening (object-index, galaxy-map, lists: the object index, the opening views and the first page of each list), built-levels (galaxy-nodes), deep-nodes (galaxy-deep-nodes), objects (sectors, systems, phenomena) and search. After each phase it prints one line: what it built, what was already stored, what the cache budget (cache.max_mb) or the cap left out, or unchanged, nothing built when the data under it has not changed since the last run. After a generation run, planetgen orbits, an edit or any other change that moves a data version tag it also starts by itself in the background (planetgen warm --on-change DATABASE, which waits cache.warm_settle_seconds for more changes and then warms once; off with cache.warm_on_change, never during an update). FAMILY is any of the families above and PHASE any of the phase names, a phase standing for all its families (the list is those, in order, whatever order they are named in); --cap overrides page_cache.warm_max_objects.

Stop everything

planetgen queue stop-all (PERF.186) is the emergency stop, the same routine as the Stop everything button on the admin Queue page. It writes a hold in the state folder (stopped.json, which survives a restart of Redis, the web server and the host), cancels the Generate page's job and every live run, empties every queue, and ends every planetgen worker, job runner and command process on the host together with the processes they started (SIGTERM, then SIGKILL after five seconds, looking again for what the dying ones started). While the hold is on nothing starts: no worker, run, Generate job, orbital update or cache warm-up, and the site's map prefetch queues nothing; a worker that is still alive ends before it takes a job. planetgen queue resume lifts the hold (and the queue pause); planetgen queue status says whether it is on and how many planetgen processes run. Run it as root so every process can be ended; the pids it could not end are listed and the command exits 1. --no-hold ends everything but leaves no hold, which is what sudo ./update.sh --kill-all runs before the update guard. It works with no Redis answering, and python3 -m planetgen.cli.queue stop-all runs it with little else imported.

tiles

Builds the whole Galaxy Map's node cache from scratch (PERF.233): every node of every level of the whole galaxy (a block of each level that holds a generated sector or a placed object, and each generated sector), into a new cache beside the live one, swapped in when it is complete. The live cache keeps serving until the swap, a run that is killed leaves it as it was, and running it again picks up the nodes already built. The map's address space is 23.9 billion cells; only the populated part is a node. It builds a level at a time, biggest blocks first, tile_cache.build_workers processes at once (0 is one per core), with one progress line per level, builds with no cache budget and no pruning, and checks the data once more before the swap: a change meanwhile deletes just the nodes it touched, which are built again. It refuses to start unless twice the projected size (110 KB a sector node and 45 KB a block node at most) is free on the cache's disk, saying the figures (--force builds anyway). Run it as the web server's user so Apache can read what it writes. --workers N overrides the setting and --no-swap leaves the finished cache in the .build folder under the cache root. It exits 0 done, 1 failed, 75 when an update is running (nothing was built) and 130 when stopped. The maintenance example examples/maintenance/planetgen-tiles@.timer runs it nightly at 05:00 after the orbit update, then planetgen warm rebuilds the lists, objects and search. The sizes and times it was planned from are in reports/perf233-tile-cache-cost-2026-11-04.md. cache.max_mb no longer counts the nodes built ahead (this build's and the warm-up's): it is the allowance of the nodes visits asked for.

python3 -m planetgen.cli.tiles

orbits

The positional update. Each planet, moon, star, binary pair, comet, facility and standalone phenomenon keeps its own clock (epoch_unix) and a time it next needs storing (next_update_due); a run moves only what is due, from its own epoch to now by the database server's clock, then refiles anything that drifted into another sector, refreshes containment (nebulae and remnants), nearest systems and location text, and recomputes the sector paths. A run prints how many years passed since the last one, what it moved and how many objects changed sector. It never moves anything backwards: if the server's clock went back it says so, moves nothing and restarts the clock. There is no update-orbits command; this is it. Run it from cron or by hand, as often as you like (a run with nothing due changes nothing):

python3 -m planetgen.cli.orbits

worker

One RQ worker, at the lowered priority generation workers run at. The site and the generation runs start these themselves (planetgen.queue.workers.ensure_workers); run one by hand only to add capacity or to watch one. Redis is read from --url, else PLANETGEN_REDIS_URL, else redis.url in config.json.

  • QUEUE ...: the queues to serve, first one first (default: the interactive queue). A worker serves one kind of queue, the web queues or a run's own, never both. The site keeps lanes of its own: planetgen-bulk (a run's units, up to the admin's worker count), planetgen-interactive (short API jobs: queue.interactive_workers workers, outside that count, at a higher priority than the others) planetgen-maintenance (the units of the cache warm-up and the database check, and the tile prefetch and rebuild: while a generation run is live queue.maintenance_workers workers, taken out of the admin's worker count, with a generation worker finishing its unit and leaving when the lane needs its place; with no generation run live the whole count; PERF.150) and planetgen-long (API jobs expected to take longer than queue.long_job_seconds, a neighbourhood or a large settle: queue.long_workers workers), so a long job never holds the worker kept for short ones (PERF.151).
  • --burst: exit once the queues are empty.
  • --idle-seconds <int>: exit after this long without work (default 60; ignored with --burst).
  • --name <name>: the worker's name (default: RQ picks one).
  • --url <redis-url>: the Redis server.
python3 -m planetgen.cli.worker --burst

query

Lists what is stored, read-only. The subcommands are sectors (the sectors with their size and system count), systems, near, planets and moons.

  • sectors [--limit N] [--after ID] and systems [--star-type TYPE] [--sector-id ID] [--limit N] [--after ID]: --limit sectors or systems at a time (default 100; --limit 0 lists every one, which on a big galaxy reads them all), the sectors nearest the galactic core first and the systems by name. When more follow, the last line prints the --after to carry on with; a page starts after that row by key, so any page costs what the first does (PERF.211).
  • near PLACE --distance PC [--kinds a,b] [--limit N] [--offset N]: everything within a distance (at most 50 pc) of an object (system:<ID>, planet:<ID>, nebula:<ID> ...; a bare three-part ID is a system) or of a galaxy-frame point x,y,z in parsecs.
  • planets and moons: [--class C] [--min-radius-km N] [--max-radius-km N] [--sector-id ID] [--system-id ID] [--limit N] [--after ID]: they list in order of system name, system, orbit (a moon's planet's orbit, then its own), then ID, --limit planets or moons at a time (default 100; --limit 0 lists every one, which on a big galaxy reads them all). When more follow, the last line prints the --after to carry on with; a page starts after that planet or moon by key, so any page costs what the first does (PERF.207).
python3 -m planetgen.cli.query sectors
python3 -m planetgen.cli.query planets --class M --sector-id <ID>
python3 -m planetgen.cli.query planets --limit 50 --after <ID of the last planet shown>

migrate

Applies any schema migration the database is missing and does nothing if it is current. install.sh and update.sh run it, so you rarely need to. It shows a progress bar (a line per step when output is not a terminal). --status prints <current version> <target version> <pending steps> <database> and changes nothing, which is how update.sh decides whether to ask about the database. A database older than schema v61 is refused.

python3 -m planetgen.cli.migrate --status

datasets

Downloads the static data files the generator reads (GEN.548) into a cache folder outside the checkout, /var/cache/planetgen/datasets (PLANETGEN_DATA_DIR moves it). install.sh and update.sh run fetch once at setup, as root, and make the folder readable for Apache's user; nothing downloads while the site or the generator runs. Each file is requested with the standard User-Agent, must have the size and sha256 the catalogue states, and is kept by an atomic rename, so an interrupted run leaves no half file. fetch prints one line per dataset and, under it, one line per file with its https URL and what happened to it: fetched (requested and kept), kept (already there with the right size and sha256, not requested again) or failed (with the reason); update.sh and install.sh show these lines. A dataset whose host does not answer, or whose file does not match, stays missing; fetch then prints the reason and exits 1, which the scripts report as a warning and not as a failure. status fetches nothing, says which datasets are present, prints the URL of every file that is missing, and exits 1 while one is missing. Bulk generation needs them (GEN.590): galaxy, plan, population and sector --num-sectors above 1 refuse to start while a dataset is missing, naming it and writing nothing, as with the math check; so do the Sector page's neighbourhood button and the Generate page's jobs, whose second step, "Check the data", is status (before the reset, so nothing is wiped for a run that cannot start). The refusal names what to do: each missing dataset, why, every file to download with its URL, and the setup command (python3 -m planetgen.cli.datasets fetch KEY, which update.sh runs for you). Unless the run is told, in so many words, to disregard missing data (GEN.599): --disregard-missing-data on the command line, the "Disregard missing data files" box on the Generate page, "disregard_missing_data": true in the neighbourhood request. The run then starts, prints which datasets are missing and the labelled fallback each takes (status --disregard-missing-data does the same and exits 0 for a dataset that has one), and hands the option to every worker through its run record; the command line is in the galaxy's run history, so a galaxy built that way can be told. The fallbacks: no main-sequence luminosity, temperature, radius or lifetime for a star (an open item on the star), the zero-temperature Chandrasekhar radius for a white dwarf with no layers, and the one [R0722] outer crust for a neutron star. Nothing falls back without the option.

python3 -m planetgen.cli.datasets fetch
python3 -m planetgen.cli.datasets status

reset

Empties every generated table of the galaxy (TRUNCATE, so the schema stays), keeping schema_migrations and the id counters (id_blocks), so the next galaxy's ids carry on past the old one's. It never touches the control database (admin accounts, sessions, API keys, audit log). It cannot be undone. By default it asks you to type the database's name back; --yes skips that for scripts. Look first with --dry-run, which lists each table and its row count and changes nothing.

python3 -m planetgen.cli.reset --dry-run

lockouts

For an admin locked out of the site. It lists what is locked and does nothing else; the lockouts live in Redis, on the rate-limit storage (ratelimit.storage_uri, else redis.url).

python3 -m planetgen.cli.lockouts

lift_lockout

Lifts login lockouts, on the same storage. One of these is needed:

  • --ip ADDRESS: lift one address (an IPv6 address by its /64).
  • --user NAME: lift one username.
  • --all: lift every lockout.

Each lift is written to the activity log as DB lockout.lift.

python3 -m planetgen.cli.lift_lockout --ip 203.0.113.5

forget_devices

forget_devices USER: that admin's browsers lose their trusted-device cookies, so the next sign-in asks for the two-factor code again. Written to the activity log as DB devices.revoke.

accounts

accounts --set-owner USER: makes that account the one Owner (USR.31), the old Owner becoming an admin. The Owner changes the Owner-tier settings (the mail server, the site's address, the From address) from the Settings page after typing the password again; this is the way back when that account is lost. Written to the activity log as DB owner.set. The rest of the accounts commands come with USR.26.

reset_two_factor

reset_two_factor USER: turns off that admin's two-factor sign-in, for a lost phone and lost recovery codes. The admin signs in with the password and can set it up again. Written to the activity log as DB totp.reset.

config

config.json is the one file that holds all program configuration, your own copy of config.json.example. check validates it the way the app reads it (an unknown key is an error) and exits 1 naming every field that does not fit. docs rewrites the generated parts, the option table in config.md, config.json.example and config.schema.json, from the settings model; a test fails when they differ from what it would write, so run it after changing an option.

get [OPTION] prints the value that applies and where it comes from (default, config.json or an environment variable; a secret shows only (set) or (empty)). set OPTION=VALUE ... and unset OPTION ... change config.json through the same writer as the Admin settings page (config.md): every value is checked first and one bad value saves nothing, the old file is backed up, and each change gets an audit row (when the control database is reachable) and an activity-log line. The command prints what needs a restart. A value is read as JSON for a number, true or a list and as text otherwise (set site_name="My galaxy" cache.max_mb=300); OPTION=- reads it from standard input, which keeps a secret out of the shell history. restore ARCHIVE puts the settings of a backup archive back (planetgen.cli.backup list shows the archives), backing up the current file first. Every option may be set here, the database, the secrets and the Owner-only ones included, because whoever can run the command owns the server; the Admin page cannot change those. If config.json does not exist the command says so and creates nothing.

python3 -m planetgen.cli.config check
python3 -m planetgen.cli.config docs
python3 -m planetgen.cli.config get cache.max_mb
python3 -m planetgen.cli.config set cache.max_mb=300 site_name="My galaxy"
python3 -m planetgen.cli.config unset cache.max_mb
python3 -m planetgen.cli.config restore 20261016T193012Z.tar.bz2

backup

Backup archives (ADM.87, config.md): one .tar.bz2 per backup, holding a part per kind of data (settings, a copy of config.json; parity, a copy of the sector repair file, which settings.backup_parity switches off and restore --part parity ARCHIVE puts back, then checks against the database; the control database in 9.0). Run it as root or the web user (the archives are mode 0600).

python3 -m planetgen.cli.backup take                    # every part (--part NAME for some)
python3 -m planetgen.cli.backup list                    # newest first, with each archive's parts
python3 -m planetgen.cli.backup verify ARCHIVE          # check every hash
python3 -m planetgen.cli.backup restore ARCHIVE         # the whole archive, or --part NAME for some
python3 -m planetgen.cli.backup parts                   # the parts this build can back up

A restore verifies the archive, backs up what it is about to replace in a safety archive, skips and reports a part this build has no provider for, and writes an audit row. settings.backups_kept of the archives are kept.
